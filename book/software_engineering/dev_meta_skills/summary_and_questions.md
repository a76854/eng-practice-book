## 本章小结

- **工程化项目结构是协作的起点**：`src` 布局通过物理隔离暴露导入与打包问题，`pyproject.toml` 统一构建与元数据，二者共同构成“可安装、可测试”的最小工程契约。
- **依赖与虚拟环境是“声明 → 隔离 → 落地”的闭环**：`venv` / `conda` / `virtualenv` 负责“在哪跑”（虚拟环境工具），`uv` 负责“要什么、怎么装”（项目管理工具），选型应基于是否管理 Python 版本与原生依赖；隔离的本质是独立的解释器，而 `pyproject.toml → 创建环境 → pip install -e . / uv sync` 构成从声明到可运行的完整链路。
- **Git 工作流让版本管理可预期**：分支隔离并行开发、小步提交让历史可读、用 PR 承载 Review 与 CI 校验。
- **Shell 的核心是可组合的文本流水线**：文件系统提供统一的路径抽象，进程提供隔离的执行上下文，管道提供"单件工具 + 文本流"的组合能力。`find/grep/awk/xargs` 各司其职，串起来就是一套完整的任务编排。
- **自动化脚本把操作变成代码**：`argparse` 负责命令行接口，`pathlib` 负责跨平台路径，`shutil` 负责文件操作，`subprocess` 负责进程调用。--dry-run、阈值确认、配置外部化、日志可观测让自动化脚本放心使用。

## 思考题

1. **架构演进**：一个项目从单个 `main.py` 起步，逐步演化为 50 个文件、5 个子模块、3 个外部依赖的复杂项目。如果完全不重构目录结构，最终会触发哪些导入与维护问题？请结合"扁平布局"的三个核心缺陷（可安装性、导入歧义、元数据散落）分析每个阶段的标志性症状和触发阈值。

2. **`src` 布局的误用**：有同学说"既然 `src` 布局这么好，我把所有项目都改成 `src` 布局"。但 `src` 布局不是SliverBullet。请思考：什么样的项目（规模、类型、使用场景）用 `src` 布局反而增加了不必要的复杂度？你的判断依据是什么？

3. **`__init__.py` 的设计权衡**：`__init__.py` 既可以保持为空，也可以将子模块的 API 全部导入并暴露给用户。请讨论这种设计选择的两面性：过度暴露 API 会带来什么风险？保持空文件又会让用户的使用体验产生什么代价？你在实际项目中如何把握这个度？

4. **依赖管理的取舍**：`uv` 比 `pip` 快 10–100 倍，`conda` 能管理 Python 版本和原生库，`venv` 零额外依赖。请针对以下三种场景分别推荐最合适的方案，并说明理由：
   - 场景 A：大四毕业设计，需在答辩电脑上演示，且该电脑不允许安装任何额外软件
   - 场景 B：深度学习项目，需用 CUDA 11.8 和 PyTorch 2.0，团队 5 人共用一台 GPU 服务器
   - 场景 C：SaaS 产品后端，CI 流水线每天触发 50 次，每次构建时间直接影响团队迭代速度

5. **提交粒度**：Git 提倡"一个提交只做一件事"。但在实际开发中，"一件事"的粒度边界很模糊。请给出你对以下两种策略的取舍分析：
   - 策略 A：频繁提交（每 10 分钟一次，甚至包含拼写错误修复）
   - 策略 B：延迟提交（功能完全跑通后才整体提交）
   每种策略在 Code Review、git bisect 定位 bug、多人协作冲突三个场景下各有什么成本？你认为理想的提交粒度是"多久一次的代码"？

6. **工作流选型**：GitHub Flow 只有 `main` + 功能分支，Git Flow 引入了 `develop`、`release`、`hotfix` 分支。请从"发布频率"和"团队规模"两个维度，画出一个决策矩阵：什么情况下用 GitHub Flow，什么情况下用 Git Flow，什么情况下需要自定义混合方案。

7. **管道思维的本质**：Shell 管道 `find | xargs | sort` 和 Python 的生成器表达式 `(process(f) for f in files if condition)` 都在做"流水线式数据处理"。但两者有一个根本差异：Shell 管道的每个阶段是独立进程，Python 生成器是同一进程内的惰性求值。请分析这一差异在以下三个维度上的影响：
   - 并行能力：每个阶段能否并行执行？
   - 错误恢复：某个阶段失败时，其他阶段的状态如何？
   - 资源开销：进程上下文切换 vs 函数调用栈

8.  **自动化脚本的角色边界**：在工程化项目中，`Makefile`、Shell 脚本、Python 脚本都可以实现"自动化"。请根据以下三个特征建立决策树，判断一个给定任务应该用哪种工具实现：
    - 特征 A：任务是否需要跨平台（Windows / Linux / macOS）一致运行？
    - 特征 B：任务是否需要复杂的条件分支或错误恢复策略？
    - 特征 C：任务是否需要读写结构化数据（Excel、JSON、数据库）？
    然后应用你的决策树分析"构建 Docker 镜像并推送"和"解析 Jenkins 日志生成测试报告"两个具体任务。

9.  **`--dry-run` 的一致性**：一个优秀的 `--dry-run` 模式需要做到"预览结果与正式执行完全一致"。但现实中做到这一点非常困难——文件系统在两次运行之间可能发生变化，进程调用可能有副作用，时间戳本身就会改变输出。请讨论：你认为 `--dry-run` 的"一致性保证"应该做到什么程度？是完全不可能实现的理论目标，还是可以基于实际工程需要设置合理边界？你如何在设计中平衡"预览准确"与"实现复杂度"？

10. **提交历史的审计价值**：一个生产事故发生后，你需要定位"谁在什么时候、出于什么原因、改了哪一行代码导致了这次事故"。请分析：什么样的提交历史能让这个追溯过程在 5 分钟内完成？什么样的提交历史会让这个过程需要 2 小时甚至无法定位？请给出具体例子对比"好提交历史"和"坏提交历史"在事故定位时的实际体验差异。

11. **脚本的测试困境**：自动化脚本往往直接操作文件系统、网络、进程，天然难以单元测试。请提出一个策略：如何将脚本设计成"核心逻辑可测试、边界操作可模拟"的结构？请用伪代码或类图说明你的设计方案，并讨论这种设计带来的代码量增加是否值得。

12. **工具链的锁定效应**：当你用 `uv` 初始化了一个项目，项目里有了 `uv.lock`，团队习惯了 `uv sync` 和 `uv run`，这时想切回 `pip` + `venv` 的代价是什么？除了技术迁移成本，还有哪些隐性成本（团队习惯、CI 配置、文档、新成员 onboarding）？这种"锁定效应"是否意味着你在做技术选型时必须更加谨慎，倾向于选择更成熟、更通用的工具？。
