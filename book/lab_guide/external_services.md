# 实验五 大模型摘要与缓存

本实验对应理论 [第 11 章 与外部世界的集成](../advanced_engineering/external_integration/index.md)。建议先通读 [大模型调用方法](../advanced_engineering/external_integration/llm_calling.md) 与 [缓存与 Redis](../advanced_engineering/external_integration/redis_cache.md)，再动手。

本实验**基于实验三的后端做增量改造，不重写服务**。你要在已有的搜索与收藏接口之上，增加文档摘要能力，并给热点数据加上缓存。

## 实验目标

通过完成外部集成，你将：

1. **调用大模型生成摘要**：对指定文档生成摘要，支持流式返回，并说清密钥为什么只能放在服务端。
2. **用 Redis 做旁路缓存**：让摘要与热搜结果命中缓存直接返回，未命中再回源并写回。
3. **理解缓存三问题**：能说清穿透、击穿、雪崩的成因，并在代码里落地其中一种解法。
4. **为外部依赖设计降级**：密钥缺失或缓存不可用时，主流程仍然可用，接口不整体失败。
5. **增量改造而非重写**：在不改变原有接口契约的前提下，把新能力接进现有服务。

## 背景故事

实验三的后端上线了，搜索能用，收藏也能存。但产品提了两个新要求：第一，用户希望每条文档能一键生成摘要，不用点开原文；第二，搜索很频繁，每次都去外部检索成本和延迟都高，热门关键词的结果应该缓存起来。

这两个要求都指向同一件事：把外部能力接进已有的服务。你不需要重写后端，只需要在现有代码上增加接口与缓存层，并保证外部服务出问题时服务还能站住。

## 预备知识

**在实验三基础上新增的接口**

| 方法 | 路径 | 说明 | 成功 | 失败 |
|------|------|------|------|------|
| GET | `/api/summary?doc_id=` | 返回文档摘要 | 200（含 `summary`） | 404 文档不存在 |
| GET | `/api/summary/stream?doc_id=` | 流式返回摘要 | 200（`text/event-stream`） | 404 |

**流式响应约定**

- 响应头 `Content-Type: text/event-stream`，`Cache-Control: no-cache`。
- 每个增量写成一行事件：`data: {"delta": "..."}`，以两个换行结束。
- 结束后发送 `data: [DONE]`。

**缓存约定**

- 摘要缓存键：`summary:{doc_id}`；搜索结果缓存键：`search:{关键词}`。
- 缓存需要设置过期时间，避免数据长期陈旧。

**环境变量**

| 变量 | 用途 | 缺失时的行为 |
|------|------|--------------|
| `LLM_API_KEY` | 调用大模型 | 摘要接口返回固定降级文案 |
| `LLM_BASE_URL` | 大模型服务地址 | 使用默认地址 |
| `REDIS_URL` | 连接 Redis | 跳过缓存，直接回源 |

**环境约定**

- 缓存可用 `fakeredis` 在本地替代真实 Redis，接口不变。
- 大模型用 OpenAI 兼容接口，用 `openai` 客户端指向 `LLM_BASE_URL`。
- 沿用实验三的目录结构，新增能力放在 service 与 repository 层，不破坏原有契约。

# 任务一：普通摘要接口

## 任务目标

在现有后端上增加一个摘要接口，调用大模型生成摘要。

## 需求

1. 实现 `GET /api/summary?doc_id=`：找到对应文档，调用大模型生成摘要，返回 `{"summary": "..."}`。
2. 大模型调用单独封装成 repository 层的一个接口，Service 不直接持有 SDK 客户端。
3. 文档不存在时返回 404。
4. 密钥从 `LLM_API_KEY` 读取，绝不写进代码或返回给前端。
5. 未配置密钥时返回固定降级文案，接口不报 500。

## 验收标准

| 验收项 | 具体要求 |
|--------|----------|
| 接口可用 | 指定存在的 `doc_id` 返回摘要 |
| 分层到位 | 大模型调用在 repository 层，Service 只面对接口 |
| 密钥外置 | 密钥来自环境变量，响应中不含密钥 |
| 降级可用 | 无密钥时返回固定文案而非报错 |

## 提交要求

```bash
git switch -c exp/01-summary
git add src/ tests/
git commit -m "feat: add document summary endpoint with llm repository"
git push -u origin exp/01-summary
```

# 任务二：流式摘要

## 任务目标

让摘要以流式返回，前端可以边收边渲染，降低首字等待。

## 需求

1. 实现 `GET /api/summary/stream?doc_id=`，按预备知识中的流式约定返回。
2. 用生成器逐块 `yield` 事件行，最后发送 `data: [DONE]`。
3. 异常不能把堆栈或密钥透传到响应，统一转成可读的降级文案。
4. 用 `curl -N` 能观察到事件逐块到达，而不是等全量后一次性返回。
5. 保持接口契约：响应头、事件格式与结束标记符合约定。

## 验收标准

| 验收项 | 具体要求 |
|--------|----------|
| 事件格式 | 事件行符合 `data: ...`，以 `data: [DONE]` 结束 |
| 首字可感 | 用 `curl -N` 或浏览器可见逐块到达 |
| 错误脱敏 | 异常返回可读文案，不含堆栈与密钥 |
| 契约一致 | 响应头与事件格式符合约定 |

## 提交要求

```bash
git switch -c exp/02-streaming-summary
git add src/ tests/
git commit -m "feat: stream summary over server-sent events"
git push -u origin exp/02-streaming-summary
```

# 任务三：Redis 旁路缓存

## 任务目标

给摘要与搜索结果加上旁路缓存，命中即返回，未命中回源写回。

## 需求

1. 读路径先查缓存：命中直接返回，未命中回源并把结果写入缓存，并设置过期时间。
2. 缓存键按预备知识的约定组织，避免不同关键词或文档互相覆盖。
3. 缓存操作封装在 repository 层，Service 通过接口使用，不直接依赖客户端细节。
4. `REDIS_URL` 缺失或连接失败时，跳过缓存直接回源，功能不受影响。
5. 用一个测试证明：第二次相同请求命中缓存，不再回源。

## 验收标准

| 验收项 | 具体要求 |
|--------|----------|
| 旁路生效 | 命中直接返回，未命中回源并写回 |
| 键设计 | 缓存键区分文档与关键词，含过期时间 |
| 分层 | 缓存细节在 repository 层 |
| 可降级 | 缓存不可用时自动跳过，功能正常 |

## 提交要求

```bash
git switch -c exp/03-redis-cache
git add src/ tests/
git commit -m "feat: add redis cache-aside for summary and search"
git push -u origin exp/03-redis-cache
```

# 任务四：缓存三问题与降级收口

## 任务目标

识别并处理缓存的穿透、击穿、雪崩，并把降级逻辑收口成一处。

## 需求

1. 针对下面三种情况，各说明成因，并至少落地一种解法：
   - 穿透：请求不存在的键，缓存始终不命中，请求全压到后端。
   - 击穿：热点键过期的瞬间，大量请求同时回源。
   - 雪崩：大量键在同一时刻集中过期。
2. 把外部依赖（大模型、缓存）的失败与降级逻辑收敛在一处，避免散落在各个接口。
3. 设计一个可演示的降级场景：故意让缓存不可用或让大模型请求失败，验证主流程仍可用、返回降级标记。
4. 在报告中说清：什么情况下缓存有效，什么情况下反而增加复杂度。

## 验收标准

| 验收项 | 具体要求 |
|--------|----------|
| 原理清楚 | 能说清穿透、击穿、雪崩的成因 |
| 解法落地 | 至少一种解法有代码与测试佐证 |
| 降级收口 | 外部失败与降级集中处理，不散落 |
| 演示可复现 | 能现场制造一次失败并展示降级结果 |

## 提交要求

```bash
git switch -c exp/04-cache-degradation
git add src/ tests/
git commit -m "feat: handle cache failure modes and centralize degradation"
git push -u origin exp/04-cache-degradation
```
