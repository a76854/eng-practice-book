# 工程化项目结构

> 学完本节，你能回答：为什么“能跑”的脚本不等同于“可维护”的项目？为什么 `src` 布局值得作为默认选择？`pyproject.toml` 的每个字段在构建链路中扮演什么角色？

## 从脚本到项目：缺了什么

初学者的典型起点是一个单文件脚本 `app.py`，同目录下再放几个工具文件。跑得动，但很快会遇到三类真实问题：

1. **导入歧义**：当测试文件也在项目根目录时，`import mymodule` 可能意外导入了根目录的同名文件而非已安装的包，导致“本地能跑、CI 失败”。
2. **元数据分散**：`setup.py`、`setup.cfg`、`requirements.txt` 各管一摊，新人不知道改哪一个，版本、依赖、入口点没有单一事实源。
3. **可安装性缺失**：无法 `pip install -e .` 后在任意目录 `import`，导致 demo、测试、脚本各自用 `sys.path` hack。

工程化的第一步，就是用**约定的目录结构 + 声明式的项目描述**把上述问题一次性收敛。

## 两种布局：扁平 vs `src`

```
# 扁平布局（不推荐作为默认）
myproject/
  mypackage/
    __init__.py
  tests/
  pyproject.toml

# src 布局（推荐）
myproject/
  src/
    mypackage/        # 真实包代码
      __init__.py
      audio.py
  tests/              # 测试与包代码物理隔离
  pyproject.toml
  README.md
```

`src` 布局的核心价值是**强制隔离**：测试与脚本无法通过“当前目录恰好在 `sys.path` 首位”侥幸导入源码，必须经过安装（`pip install -e .`）才能 `import mypackage`。这恰好暴露了缺失的 `__init__.py`、错误的 `packages` 配置等问题，而不是把它们掩盖到上线后。以通用示例为例，安装后应能在任意目录执行 `import mypackage`，而不是依赖 `sys.path` 的临时 hack。

> **环境约定**：本书面向 Linux，路径统一用 `/` 书写，目录树示例不再标注平台差异。

## `pyproject.toml`：PEP 517 / 518 / 621 的统一入口

`pyproject.toml` 用一个文件回答三件事：

- **PEP 518 — 用什么工具构建**：`[build-system]` 声明 `requires` 与 `build-backend`，让 `pip` 知道该调用 `setuptools` 还是 `hatch` / `poetry`。
- **PEP 517 — 如何构建**：`build-backend` 指向的后端负责把源码打包成 wheel / sdist，前端（`pip` / `build`）无需关心细节。
- **PEP 621 — 项目是谁**：`[project]` 段以声明式方式描述 `name`、`version`、`dependencies`、`requires-python` 等元数据，替代分散的 `setup.cfg` 与 `requirements.txt`。

以通用项目 `myproject` 为例（文件 `pyproject.toml`）：

```toml
[build-system]
requires = ["setuptools>=61"]
build-backend = "setuptools.build_meta"

[project]
name = "myproject"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = ["numpy>=1.26", "soundfile>=0.12"]

[tool.setuptools]
packages = ["mypackage"]
```

一个更完整的生产形态会进一步利用同一文件收敛其他配置，例如用 `[project.scripts]` 定义命令行入口、`[project.optional-dependencies]` 区分 `dev` 与可选依赖、`[tool.ruff]` / `[tool.mypy]` 收敛代码质量工具——**一个文件即是项目的单一事实源**。

```bash
# 查看项目元数据
cat pyproject.toml

# 可编辑安装，验证 src 布局是否正确（以教学包 m2t 为例）
pip install -e .
python -c "import m2t; print(m2t.__version__)"
```

> **贯穿案例 — MeetingToText**：教学仓 `eng-practice-book` 的 `m2t` 包与真实项目 `MeetingToText` 的 `backend/app` 分层，都遵循同样的“约定目录 + 声明式描述”思想。前者通过 `packages = ["m2t"]` 让正文示例可 `import m2t`，后者在一份 `pyproject.toml` 中用 `[project.scripts]` 定义 `meetingtotext` 命令、`[project.optional-dependencies]` 区分 `dev` 与 `asr`，都是“一个文件即单一事实源”的具体落地。

## 可运行示例：解析 `pyproject.toml`

下面用标准库解析 `pyproject.toml`，验证 PEP 621 字段是否符合预期。示例采用**字符串内嵌 TOML** 的方式，避免对文件路径的依赖，保证在 MyST 构建环境中可复现；同时演示 `tomllib`（Python 3.11+）的用法，真实项目中可替换为 `pathlib.Path("pyproject.toml").read_bytes()` 后解析。

文件 `book/part1_software_engineering/chapter01_dev_meta_skills/demo_pyproject.py`：

```{code-cell} ipython3
import sys
# tomllib 在 Python 3.11+ 为标准库；兼容写法
try:
    import tomllib
except ModuleNotFoundError:
    import tomli as tomllib  # type: ignore
import textwrap

toml_text = textwrap.dedent("""
[build-system]
requires = ["setuptools>=61"]
build-backend = "setuptools.build_meta"

[project]
name = "myproject"
version = "0.1.0"
description = "示例教学包（通用）"
requires-python = ">=3.12"
dependencies = ["numpy>=1.26", "soundfile>=0.12"]

[project.optional-dependencies]
dev = ["pytest>=8.0", "ruff>=0.9"]

[tool.setuptools]
packages = ["mypackage"]
""").strip()

# tomllib.loads 接收 bytes（3.11 标准）；做兼容处理
try:
    data = tomllib.loads(toml_text)
except TypeError:
    data = tomllib.loads(toml_text.encode())

proj = data["project"]
build = data["build-system"]
print("name:", proj["name"])
print("version:", proj["version"])
print("requires-python:", proj["requires-python"])
print("build-backend:", build["build-backend"])
print("deps:", proj["dependencies"])
print("optional dev:", data["project"]["optional-dependencies"]["dev"])
# 断言：保证契约符合预期（通用示例以 myproject 命名；教学包 m2t 结构与此一致）
assert proj["name"] == "myproject"
assert "numpy" in proj["dependencies"][0]
assert build["build-backend"] == "setuptools.build_meta"
# 预期输出:
# name: myproject
# version: 0.1.0
# requires-python: >=3.12
# build-backend: setuptools.build_meta
# deps: ['numpy>=1.26', 'soundfile>=0.12']
# optional dev: ['pytest>=8.0', 'ruff>=0.9']
```

> **工程启示**：`pyproject.toml` 不是“配置文件”，而是“项目契约”。把它作为唯一事实源，配合 `src` 布局与 `pip install -e .`，后续的虚拟环境、测试、打包、CI 才能建立在同一套可复现基座上。更多质量门禁见 [第2章 构筑代码质量的护城河](../chapter02_code_quality/index.md)。

> **贯穿案例 — MeetingToText**：在 MeetingToText 中，上述契约直接决定了示例能否复现。教学仓用 `m2t` 包承载 `resample_audio`、`TaskStore` 等最小实现，真实项目用 `backend/app` 分层承载完整服务，二者都依赖“声明式描述 + 可安装布局”来避免“相对路径拼凑导入”的常见陷阱。

文件 `book/part1_software_engineering/chapter01_dev_meta_skills/demo_layout_check.py`（校验 `src` 布局的导入隔离）：

```{code-cell} ipython3
import pathlib, sys
# 模拟检查：src 布局下，包应可被导入且路径指向 src/m2t 或 m2t
import m2t, inspect
pkg_path = pathlib.Path(inspect.getfile(m2t)).resolve()
print("m2t file:", pkg_path)
# 关键判断：包路径不应是当前工作目录的临时脚本
assert "m2t" in pkg_path.parts
print("src 布局校验通过：import m2t 指向已安装包，而非临时脚本")
# 预期输出:
# m2t file: .../m2t/__init__.py
# src 布局校验通过：import m2t 指向已安装包，而非临时脚本
```
