# 工程化项目结构

学完本节，你能回答：

- 为什么"能跑"的脚本不等同于"可维护"的项目？
- 为什么 src 布局值得作为默认选择？
- pyproject.toml 的每个字段在构建链路中扮演什么角色？

> 一个项目如果只有扁平结构，就像火锅里的一根粉条——你夹住了这头，却不知道那头在哪里；它看似完整，却在锅里纠缠不清，一根夹不断，一团吃不完。 —— 每一个踩过导入坑的 Python 开发者

扁平布局之所以危险，恰恰因为它"看起来能跑"。就像粉条刚下锅时条条分明，但随着时间推移，它缠成一团——你无法单独夹起一根而不带起别的。代码也一样：`main.py`、`utils.py`、`test.py` 挤在同一个目录，起初各司其职，但很快你会发现 import 语句像火锅里的粉条一样，牵一发而动全身。改一个文件，不知道会影响到谁；加一个测试，不知道会导入哪个同名模块。"能跑"是暂时的幻觉，"可维护"才是工程的真问题。

## 从脚本到项目：缺了什么

初学者的典型起点是一个单文件脚本 `main.py`，同目录下再放几个工具文件。代码能跑起来，但很快就触及真实工程的边界。

假设你在写一个音频处理工具，目录结构如下：

```
audio_tool/
├── main.py          # 入口，调用 processor.py
├── processor.py     # 核心处理逻辑
├── utils.py         # 辅助函数
├── test_processor.py # 测试文件
└── config.py        # 配置常量
```

一切看似正常。直到有一天，你想在另一个项目里复用 `processor.py` 中的音频处理功能。你写了 `from audio_tool.processor import AudioProcessor`，却报 `ModuleNotFoundError`。你把 `audio_tool` 文件夹复制到新项目的目录下，调整了导入路径，总算能跑了。但过了一个月，你在第三个项目中又要用到这个功能——同样的代码，同样的导入错误，你不得不第三次折腾路径。

你花时间才发现：`from audio_tool.processor` 能工作，完全是因为运行目录恰好包含了 `audio_tool` 这个文件夹。一旦离开这个"恰好"，Python 根本找不到它。

这个问题的根源在于：**你依赖的是"当前目录恰好在导入路径上"这个偶然条件，而不是一个明确可安装的包**。

上述困境并非个例，它暴露了脚本式项目普遍缺少的三个要素：

**1. 可安装性缺失**

一个健康项目的标准是：在任何目录下执行 `python -c "import audio_tool"` 都能成功。但扁平结构的项目做不到——`import` 行为完全取决于运行时的当前目录。于是常见的补救措施是在每个文件开头写：

```python
import sys
sys.path.append("..")  # 或更复杂的相对路径 hack
```

这种"临时修路"式的做法，让每个脚本都成了"孤岛"：

- 你在 `main.py` 里能 `import processor`，但换到 `tests/` 目录下就不行
- 你在 Jupyter Notebook 里调试能导入，但写成 `.py` 文件又报错
- 你把代码发给同事，他在自己的机器上跑不起来，因为目录结构稍有不同

你无法 `pip install -e .` 后在任何地方 `import`，导致 demo、测试、脚本各自为政，复用更是奢望。

**2. 导入歧义**

扁平布局下，项目根目录同时承载着源码、测试、脚本等多个角色。Python 的导入机制会把当前目录排在 `sys.path` 首位，这意味着：

- 测试文件 `test_processor.py` 中的 `import processor` 可能导入源码 `processor.py`，也可能导入另一个同名测试辅助文件
- 当项目逐渐变大、引入第三方包时，如果本地有一个文件恰好叫 `requests.py`，它会遮蔽真正的 `requests` 库
- 你在一个目录下能跑，换个目录就不行，因为 Python 找到的是不同的文件

这些问题的本质是：**源码与测试、脚本混杂在同一命名空间，没有清晰的边界**。

**3. 元数据散落**

即便你意识到了需要声明"这是一个项目"，Python 历史上也缺乏统一入口：

- `requirements.txt` 只列依赖，却管不了项目名称和版本
- `setup.py` 能声明元数据，但它是可执行脚本，容易引入副作用
- `setup.cfg` 是声明式，但和 `setup.py` 分工模糊
- `MANIFEST.in` 还要单独控制打包哪些文件

新人接手一个项目，常常要问："改版本号改哪里？添加依赖改哪个文件？入口命令怎么定义的？"因为答案分散在四五个文件中，没有单一事实源。

### 工程化的起点

上述三个问题——不可安装、导入混乱、元数据分散——看起来彼此独立，但解决方案是统一的：**用约定的目录结构 + 声明式的项目描述文件**。

- **目录结构**把源码、测试、资源隔离到不同位置，从物理上避免命名空间污染
- **项目描述文件**用一份声明式的配置完整定义"这个项目是什么、依赖谁、怎么安装"

接下来的两节会分别展开：先看目录布局如何解决"可安装性"与"导入歧义"，再看 `pyproject.toml` 如何一统元数据。

`src` 布局的核心价值是**强制隔离**：测试与脚本无法通过"当前目录恰好在 `sys.path` 首位"侥幸导入源码，必须经过安装（`pip install -e .`）才能 `import mypackage`。这恰好暴露了缺失的 `__init__.py`、错误的 `packages` 配置等问题，而不是把它们掩盖到上线后。

## 依赖管理的演进：从 `requirements.txt` 到 `pyproject.toml`

有了目录结构，接下来要解决"项目是什么"——它的名字、版本、依赖谁、怎么安装。过去很长一段时间，Python 社区依靠一系列分散的文件来回答这些问题。

### `requirements.txt` 的局限

`requirements.txt` 是最为人熟知的依赖清单，它诞生于一个更简单的时代：逐行列明 `pip install` 需要的包名与版本。它的写法很直观：

```
numpy>=1.24.0
requests>=2.31.0
pytest>=7.0.0
```

但仅有它远远不够。真正的问题是：

- **职责模糊**：`requirements.txt` 只能列出依赖，但项目名称、版本、作者、入口点、可选依赖这些元数据没有地方放，于是又冒出 `setup.py`、`setup.cfg`、`MANIFEST.in` 凑成"项目描述全家桶"。
- **区分不明**：运行时依赖与开发依赖挤在同一个文件，要么全装，要么手动拆分出 `requirements-dev.txt`，靠约定而非规范来区分。
- **安装方式不统一**：用 `pip install -r requirements.txt` 只能装依赖，无法"安装项目本身"（即无法让 `import mypackage` 在任何目录生效）。想要可编辑安装必须回到 `setup.py` 或 `setup.cfg`，两套入口让新人困惑。

简单说，`requirements.txt` 只是一个"购物清单"，告诉你要买什么；但缺了一份"产品说明书"，告诉别人这个项目是谁、如何构建、如何安装。

### `pyproject.toml`：单一事实源

为了解决上述碎片化问题，Python 社区通过 PEP[^1] 517、518、621 等系列提案，最终确立了 `pyproject.toml` 作为现代 Python 项目的**唯一配置入口**。用一份 TOML 文件承载三件事：

- **PEP 518 — 用什么工具构建**：`[build-system]` 声明构建时依赖与后端。
- **PEP 517 — 如何构建**：`build-backend` 指定后端（如 `hatchling.build`）负责打包成 wheel / sdist。
- **PEP 621 — 项目是谁**：`[project]` 以声明式描述项目元数据，替代散落在各处的配置文件。

`pyproject.toml` 的出现，意味着从"一堆文件凑在一起描述项目"进化到"一个文件定义一切"。开发者不再需要在 `setup.py`、`setup.cfg`、`requirements.txt`、`MANIFEST.in` 之间来回跳转。

以通用项目为例：

```toml
[project]
name = "mypackage"
version = "0.1.0"
description = "My awesome package"
readme = "README.md"
requires-python = ">=3.8"
dependencies = [
    "numpy>=1.24.0",
    "requests>=2.31.0",
]

[project.scripts]
mypackage = "mypackage.main:main"

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[tool.uv]
dev-dependencies = [
    "pytest>=7.0.0",
    "black>=23.0.0",
    "ruff>=0.1.0",
]
```

逐段看每个字段在构建链路中的作用：

- `[build-system]`：声明用什么构建后端。`requires` 列出构建时依赖，`build-backend` 指定后端入口，`pip` 与 `build` 会据此调用相应后端完成打包，无需再维护 `setup.py`。
- `[project]`：描述项目本身。`name` 是包名与 `pip` 安装名，`version` 是发布版本，`requires-python` 限定解释器范围，`dependencies` 列出运行时依赖。它们共同构成 PEP 621 定义的单一事实源。
- `[project.scripts]`：定义命令行入口。例如 `mycli = "mypackage.cli:main"` 会在安装后生成可执行命令 `mycli`，替代手写 `if __name__ == "__main__"` 脚本。
- `[project.optional-dependencies]`：分组可选依赖。如 `dev = ["pytest>=8.0", "ruff>=0.9"]` 供 `pip install -e ".[dev]"` 按需安装。
- `[tool.setuptools]`：告知构建后端去哪里找包。`packages = ["mypackage"]` 配合 `src` 布局，明确包代码在 `src/mypackage` 下，避免把测试或示例误打包。

**一个文件即是项目的单一事实源**——不仅依赖与元数据在此声明，质量工具如 Ruff、Mypy、Black 的配置也可收敛于 `[tool.ruff]`、`[tool.mypy]` 等段，进一步减少配置文件散落。

写好这份文件后，`pip install -e .` 就能把项目装成可 `import` 的包，并可定义命令入口。`-e` 表示可编辑安装，源码改动无需重装即可生效，配合 `src` 布局可立即暴露导入或打包配置错误。
