# 1.5 Git 工作流——用分支与 PR 协作

> 学完本节，你能回答：为什么团队要用 Git 而不是复制文件夹？怎样写出可读的提交？怎样用分支并行开发并通过 PR 合入主线？日常提交前要检查什么？

Git 解决的核心问题不是“备份”，而是“协作”。多人同时改同一份代码，怎样知道谁改了什么、能否安全合并、出问题能否回退，这些都靠工作流来回答。本节不讲底层对象设计，只讲你每天会用到的五个动作：看状态、做提交、开分支、推远端、过 PR。

## 为什么用 Git

没有版本控制时，常见的办法是复制目录加日期后缀。`my_project_final`、`my_project_real_final` 越来越多，改出 bug 想回退，却不知道哪个目录才是对的。协作时两人各改一份，手动合并更容易丢代码。

Git 把这些问题收成三件事。第一，每次提交都是一个带说明的快照，想回看直接切历史。第二，每个人在本地都有完整历史，离线也能提交与对比。第三，分支让并行开发互不干扰，合并时再把变更合在一起。

日常你最常用的是这条循环：改文件、看状态、进暂存、写提交、看历史。先把这条循环跑顺，再学分支也不迟。

```bash
# 最小循环
git status
git add <file>
git commit -m "feat: add audio resample helper"
git log --oneline -5
```

要点：提交前先 `git status` 确认改了什么，比直接 `git add .` 更可控。

## 最小提交：让历史可读

提交是给人看的。好的提交只做一件事，信息包含“改了什么、为什么改”。太大的提交让 Review 难读，回退也难挑。太小的提交如果没有完整上下文，同样让历史变碎。平衡点是“一个提交完成一个可描述的意图”。

实用规范很简单。暂存时只加本次意图相关的文件，不要把无关改动顺手带进去。提交信息用短句说明意图，前缀如 `feat`、`fix`、`docs`、`refactor` 能让 `git log` 一眼分类。正文需要时补充背景与影响面。

```bash
# 只提交本次意图相关文件
git status
git add src/mypackage/audio.py tests/test_audio.py
git commit -m "feat(audio): support 16k resample"
git log --oneline -5
# 按需撤销暂存或修改最后一次提交
git restore --staged <file>
git commit --amend -m "feat(audio): support 16k resample with fallback"
```

小技巧：写提交前用 `git diff --staged` 再看一遍将要提交的内容，等于给自己做一次轻量 Review。

## 分支与合并：并行不踩脚

分支让“正在做的事”与“稳定的主线”分开。常见做法是在 `main` 上保持可运行状态，新功能或修复都从 `main` 开分支，完成后合回。分支很轻量，创建与切换不复制文件，只是移动指针与工作区。

最常用的两条命令是 `git switch -c <branch>` 创建并切到新分支，以及 `git merge <branch>` 把分支合回。冲突不可怕，Git 会标出冲突区间，人工决定保留哪部分，再 `add` 后提交即可。

```bash
# 从 main 开新分支，做完再合回
git switch main
git pull
git switch -c feat/transcribe-cli
# ... 修改、提交 ...
git switch main
git merge feat/transcribe-cli
git branch -d feat/transcribe-cli

# 若有冲突，编辑冲突文件后
git add <resolved-file>
git commit
# 或中止合并
git merge --abort
```

记住两个习惯。分支名用 `feat/`、`fix/`、`docs/` 前缀让人一眼看懂意图。合并前先 `git fetch` 再 `git log --oneline main..feat/xxx` 预览要合入的提交，比直接合更安心。常用组合是 `git switch -c feat/demo` 开分支与 `git merge feat/demo` 合分支，日常每天都会用到。

## 远端与 PR：把协作放到线上

本地分支需要通过远端与他人协作。远端是 `origin` 指向的线上仓库，`push` 把本地提交推上去，`pull` 或 `fetch` + `merge` 把线上更新拿下来。PR（Pull Request）是在线上发起的“请求合入”，提供讨论、Review 与 CI 校验的入口。

推荐用 GitHub Flow 这类轻量流程。`main` 始终可发布，所有开发在短命分支上完成，推远端后开 PR，至少一人 Review 并通过 CI 后再合入。这样既保留主线稳定，又避免长期分支的合并痛苦。

```bash
# 第一次推分支并关联远端
git push -u origin feat/transcribe-cli

# 日常同步与清理
git fetch --prune
git pull --ff-only
git push

# 已合入的分支在本地清理
git branch -d feat/transcribe-cli
git push origin --delete feat/transcribe-cli
```

PR 不是形式。标题写清意图，描述写清变更点与风险，关联 issue，Review 时只围绕“是否达到意图”讨论。CI 过了、讨论收敛了，再点合并。

## 日常 checklist：提交前五分钟

把下面这份清单贴在手边，提交与推远端前逐项过一遍，能避免大多数“后悔提交”。

1. `git status` 看清改了哪些文件，是否有遗漏或误改。
2. `git diff` 与 `git diff --staged` 各看一遍，确认变更符合本次意图。
3. 检查 `.gitignore` 是否已忽略 `__pycache__/`、`*.pyc`、`.venv/`、`data/` 等不应入库的产物。
4. 在本地跑最快的一轮校验，如 `ruff check .` 或 `pytest -q`。
5. 写提交信息时回答“改了什么、为什么”，需要时在正文补充上下文。
6. 推远端前先 `git pull --ff-only` 或 `git fetch`，避免在线上产生不必要的合并。

`.gitignore` 示例：

```bash
# Python / env / data
__pycache__/
*.pyc
.venv/
data/
_build/
```
