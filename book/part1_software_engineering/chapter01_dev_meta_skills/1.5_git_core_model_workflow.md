# Git 核心模型与工作流

> Git 不是“带历史的文件夹”，而是一个**内容寻址的文件系统**加上**有向无环图**。看懂对象模型，分支与合并就不再神秘。

## 对象模型：blob / tree / commit

Git 在 `.git/objects` 中存储四类对象，全部以 `SHA-1(头部 + 内容)` 寻址：

- **blob**：文件内容。`blob <size>\0<content>` 的哈希即是文件指纹，改一个字节哈希就变。
- **tree**：目录快照。记录“文件名 → blob 哈希 / 子 tree 哈希”的映射，递归描述整棵目录树。
- **commit**：一次提交。包含 `tree` 哈希、`parent` 哈希、作者、时间与提交信息，是 DAG 的节点。
- **tag**（可选）：对 commit 的命名指针。

```
commit c2 (parent: c1) ──> tree t2 ──> blob "hello v2"
   ^                        ├── blob "README.md"
   |                        └── tree "src" ──> blob "app.py"
commit c1 ──> tree t1 ──> blob "hello v1"
```

分支（branch）只是**指向某个 commit 的可移动指针**，`HEAD` 则指向当前分支。`merge` 是在 DAG 上找到最近公共祖先后做三方合并，`rebase` 是把一段提交在新基底上重放——二者都是图操作，而非文件复制。

```bash
# 查看对象（Git 命令）
git cat-file -p HEAD          # 查看 HEAD commit 内容
git cat-file -p HEAD^{tree}   # 查看 HEAD 对应的 tree
git ls-tree HEAD              # 列出 tree 中的条目
git hash-object -w --stdin <<< "hello"  # 计算 blob 哈希
```

## Git Flow vs GitHub Flow

| 维度 | Git Flow | GitHub Flow |
|---|---|---|
| 分支模型 | `main` / `develop` / `feature/*` / `release/*` / `hotfix/*` | `main` + 短命 `feature/*` 分支 |
| 发布节奏 | 固定版本、需 `release` 分支预发布 | 持续部署、`main` 随时可发布 |
| 适用团队 | 大型、需并行维护多版本的团队 | 中小型、追求快速迭代的团队 |
| 成本 | 分支多、合并复杂、需严格规范 | 简单，但依赖 CI 与 feature flag |

> **中立性说明**：二者无优劣，只有 trade-off。通用建议是：以 GitHub Flow 为默认（`main` + 短命 `feature/*`、PR 驱动、CI 校验后合并），若需并行维护已发布版本再引入 `release` 分支。

```bash
# GitHub Flow 日常
git checkout -b feat/transcribe-cli
git add -A && git commit -m "feat: add transcribe subcommand"
git push -u origin feat/transcribe-cli
# 发起 PR，CI 通过后合并到 main

# Git Flow 发布（仅在需要时）
git checkout -b release/0.2.0 develop
# ... 修复发布问题 ...
git checkout main && git merge release/0.2.0
git checkout develop && git merge release/0.2.0
```

## `rebase` 与 `merge` 的取舍

- `merge` 保留完整历史，适合**公共分支**与**需要审计**的场景。
- `rebase` 线性化历史，适合**个人分支整理**后再合入主线；已推送的公共提交避免 `rebase`。

> **协作底线**：已推送到远端的提交不要 `rebase`，除非团队明确约定且使用 `git push --force-with-lease`。

## 可运行示例：用纯 Python 模仿 Git 对象

文件 `book/part1_software_engineering/chapter01_dev_meta_skills/demo_git_objects.py`（`hash-object` 与 commit 构造）：

```{code-cell} ipython3
import hashlib, pathlib

def git_blob_hash(content: bytes) -> str:
    """复刻 git hash-object 的计算：SHA-1('blob <len>\\0' + content)"""
    header = f"blob {len(content)}\0".encode()
    return hashlib.sha1(header + content).hexdigest()

def git_tree_entry(mode: str, name: str, sha_hex: str) -> bytes:
    """构造 tree 条目（简化版）：mode + space + name + \\0 + sha 二进制"""
    return f"{mode} {name}\0".encode() + bytes.fromhex(sha_hex)

# 1) 计算两个 blob 的哈希
h1 = git_blob_hash(b"hello world\n")
h2 = git_blob_hash(b"hello world!\n")
print("blob hello:", h1)
print("blob hello!:", h2)
assert h1 != h2  # 内容不同，哈希必不同
assert len(h1) == 40

# 2) 构造一个简化 tree（包含一个文件）
tree_content = git_tree_entry("100644", "greeting.txt", h1)
tree_header = f"tree {len(tree_content)}\0".encode()
tree_hash = hashlib.sha1(tree_header + tree_content).hexdigest()
print("tree hash:", tree_hash)
assert len(tree_hash) == 40

# 3) 构造一个简化 commit（指向 tree，无 parent）
commit_body = f"tree {tree_hash}\nauthor Demo <demo@example.com> 0 +0000\ncommitter Demo <demo@example.com> 0 +0000\n\ninit\n"
commit_hash = hashlib.sha1(f"commit {len(commit_body)}\0{commit_body}".encode()).hexdigest()
print("commit hash:", commit_hash)
assert len(commit_hash) == 40
# 预期输出示例（哈希值固定，tree/commit 随实现细节变化）:
# blob hello: 3b18e512dba79e4c8300dd08aeb37f8e728b8dad
# blob hello!: a0423896973644771497bdc03eb99d5281615b51
# tree hash: <40位 hex>
# commit hash: <40位 hex>
```

文件 `book/part1_software_engineering/chapter01_dev_meta_skills/demo_git_flow.py`（分支指针与 DAG 的 Python 模型）：

```{code-cell} ipython3
from dataclasses import dataclass, field

@dataclass
class Commit:
    oid: str
    parents: list[str] = field(default_factory=list)
    message: str = ""

# 用字典模拟对象库 + 分支指针
commits = {}
branches = {"main": None}

def commit(oid: str, parents: list[str], message: str):
    commits[oid] = Commit(oid, parents, message)
    return oid

def update_branch(branch: str, oid: str):
    branches[branch] = oid
    print(f"{branch} -> {oid} ({commits[oid].message})")

# 模拟 GitHub Flow：main 上有 c1，feature 分支从 c1 分叉出 c2、c3
c1 = commit("c1", [], "init")
update_branch("main", c1)

branches["feat/cli"] = c1
c2 = commit("c2", ["c1"], "feat: add cli skeleton")
update_branch("feat/cli", c2)
c3 = commit("c3", ["c2"], "feat: add transcribe subcommand")
update_branch("feat/cli", c3)

# 模拟合并：main 快进或创建合并提交
c4 = commit("c4", ["c1", "c3"], "Merge feat/cli into main")
update_branch("main", c4)
print("DAG:", {k: v.parents for k, v in commits.items()})
assert branches["main"] == "c4"
assert "c3" in commits["c4"].parents

# 演示 rebase 思想：把 feat/cli 的提交在新基底上重放（此处简化为改 parent）
# 真实 rebase 会重写 oid，这里仅示意“重放”语义
print("rebase 前 feat parent:", commits["c2"].parents)
# 预期输出:
# main -> c1 (init)
# feat/cli -> c2 (feat: add cli skeleton)
# feat/cli -> c3 (feat: add transcribe subcommand)
# main -> c4 (Merge feat/cli into main)
# DAG: {'c1': [], 'c2': ['c1'], 'c3': ['c2'], 'c4': ['c1', 'c3']}
# rebase 前 feat parent: ['c1']
```

文件 `book/part1_software_engineering/chapter01_dev_meta_skills/demo_m2t_git_store.py`（把 Git 思想映射到通用任务存储；此处以教学包 `m2t` 为例）：

```{code-cell} ipython3
import tempfile, pathlib, hashlib, json
from m2t.store import TaskStore

# 类比：TaskStore 的每条记录也可用内容哈希做“不可变快照”
def task_hash(task_dict: dict) -> str:
    payload = json.dumps(task_dict, sort_keys=True, ensure_ascii=False).encode()
    return hashlib.sha1(payload).hexdigest()[:12]

with tempfile.TemporaryDirectory() as td:
    db = pathlib.Path(td) / "git_like.db"
    store = TaskStore(db)
    store.create("t1", "meeting.wav", full_text="hello")
    row = store.get("t1")
    h1 = task_hash(row)
    print("snapshot t1 hash:", h1)
    store.update("t1", full_text="hello world")
    row2 = store.get("t1")
    h2 = task_hash(row2)
    print("snapshot t1' hash:", h2)
    assert h1 != h2  # 内容变化，哈希变化——与 Git blob 思想一致
    print("Git-like 不可变快照思想在任务存储中同样适用")
# 预期输出:
# snapshot t1 hash: <12位 hex>
# snapshot t1' hash: <12位 hex>
# Git-like 不可变快照思想在任务存储中同样适用
```
