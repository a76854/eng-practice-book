# FastAPI 异步陷阱

> 学完本节，你能回答：FastAPI 的 `async def` 与 `def` 路由有何本质差异？为什么在 `async def` 中调用同步阻塞代码会拖垮整个事件循环？如何用 `run_in_executor` / `anyio.to_thread` 或改回同步路由来修复？

## 为什么这是陷阱：单线程事件循环的“单行道”

把 `asyncio` 事件循环比作**单车道的收费站**：所有 `async` 请求都在这条车道上排队，`await` 是“前方车辆让行”的信号——让出的瞬间，后面的车才能通过。若某辆车（某个请求）在车道中央**停车卸货**（执行 `time.sleep`、同步文件读写、大规模计算），整条车道的车都会被堵住，后续请求的延迟会线性增长。

FastAPI 的关键设计是：

- `async def` 路由运行在**事件循环线程**中，由 `anyio` 调度，适合 `await` 非阻塞 I/O。
- `def` 路由运行在**线程池**（`run_in_threadpool`）中，框架自动把同步阻塞代码放到独立线程执行，不会卡住事件循环。

> **一句话规则**：路由内若有**阻塞调用**（`time.sleep`、同步 `open().read()`、`requests.get`、纯 Python 大循环），要么用 `def` 让框架丢进线程池，要么在 `async def` 中显式 `await run_in_executor` / `await anyio.to_thread.run_sync` 把阻塞移出事件循环。最差的选择是“在 `async def` 中直接调用阻塞代码”。

## 常见阻塞源清单

| 阻塞源 | 症状 | 修复 |
| --- | --- | --- |
| `time.sleep` / `requests` 同步请求 | 事件循环被卡，并发退化为串行 | 改 `await asyncio.sleep` / `httpx.AsyncClient`，或 `run_in_executor` |
| 同步文件 I/O（`open` 大文件） | 读盘期间循环无响应 | 用 `def` 路由，或 `await anyio.to_thread.run_sync` |
| 纯 CPU 循环（大正则、大 JSON） | 单请求占满循环，其他请求排队 | 下沉到进程池或单独线程池，或拆分为可 `await` 的分片 |
| 数据库同步驱动（`sqlite3` 阻塞） | 同理 | 用异步驱动（`asyncpg` / `aiosqlite`）或线程池 |

> **与 `m2t` 的呼应**：`m2t/audio.py` 的 `load_audio` 若在 `async def` 中直接同步读盘，且音频较大，会短暂阻塞循环；正确做法是用 `def` 路由或线程池包装。`m2t/asr.py` 的网络调用若用同步客户端，也需同样处理。

> **跨平台提示**：本节示例用标准库 `asyncio` + `time` 模拟阻塞与线程池修复，Windows / macOS / Linux 行为一致；FastAPI 本身的 `def` vs `async def` 调度差异在三平台一致，差异仅在路径分隔符与虚拟环境激活命令。

## 可运行示例一：阻塞调用如何拖垮事件循环（`asyncio` 模拟）

文件 `book/part2_后端开发全景与核心基石/chapter06_并发模型与性能工程/demo_fastapi_blocking.py`（用 `asyncio` 模拟 4 个并发请求，分别走“阻塞”与“非阻塞”路径，耗时对比）：

```{code-cell} ipython3
# 文件 book/part2_后端开发全景与核心基石/chapter06_并发模型与性能工程/demo_fastapi_blocking.py
import asyncio
import time
import concurrent.futures

# 模拟阻塞的同步函数（代表 time.sleep / 同步文件 I/O / 计算）
def blocking_io(task_id: int, delay: float = 0.05) -> str:
    time.sleep(delay)
    return f"done-{task_id}"

async def non_blocking_io(task_id: int, delay: float = 0.05) -> str:
    await asyncio.sleep(delay)
    return f"done-{task_id}"

async def bad_handler(task_id: int) -> str:
    """反例：在 async 上下文中直接调用阻塞函数（拖垮循环）。"""
    # 这里的 time.sleep 会卡住整个事件循环，其他并发任务无法推进
    return blocking_io(task_id)

async def good_handler_via_executor(task_id: int) -> str:
    """正例：把阻塞调用丢进线程池，不卡事件循环。"""
    loop = asyncio.get_running_loop()
    return await loop.run_in_executor(None, blocking_io, task_id)

async def good_handler_async(task_id: int) -> str:
    """正例：本身就是异步 I/O，直接 await。"""
    return await non_blocking_io(task_id)

async def _bench(handler, label: str, n: int = 4):
    t0 = time.perf_counter()
    results = await asyncio.gather(*(handler(i) for i in range(n)))
    elapsed = time.perf_counter() - t0
    print(f"{label} results:", sorted(results), f"elapsed {elapsed:.3f}s")
    assert sorted(results) == [f"done-{i}" for i in range(n)]
    return elapsed

# 1) 阻塞版本：4 个 50ms 阻塞任务在 async 中串行化，约 200ms
t_bad = await _bench(bad_handler, "bad (blocking in async)")
assert 0.15 < t_bad < 0.40

# 2) 线程池修复：同等任务通过 run_in_executor 重叠，约 50ms
t_good_ex = await _bench(good_handler_via_executor, "good (run_in_executor)")
assert t_good_ex < t_bad

# 3) 原生异步：本身非阻塞，直接并发，约 50ms
t_good_async = await _bench(good_handler_async, "good (native async)")
assert t_good_async < t_bad

print(f"陷阱对照：阻塞 {t_bad:.3f}s > 线程池 {t_good_ex:.3f}s | 原生异步 {t_good_async:.3f}s")
print("结论：在 async 上下文中直接调用同步阻塞会让并发退化为串行，需用线程池或原生异步修复")
# 预期输出:
# bad (blocking in async) results: ['done-0', ...] elapsed 0.20x s
# good (run_in_executor) results: ['done-0', ...] elapsed 0.05x s
# good (native async) results: ['done-0', ...] elapsed 0.05x s
# 陷阱对照：阻塞 ... > 线程池 ... | 原生异步 ...
```

```bash
# 本地验证线程池与事件循环（macOS / Linux）
.venv/bin/python -c "import asyncio, concurrent.futures; print('executor ok')"
# Windows 需用
.venv\Scripts\python.exe -c "import asyncio, concurrent.futures; print('executor ok')"
```

## 可运行示例二：FastAPI 语义的本地复刻（不用启动服务）

文件 `book/part2_后端开发全景与核心基石/chapter06_并发模型与性能工程/demo_fastapi_semantics.py`（不依赖 FastAPI 网络，仅用 `asyncio` 复刻“`async def` 在事件循环、`def` 在线程池”的调度语义，展示为何后者不阻塞）：

```{code-cell} ipython3
# 文件 book/part2_后端开发全景与核心基石/chapter06_并发模型与性能工程/demo_fastapi_semantics.py
import asyncio
import time

def sync_heavy(task_id: int) -> str:
    """模拟同步路由中的阻塞工作（会被框架放到线程池）。"""
    time.sleep(0.04)
    return f"sync-{task_id}"

async def async_heavy_blocking(task_id: int) -> str:
    """模拟 async 路由中的阻塞反例（直接阻塞事件循环）。"""
    time.sleep(0.04)
    return f"async-blocking-{task_id}"

async def async_heavy_fixed(task_id: int) -> str:
    """模拟 async 路由中的修复：把阻塞丢进线程池。"""
    loop = asyncio.get_running_loop()
    return await loop.run_in_executor(None, sync_heavy, task_id)

async def simulate_fastapi_dispatch():
    # 场景 A：4 个 async-blocking 请求并发（都会卡循环，近似串行）
    t0 = time.perf_counter()
    r1 = await asyncio.gather(*(async_heavy_blocking(i) for i in range(4)))
    t_blocking = time.perf_counter() - t0
    print("async-blocking:", sorted(r1), f"{t_blocking:.3f}s")

    # 场景 B：4 个 via-executor 请求并发（线程池重叠，约 40ms）
    t0 = time.perf_counter()
    r2 = await asyncio.gather(*(async_heavy_fixed(i) for i in range(4)))
    t_fixed = time.perf_counter() - t0
    # run_in_executor 返回的是 sync_heavy 的结果，前缀为 sync-
    print("async-fixed (executor):", sorted(r2), f"{t_fixed:.3f}s")

    # 场景 C：模拟 def 路由的线程池调度（与 B 同模型，展示语义一致）
    t0 = time.perf_counter()
    loop = asyncio.get_running_loop()
    with concurrent.futures.ThreadPoolExecutor(max_workers=4) as pool:
        # 模拟框架对 def 路由的调度：每个请求在独立线程中执行 sync_heavy
        futs = [loop.run_in_executor(pool, sync_heavy, i) for i in range(4)]
        r3 = await asyncio.gather(*futs)
    t_sync_pool = time.perf_counter() - t0
    print("def-style (threadpool):", sorted(r3), f"{t_sync_pool:.3f}s")

    assert sorted(r1) == [f"async-blocking-{i}" for i in range(4)]
    assert sorted(r2) == [f"sync-{i}" for i in range(4)]
    assert sorted(r3) == [f"sync-{i}" for i in range(4)]
    # 修复后应快于阻塞版本
    assert t_fixed < t_blocking
    assert t_sync_pool < t_blocking
    print(f"调度语义验证：阻塞 {t_blocking:.3f}s > 修复 {t_fixed:.3f}s | def池 {t_sync_pool:.3f}s")

import concurrent.futures
await simulate_fastapi_dispatch()
print("FastAPI 语义复刻通过：async 中阻塞会拖垮循环，线程池可隔离")
# 预期输出:
# async-blocking: ['async-blocking-0', ...] 0.16x s
# async-fixed (executor): ['sync-0', ...] 0.04x s
# def-style (threadpool): ['sync-0', ...] 0.04x s
# 调度语义验证：阻塞 ... > 修复 ... | def池 ...
```

```bash
# 本地验证（macOS / Linux）
.venv/bin/python -c "import asyncio; print('fastapi semantics ok')"
# Windows 需用
.venv\Scripts\python.exe -c "import asyncio; print('fastapi semantics ok')"
```

> **选型 checklist**：写 FastAPI 路由前先问三句——① 本路由会做 I/O 吗？② 该 I/O 有异步客户端吗？③ 若没有，我愿意把它丢进线程池吗？回答“是-否-是”则用 `def` 或 `run_in_executor`；回答“是-是-否”则用 `async def` + `await`。与 [6.1](6.1_并发并行异步.md) 的 I/O/CPU 分型与 [6.3](6.3_异步编程核心.md) 的让出语义相互印证。
