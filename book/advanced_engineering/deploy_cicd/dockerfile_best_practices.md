# Dockerfile 最佳实践

上一节把“可复现”交给了镜像，这一节回答镜像怎么写。Dockerfile 看起来只是一串命令，写得对与写得差在功能上几乎没有区别，差别全落在构建速度与镜像体积上：顺序对了，改一行业务代码只需重建最后一层，几秒钟出镜像；顺序错了，每次都要重装依赖，几分钟起步。本节先讲清分层与缓存的机制，给出两条能直接照做的规则，再交代多阶段构建与最小可用的收尾细节。

## Dockerfile 的本质

每一行 Dockerfile 指令都会在上一层的基础上产生一个新的只读层（layer），最终镜像是这些层的叠加。运行时在此之上挂载一个可写层，容器内的修改只落在可写层，不污染镜像层。

- `FROM`：起始层，通常选 `python:3.12-slim` 这类裁剪过的基座，比 `python:3.12` 小数百 MB，且已包含最小的 `apt` 源。
- `RUN`：执行命令并固化结果为一层，如 `apt-get install` 或 `uv sync`。
- `COPY`：把构建上下文中的文件拷入镜像，形成新层。
- `ENV` / `WORKDIR` / `EXPOSE` / `CMD`：元数据或运行时默认，不产生重量级层但影响可观测与启动。

> **类比叠加**：镜像像“千层蛋糕”，每一层都是上一层的增量；缓存命中时直接复用已烤好的层，失效时该层及之后所有层重烤。

## 层缓存

Docker 构建时会为每条指令计算缓存键：指令文本 + 被 `COPY` 的文件内容的哈希 + 前一层的哈希。若三者均未变，则直接命中缓存，跳过执行；若任一变化，则该层及之后所有层失效重建。

由此导出两条黄金规则：

1. **把最不常变的放最前**：依赖清单与锁文件（`pyproject.toml`、`uv.lock`）数周才变一次，应先 `COPY` 这两份文件并安装依赖，让该层长期命中缓存；业务代码（`src/`）每天都变，应后 `COPY`，避免频繁使依赖层失效。
2. **合并可合并的 `RUN` 并清理缓存**：如 `apt-get update && apt-get install -y ... && rm -rf /var/lib/apt/lists/*` 写在同一 `RUN`，既减少层数，又避免 `apt` 缓存留在镜像中。

反例：若先 `COPY . .` 再安装依赖，则任何业务文件的改动都会让依赖层一起失效，CI 每次都要重装依赖，构建时间从秒级退化为分钟级。

| 构建顺序 | 首次构建 | 只改业务代码后的重建 | 代价 |
| --- | --- | --- | --- |
| 先拷清单与锁文件，装依赖，再拷代码 | 装依赖 + 拷代码 | 只有代码层失效 | 秒级 |
| 先 `COPY . .`，再装依赖 | 装依赖 + 拷代码 | 依赖层一起失效，依赖重装 | 分钟级 |

两条规则指向同一件事：让缓存键里的“易变部分”尽量靠后，缓存才能长期命中。

## 多阶段构建

多阶段构建用多个 `FROM` 段落：前一阶段用重型基座完成编译、安装或前端打包，后一阶段仅 `COPY --from=builder` 产物到轻量运行时。优势是运行时镜像不含编译器、源码与中间缓存，体积与攻击面同步下降。

文档查询后端的典型二阶段：

- `builder` 阶段用 `python:3.12`，装好依赖并执行前端打包（若含前端）；
- `runtime` 阶段用 `python:3.12-slim`，仅拷入已安装的 `site-packages`、`src/` 与前端静态产物。

下面的单阶段示例只拷入需要的 `pyproject.toml`、`uv.lock` 与 `src/`，避免把无关文件带入镜像。这是选择性 `COPY`，并非多阶段构建。实验六要求自行编写 Dockerfile；如果前端也需要构建镜像，可增加独立的前端构建阶段，再将构建产物复制到 Nginx 运行镜像。

## 最小可用原则与安全细节

- **选择性 `COPY`**：只拷 `pyproject.toml`、`uv.lock` 与 `src/`，不 `COPY . .`，既加速上下文传输，也避免把 `.git`、`.venv`、数据文件误入镜像。
- **不保留缓存**：引导 `uv` 的那一步用 `pip install --no-cache-dir uv`；`uv` 自己的下载缓存在镜像外（`~/.cache/uv`），需要时用 `UV_NO_CACHE=1` 关闭，教学示例从简未加。
- **非 root 运行（生产建议）**：教学样例为简洁未切用户，生产应在 `RUN useradd -m app && USER app` 后再 `CMD`，降低容器逃逸后的权限。
- **`EXPOSE` 仅声明**：`EXPOSE 8000` 不自动发布端口，发布由 `docker run -p` 或 Compose 的 `ports` 决定，声明的价值在于文档化与 `docker inspect` 可见。

> **环境约定**：本书面向 Linux，镜像内路径统一为 Linux 风格 `/app`、`/data`，构建上下文的路径分隔符由 Docker 客户端处理，正文中的 `COPY src/ ./src/` 在 Linux 环境均一致。

## 一份缓存友好的 Dockerfile

把两层分开写出来，就是这个样子：

```dockerfile
FROM python:3.12-slim
WORKDIR /app

# 依赖层：清单与锁文件数周才变，安装结果可长期命中缓存
COPY pyproject.toml uv.lock ./
RUN pip install --no-cache-dir uv && uv sync --frozen --no-dev --no-install-project

# 代码层：业务代码每天在变，只让这一层失效
COPY src/ ./src/

ENV PATH="/app/.venv/bin:$PATH"
ENV PYTHONDONTWRITEBYTECODE=1
ENV DOCSEARCH_DATA_DIR=/data
RUN mkdir -p /data

EXPOSE 8000
CMD ["uvicorn", "docsearch.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

从上往下读：`FROM` 定基座；第一组 `COPY` 把清单与锁文件拷进来，紧跟的 `RUN` 装依赖，这两条合起来就是依赖层；第二组 `COPY` 才把业务代码拷进来，它是代码层；`ENV` 把解释器路径、字节码开关与数据目录固定下来；`EXPOSE` 声明端口；`CMD` 交代启动命令。改业务代码时，失效的只有代码层，依赖层照旧命中缓存。

`uv sync` 的三个参数各管一件事：`--frozen` 完全按 `uv.lock` 安装，不在镜像里重新求解依赖，保证构建可复现；`--no-dev` 不装 `ruff`、`pytest` 这类只在开发时用的包；`--no-install-project` 表示此刻只装第三方依赖，不装项目自己，因为 `src/` 还没拷进来。

```bash
# 在实验六项目根目录，核对自己编写的 Dockerfile 中关键指令的顺序
grep -nE '^(FROM|COPY|RUN|CMD)' Dockerfile
# 已安装并启动 Docker 时，验证镜像能否构建
docker build -f Dockerfile -t docsearch-backend:local .
```

## COPY 顺序与构建速度

Docker 为每条指令算一个缓存键：指令文本、被 `COPY` 的文件内容哈希、前一层的哈希。三者都没变才命中缓存；任何一项变了，这一层以及它之后的所有层都要重来。顺序之所以关键，就在于“易变的文件”落在哪一层：放在后面，它只影响自己；放在前面，它会把后面的一起拖下水。

把两种顺序各构建两次，第二次只改业务代码，各层的下场是这样的：

| 层 | 好顺序（清单在前） | 差顺序（`COPY . .`） |
| --- | --- | --- |
| 依赖清单与锁文件 | 命中缓存 | 失效（代码与它混在同一层） |
| 安装依赖 | 命中缓存 | 重新安装 |
| 业务代码 | 重建 | 重建 |

好顺序只重建最后一层，几秒钟出镜像；差顺序每次都要重装依赖，在 CI 里就是从秒级退化到分钟级。这也解释了为什么“拷错顺序”会让流水线越跑越慢，而且慢下来的每一次都在烧时间。

## 本节小结

- 镜像由只读层叠加而成，每条指令一层；缓存键包含指令文本、被拷文件内容与上一层哈希，任一变化则其后所有层失效。
- 两条规则：不常变的清单与锁文件放最前，可合并的 `RUN` 合并并清理缓存。
- 依赖层与代码层分开写，业务改动只让最后一层失效；`COPY . .` 会把依赖层一起拖下水。
- `uv sync --frozen --no-dev --no-install-project` 分别对应可复现安装、不装开发依赖、暂不装项目自身。
- 多阶段构建把编译与打包留在 builder，运行时只留产物；按需 `COPY`、非 root 运行、`EXPOSE` 只声明不发布，是一份最小可用 Dockerfile 的收尾细节。
