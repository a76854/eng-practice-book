# 消息队列与 Kafka

学完本节，你能回答：

- 什么样的任务不能在 HTTP 请求里做，只能进队列
- 生产者、Broker、消费者这三件，各自负责什么
- 同一条消息被投递两次，业务怎么保证不出错
- 库写了、消息没发出去，这笔糊涂账怎么算清

> 饭点餐厅取号等位，点菜只拿号，叫号再吃，后厨按号做菜。HTTP 只取号，队列就是叫号系统，worker 是后厨。取号很快，吃上要等，但谁也不用堵在门口。

前两节解决了放哪和查得快，本节解决做得慢。本节是第三个帮手，管长时工作别堵住请求。学完本节，什么进队列、重复投递怎么办、消息丢了找谁，都有下落。定时任务在节末一句话，不单开。

## 进队列的任务

进队列的任务有三个特征，耗时久、可异步、可重试。文档上传后要解析建索引，几十秒跑完，用户不可能对着转圈等。解析结果晚一分钟出来没人投诉，但请求超时了人人都要骂。所以 HTTP 只做入队加返回任务 ID，解析在队列里慢慢做，前端轮询进度即可。

判断进不进队列，看用户等不等得起。等不起但结果可以晚到，进队列。等得起、几百毫秒能回，直接在请求里做。Celery 这类轻量队列适合团队起步，Kafka 适合量上来之后，本节讲 Kafka，思路通用。

## 生产与消费

队列的抽象只有三件。生产者是前台，只管取号入队。Broker 是叫号系统，存消息、分发。消费者是后厨，取活干活、汇报结果。

```python
# 生产者：HTTP 里只做入队，返回任务 ID（展示代码）
producer.send("doc-parse", key=doc_id, value={"doc_id": doc_id, "file_key": key})
return {"task_id": doc_id, "status": "pending"}
```

Kafka 的最小集是三个名词。topic 是队列的名字，一类任务一个 topic。partition 是 topic 下的分区，同 topic 的消息按 key 散到不同分区，并行消费就靠它。consumer group 是一组消费者，组内每条消息只被消费一次，加机器就加消费能力。消费者长这样：

```python
# 消费者：取活干活，结果写回库（展示代码）
for msg in consumer:
    result = parse_document(msg.value["file_key"])
    db.execute("UPDATE documents SET indexed = 1 WHERE id = ?", (msg.key,))
    consumer.commit()
```

## 重复投递

队列保证至少投递一次，不保证只投递一次。消费者崩在 commit 之前，重启后同一条消息会再来一遍。解法是幂等，同一条消息做两次和做一次，结果一样。

做法是去重表，消息 ID 落库判重：

```python
# 幂等：处理前先看这条消息做过没有（展示代码）
if db.exists("SELECT 1 FROM processed WHERE msg_id = ?", (msg_id,)):
    consumer.commit()
    continue
do_work(msg)
db.execute("INSERT INTO processed(msg_id) VALUES (?)", (msg_id,))
```

去重表与业务写要在一个事务里，否则"活干了、去重没记"还是会重做。key 的设计沿用上一章的思路，天然唯一的业务 ID 就是最好的消息 ID。

## 发件箱

反过来还有一笔糊涂账，业务库写成功了，发消息那一步崩了，消息就没了。解法是发件箱，业务数据和"要发的消息"写在同一个事务里，再由搬运工把消息搬进队列：

```{mermaid}
flowchart LR
    A["HTTP 请求"] --> B["同一事务写业务<br/>加写 outbox 表"]
    B --> C["返回成功"]
    D["搬运工轮询 outbox"] --> E["发进 Kafka"]
    E --> F["标记已发"]
```

业务与 outbox 同成功同失败，搬运工只管把没标记的消息发出去，发完标记。消息可能重复，但重复有幂等兜着。至此重复与丢失两笔账都算清了。

## 顺序与分区

队列默认不保序，同一文档的"解析完成"跑到"开始解析"前面，状态机就乱了。保序靠 key，同 key 的消息进同分区，分区内严格有序。代价是同 key 的活只能串行，并行度被分区数封顶。

| 问题 | 答案 |
| --- | --- |
| 消息保序 | 同 key 进同分区，分区内有序，分区间无序 |
| 加机器提速 | 消费者数不超过分区数，加多了闲着 |
| 消费者崩了 | 组内再均衡，分区转给活着的接着吃，重复用幂等兜 |

分区数一开始按峰值估，改大容易改小难。顺序只在需要的地方保，全局保序等于放弃并行，得不偿失。

## 起步与定时

量没上来之前，不必上 Kafka。数据库轮询 outbox、内存队列、Celery，都是够用的起点，迁移到 Kafka 时生产消费的姿势不变。定时任务也归这一节管，cron 风格用调度器，延迟执行用延迟队列，知道名字，用到时再查手册。

## 本节小结

- 用户等不起、结果可晚到的任务进队列，HTTP 只入队返回 ID，解析建索引这类活在 worker 里做。
- 生产者取号，Broker 叫号，消费者做菜，topic 分 partition 并行，consumer group 加机器加能力。
- 队列只保至少一次，重复用幂等键去重表兜住，去重与业务写要在同一事务。
- 库写了消息没发，用发件箱把业务与消息绑在同一事务，搬运工负责发出。
- 保序靠同 key 进同分区，消费者不超分区数，再均衡的重复用幂等兜。
