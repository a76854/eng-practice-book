# 对象存储

学完本节，你能回答：

- 文件为什么不进数据库，也不落应用服务器的磁盘
- bucket 与 key 这两级名字，各自管什么
- 私有文件怎么给前端看一眼，又不对外公开
- 大文件上传为什么不走后端中转，断点续传是什么思路

> 火车站的行李寄存处只做两件事，收行李给小票，凭小票取行李。柜子不问你是谁，只认票。对象存储也一样，文件存在它那里，应用只留一张小票，也就是 key，凭 key 存取，不问文件里是什么。

本章讲后端之外的四个帮手，存储、缓存、队列，再加一个新同事大模型。本节是第一个帮手，管文件放哪。学完本节，文档原文这类数据库存不下、服务器磁盘存不起的东西，都有地方去。后面三节再解决查得快、做得慢、答得聪明。

## 文件与数据库的分工

数据库的行是为结构化数据设计的，文件塞进去有三笔账算不过来。体积上，一篇 PDF 几 MB，上千篇就是几 GB，表膨胀之后备份越来越慢。查询上，再简单的 `SELECT` 也要扛着大字段走，索引帮不上忙。职责上，数据库要保事务与一致性，拿它当文件柜用，贵的东西干了便宜的活。

落应用服务器磁盘也不行，多机部署下每台机器各存各的，用户这次上传到 A 机，下次请求落到 B 机就找不到。换机器、扩容，文件跟着丢。三种放法对比如下：

| 放哪 | 体积大了会怎样 | 多机部署会怎样 | 前端加速怎么做 |
| --- | --- | --- | --- |
| 数据库 | 表膨胀，备份与查询一起慢 | 主从同步拖着大字段跑 | 做不了，只能走应用 |
| 应用服务器磁盘 | 单机磁盘迟早满 | A 机存的 B 机看不到 | 做不了，只能走应用 |
| 对象存储 | 按量计费，加机器是服务商的事 | 任何机器凭 key 都能取 | CDN 直接加速，不走应用 |

文档查询应用里，文档原文 PDF、用户上传的文件都走对象存储，SQLite 里只存 key。数据库保关系，对象存储保文件，各干各的。

## bucket 与 key

对象存储的命名只有两级。bucket 是顶层桶，一类文件开一个桶，比如 `doc-originals` 存原文，`doc-thumbs` 存预览图。key 是桶内路径，形如 `docs/{doc_id}/original.pdf`，既是地址也是名字。

上传时后端做两件事，把文件放进桶，把 key 写进库：

```python
# 后端：文件进桶，key 入库（展示代码，boto3 未在本书环境安装）
import boto3

s3 = boto3.client("s3", endpoint_url="http://localhost:9000")
key = f"docs/{doc_id}/original.pdf"
s3.upload_fileobj(file_obj, "doc-originals", key)
db.execute("UPDATE documents SET file_key = ? WHERE id = ?", (key, doc_id))
```

之后任何机器、任何时候，凭这个 key 都能把文件取回来。key 的设计是一门手艺，带上业务 ID 做前缀，既能按前缀批量删，又能在控制台一眼看出归属。

## 预签名 URL

桶不能公开，公开等于把所有文件送人。前端要看某篇文档，后端签一张限时票，也就是预签名 URL，票上写着哪个 key、几分钟内有效：

```python
# 后端：签一张 300 秒有效的票，前端拿票直接读文件
url = s3.generate_presigned_url(
    "get_object",
    Params={"Bucket": "doc-originals", "Key": key},
    ExpiresIn=300,
)
```

前端拿票直接读对象存储，不经过后端。后端只做鉴权，决定这张票给不给、给多久。票过期重签即可，文件本身一直在桶里没动过。

## 直传与断点续传

小文件走后端中转无所谓，大文件不行。经过后端意味着带宽花两遍，内存里还要过一手，并发一高后端先被拖垮。正确姿势是前端直传，后端只发凭证：

```{mermaid}
flowchart LR
    A["前端请求上传凭证"] --> B["后端鉴权<br/>签发直传票"]
    B --> C["前端拿票<br/>PUT 直达对象存储"]
    C --> D["前端回告后端<br/>key 已就绪"]
    D --> E["后端把 key 入库"]
```

直传之后还有断点续传，思路是切块编号。前端把大文件切成固定大小的块，每块独立上传，服务端按编号拼。断网了只重传没到的块，不用从头来。块大小与并发数是经验值，内网可大、弱网调小，这就是全部诀窍。

## 生命周期

文件有晚年。访问日志、缩略图、过期导出，放着占钱，删了可惜，办法是生命周期规则，按年龄自动搬家：

| 数据 | 规则 | 理由 |
| --- | --- | --- |
| 访问日志 | 30 天后删 | 只用于排查，过期无用 |
| 缩略图 | 90 天后转冷存储 | 偶尔看，便宜优先 |
| 文档原文 | 长期保留，开版本控制 | 误删可找回，版本是后悔药 |

版本控制防的是误覆盖，同 key 上传新文件，旧版本留着，删错了能找回。配额告警也要开，桶的账单按量走，半夜被刷量时，告警比复盘便宜。

## 本节小结

- 数据库保关系，对象存储保文件，大文件进表会拖慢备份与查询，多机下磁盘文件会找不到。
- bucket 按文件类别开，key 带业务 ID 做前缀，库里只存 key，凭 key 在任何机器取回。
- 桶不公开，前端看文件靠后端签限时票，票过期重签，文件不动。
- 大文件走前端直传，后端只发凭证，断点续传送靠切块编号，断了只重传没到的块。
- 文件有晚年，日志过期删，冷数据转冷存储，原文开版本防误删，账单配告警。
