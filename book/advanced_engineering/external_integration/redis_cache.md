# 缓存与 Redis

学完本节，你能回答：

- 数据库扛不住什么样的读，什么样的结果值得缓存
- 旁路缓存下，读与写的顺序为什么不能反
- 缓存穿透、击穿、雪崩各是什么局面，分别怎么解
- 会话、限流、分布式锁，为什么也落在 Redis 身上

> 常用的电话号码贴在冰箱上，翻电话本太慢。缓存就是冰箱贴，常用的抄一份放手边，过期撕掉重抄。冰箱贴再方便，也替代不了电话本，丢了还能重抄是缓存的前提。

上一节给文件找了去处，数据这一侧还有一个老问题：有些东西读得太频繁。文档查询应用里，同一个热门关键词一分钟被搜上百次，每来一次就要把同样的查询在数据库里重跑一遍，数据库再快也架不住这么读。解法是几百年传下来的老思路：把常用的结果抄一份，放在更快的地方，读的时候先看抄件。这层抄件就是缓存（cache）。

放抄件的地方要满足两个条件：足够快，丢了不心疼。于是内存数据库登场，数据放在内存里，读写都是毫秒级；支持给每份数据设一个过期时间，到点自动清掉。这门手艺里最常用的工具是 Redis，本节以它为例。先讲什么样的数据值得缓存，再讲读写怎么配合、三种经典故障怎么防、过期和内存怎么管，最后看它在缓存之外还常被借去做的几件事。

## 值得缓存的数据

先解决判断问题：不是所有数据都值得抄一份，抄错了只是多出一份要维护的副本。

数据库最怕的是高频重复读。重复意味着同样的结果被反复计算，高频意味着这个浪费被放大了很多倍。但要抄进缓存，还得看三条：

- 读远多于写。抄件才有机会被多次命中，否则还没被读几次就改掉了，命中率上不去。
- 丢了能重建。缓存可能被清空、可能宕机，能从数据库重新读出来，才敢把它当消耗品用。
- 允许短暂不一致。读者看到五分钟前的搜索结果没关系，看到五分钟前的账户余额就要出事。

三条全中，放手边。任何一条对不上，就老老实实走数据库。文档搜索的结果正好三条都中，是天然的缓存对象。

## 旁路缓存

确定了对象，接下来定规矩：缓存加进来之后，应用该先跟谁说话。

一种思路是让数据库自带缓存，应用无感知；另一种更常见的做法是应用自己管：读的时候先问缓存，命中就直接返回，没有就问数据库，顺手把结果抄一份回去；写的时候先改数据库，再把缓存里那份作废。数据库始终是唯一的真相，缓存只是随用随丢的副本。这种绕开数据库去读缓存的走法，叫旁路缓存（cache-aside）。

```python
# 读：先看缓存，没有再查库，查到回填并设过期（展示代码）
cached = redis.get(f"search:{q}")
if cached is None:
    results = db.search(q)
    redis.setex(f"search:{q}", 300, json.dumps(results))
    return results
return json.loads(cached)
```

写侧的顺序是这门手艺里最容易翻车的细节：一定先写库、后删缓存。反过来先删缓存再写库，中间的空窗里如果插进来一个读请求，它会把旧数据重新抄回缓存，脏数据就住下了。先写库再删缓存，最坏情况只是删缓存失败，交给重试补一次即可。

## 缓存三坑

读写顺序立对了，缓存也并非高枕无忧。上线之后，有三类故障几乎一定会来敲门，行业里给它们起了名字：

| 局面 | 长什么样 | 怎么解 |
| --- | --- | --- |
| 穿透 | 查不存在的东西，每次都打穿缓存直达 DB，恶意构造直接打垮 DB | 空结果也缓存一份，过期设短；或在入口校验参数合法性 |
| 击穿 | 某个热点 key 恰好过期，瞬间上百个请求同时回源，DB 被冲垮 | 热点 key 永不过期加后台刷新，或加互斥锁只放一个请求回源 |
| 雪崩 | 大批 key 同时过期，或 Redis 宕机，所有请求一起压向 DB | 过期时间加随机抖动；Redis 高可用部署；DB 侧保留限流兜底 |

三个名字指向同一件事：请求绕过缓存，一起压向数据库。解法也共享一条思路：别让"同时回源"发生。以穿透为例，文档搜索里，空关键词的结果也缓存一份短过期的空列表，反复刷不存在的词就刷不穿。

## 过期时间

三个坑里有两个和过期时间直接相关，值得把它单独拿出来说。过期时间给多久不能拍脑袋，看数据变化的速度：

| 数据 | 过期 | 理由 |
| --- | --- | --- |
| 搜索结果 | 5 分钟 | 别处新增文档，晚上架几分钟没人投诉 |
| 会话 | 30 分钟 | 人走茶凉，过期即登出 |
| 字典配置 | 1 天 | 几乎不变，变了等一天也能接受 |

还有一条纪律：同一批写入、同一时刻过期的数据，会约好在同一秒失效，雪崩就是这么来的。给过期时间加一点随机抖动，比如 300 秒上下浮动几十秒，回源就被打散了。拿不准时先设短：设短了只是多查几次数据库，设长了是脏数据住下。

## 内存与淘汰策略

过期决定数据什么时候主动退场，还有另一半问题：内存是有限的，数据还没到期就把内存用满了，怎么办。答案不是加内存，而是事先定好淘汰规则，满了之后按规则丢数据，而不是直接报错：

| 策略 | 含义 | 适用 |
| --- | --- | --- |
| noeviction | 满了直接报错 | 数据一条不能丢，且有人值班 |
| allkeys-lru | 全体里踢最久没用的 | 缓存场景默认选这个 |
| volatile-ttl | 有过期的里踢快到期的 | 冷热分明，且都设了过期 |

缓存场景默认选 allkeys-lru，实在挑不出该丢谁，就丢最久没用过的。要接受一个事实：被淘汰是缓存的常态，丢了回数据库重建即可。真正该担心的是不设上限，让 Redis 吃光机器内存，把同机的其他服务一起拖下水。

## 会话、限流与锁

到这里，缓存这一件事就讲完了。不过 Redis 的用途不止缓存：它读写快、支持过期、又能被多个服务共同访问，很多系统顺手把它当作一块共享的临时黑板。三件事最常见：登录态放 Redis，多台服务共享同一份会话，重启任意一台都不掉线；计数器做限流，某个 key 一分钟加了几次，超了直接拒绝；分布式锁，多台机器抢同一件活时，先到 Redis 里抢一把锁。每一件都值得单开一节，本书点到为止，用到时知道该找谁。

## 本节小结

- 高频重复读最伤数据库，读多写少、丢了能重建、允许短暂不一致的数据值得放手边。
- 读先看缓存再回填，写先改库再删缓存，顺序反了会住下脏数据。
- 穿透、击穿、雪崩本质都是请求一起压向数据库，解法共同点是别让同时回源发生。
- 过期时间按数据变化定，同一批加随机抖动；内存设上限，满了按策略淘汰，被淘汰是缓存的常态。
- 登录态、限流、分布式锁是 Redis 在缓存之外的常见用途，本章只给归属，用到时再深挖。
