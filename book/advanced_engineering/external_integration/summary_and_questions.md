## 本章小结

- **文件找寄存处**：数据库保关系，对象存储保文件，库里只存 key；桶不公开，看文件靠限时票，大文件走前端直传（见 [对象存储](object_storage.md)）。
- **热数据放手边**：读多写少、可重建、允许短暂不一致的结果值得缓存；读先看缓存，写先写库再删缓存；穿透击穿雪崩都是别让请求同时打到 DB（见 [缓存与 Redis](redis_cache.md)）。
- **慢活进队列**：HTTP 只入队返回 ID，解析建索引在 worker 里做；重复用幂等键兜，丢失用发件箱兜（见 [消息队列与 Kafka](kafka_queue.md)）。
- **大模型请得动也要管得住**：key 放服务端；流式降首字时延；结构化输出先解析再校验；函数调用让模型查它不知道的事；token 记账（见 [大模型调用方法](llm_calling.md)）。
- **总体启示**：外部集成不是把活推出去就行，而是给每一份推出去的活配好凭证、顺序、去重与账单；四种外部能力组合起来，系统才敢借力。

## 思考题

1. **请分析**：文档原文存数据库、落应用磁盘、放对象存储三种放法，分别在体积、多机部署、前端加速三件事上付出什么代价？为什么说"库里只存 key"是职责分清的标志？
2. **请判断**：搜索结果缓存 300 秒过期，恰好过期那一刻涌进 200 个相同请求。从穿透击穿雪崩里对号入座，说明这是哪个局面，并给出两种解法，比较它们的代价。
3. **请分析**：消费者崩在 commit 之前，同一条解析任务被执行两次。从幂等键与发件箱里各找一处发力点，说明第一次执行与第二次执行分别在哪里被拦住，去重表与业务写为什么要在同一事务。
4. **请设计**：给文档摘要功能设计调用方案，覆盖 key 放哪、流式还是全量、输出怎么校验、用量怎么记。并说明 key 泄露与 token 失控分别是谁的责任，怎么防。
5. **请判断**：团队量小，Kafka、Celery、数据库轮询 outbox 三选一。从运维成本与迁移成本出发，说明起步选哪个，量上来后换哪个，换的时候生产消费的姿势要不要变。
