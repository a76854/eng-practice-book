# 实验五 异步改造与接口压力测试

本实验对应理论 [第6章 并发模型与性能工程](../../part2_后端开发全景与核心基石/chapter06_并发模型与性能工程/index.md)。建议先通读第6章 6.3 至 6.5 节的异步核心、FastAPI 异步陷阱与性能剖析方法，再动手。你会在本实验中把同步的文件或数据库操作改造为异步形态，用并发脚本模拟接口压力，对比改造前后的吞吐与时延，并写出一份可复现的分析报告。

## 实验目标

- 能说清同步阻塞与异步非阻塞在连接型服务中的差异，并解释事件循环为何会被同步 DB 或文件操作卡住。
- 能把同步的查询或写入逻辑改造为异步形态，理解 `async` / `await`、`asyncio.gather` 与线程池托底的适用边界。
- 能用标准库并发脚本模拟压测，采集并发度、总耗时、平均时延与吞吐等指标，体会 `ab` / `locust` 类工具的核心度量思路。
- 能按“度量、定位、优化、回归”闭环组织对比实验，写出包含环境、方法、数据与结论的分析报告。
- 能识别异步改造中的常见陷阱，例如在 `async def` 中直接调用阻塞代码导致并发退化，并给出修复方案。

## 任务步骤

### 步骤 1 阅读理论与现状

1. 阅读 [第6章 6.1 并发、并行与异步](../../part2_后端开发全景与核心基石/chapter06_并发模型与性能工程/6.1_并发并行异步.md) 至 [6.4 FastAPI 异步陷阱](../../part2_后端开发全景与核心基石/chapter06_并发模型与性能工程/6.4_FastAPI异步陷阱.md)，重点关注协作式调度与“阻塞事件循环”的危害。
2. 阅读 [第6章 6.5 性能剖析方法论](../../part2_后端开发全景与核心基石/chapter06_并发模型与性能工程/6.5_性能剖析方法论.md) 中关于 `cProfile`、`timeit` 与压测度量的讨论，理解为何必须先度量再优化。
3. 回顾实验四的任务接口与存储层，明确本实验的改造对象是其中的同步查询或写入路径。

> 跨平台提示：`asyncio`、`time`、`cProfile` 均为标准库，Windows / macOS / Linux 行为一致。路径示例统一写 `/`，`pathlib.Path` 自动适配 `\`。虚拟环境激活为 `source .venv/bin/activate`（macOS / Linux）与 `.venv\Scripts\activate`（Windows）。

### 步骤 2 读懂起手骨架

1. 打开 `labs/lab05_异步改造与压测/starter/main.py`，运行 `python main.py` 与 `python main.py --help`，观察同步与异步两条路径的耗时对比输出。
2. 阅读 `starter/README.md` 与 `starter/bench.py` 中的注释，理解骨架如何用 `asyncio.sleep` 模拟 I/O 等待，用 `asyncio.gather` 重叠等待。
3. 尝试调整 `main.py` 中的 `--tasks` 与 `--delay` 参数，观察并发数与单任务时延对总耗时与吞吐的影响。

### 步骤 3 将同步操作改造为异步

1. 以骨架中的 `sync_fetch` 为起点，梳理同步路径的耗时构成：每次查询含一次固定时延，串行执行时总耗时线性叠加。
2. 实现异步版本 `async_fetch` 与 `async_fetch_many`，要求：
   - 每个单次操作用 `await asyncio.sleep(delay)` 模拟非阻塞 I/O。
   - 批量操作用 `asyncio.gather` 并发等待，验证 N 个任务的总耗时接近单任务时延而非 N 倍叠加。
   - 若需包装真实阻塞调用，演示 `loop.run_in_executor` 将其移出事件循环的写法，并在注释中说明何时应改用 `def` 路由托底。
3. 保持接口契约一致：同步与异步版本接收相同的任务列表与参数，返回相同结构的结果与耗时，便于后续压测直接替换。

### 步骤 4 搭建压测辅助脚本并设计对照

1. 以 `starter/bench.py` 为起点，完善压测脚本的度量能力：
   - 支持参数 `--concurrency` 与 `--requests`，控制并发度与总请求数。
   - 统计总耗时、平均时延、P95 思路的近似分位与每秒完成数，输出为可复制的表格或 CSV 行。
   - 脚本仅依赖标准库 `asyncio`、`time`、`argparse`，不引入 `locust`、`ab` 等外部工具，但输出指标与这些工具的关注点对齐。
2. 设计两组对照：
   - 对照 A，同步串行：循环调用 `sync_fetch`，记录总耗时。
   - 对照 B，异步并发：用 `asyncio.gather` 并发调用 `async_fetch`，记录总耗时与吞吐。
3. 在本地固定环境下各执行至少 3 次，取均值作为对比基线，减少单次抖动对结论的干扰。

### 步骤 5 采集数据并撰写分析报告

1. 在同一台机器、同一虚拟环境、相近系统负载下完成两组对照的压测，记录并发度、总耗时、吞吐与时延分布。
2. 用 `cProfile` 或 `time.perf_counter` 的分段计时定位热点，解释为何异步版本在 I/O 等待可重叠时吞吐更高，以及在纯计算或低并发下为何提升有限。
3. 撰写 `report.md` 或在仓库 `README.md` 中补充一节“压测分析”，包含：
   - 测试环境：Python 版本、操作系统、CPU 与内存简述。
   - 测试方法：并发模型、参数、执行次数与取均值方式。
   - 原始数据：表格展示两组对照的耗时与吞T吐。
   - 结论与边界：何时异步有效，何时需配合线程池或进程池，哪些陷阱会导致并发退化。

### 步骤 6 自检与清理

1. 运行 `python -m py_compile starter/main.py starter/bench.py` 确认语法通过，执行 `python starter/main.py --help` 确认帮助信息完整且退出码为 0。
2. 重跑 `python starter/main.py`，确认输出包含同步与异步的耗时对比，且异步总耗时显著低于同步串行。
3. 用 `git status` 确认无 `.venv`、`__pycache__`、`*.db`、`htmlcov` 等不应提交的内容，准备演示改造思路与压测结论。

## 验收标准

逐条自查，全部勾选即视为完成：

- [ ] 能口头解释同步阻塞如何卡住事件循环，以及 `async` / `await` 与 `asyncio.gather` 重叠等待的原理。
- [ ] 同步与异步两条路径在 `main.py` 中均可运行，接口契约一致，批量异步的总耗时接近单任务时延而非线性叠加。
- [ ] 压测脚本支持 `--concurrency` 与请求数参数，输出总耗时、平均时延与吞吐等指标，度量思路与 `ab` / `locust` 的关注点对齐。
- [ ] 已在固定环境下完成至少两组对照的多次执行，能展示同步与异步的耗时与吞吐对比数据。
- [ ] 已撰写分析报告，包含环境、方法、原始数据、结论与适用边界，能说明何时异步有效、何时需托底到线程池。
- [ ] 能演示一个异步陷阱案例，例如在 `async def` 中直接调用 `time.sleep` 导致并发退化，并给出 `run_in_executor` 或改 `def` 路由的修复。
- [ ] `python -m py_compile starter/main.py starter/bench.py` 通过，`python starter/main.py --help` 退出码为 0，`git status` 干净。
