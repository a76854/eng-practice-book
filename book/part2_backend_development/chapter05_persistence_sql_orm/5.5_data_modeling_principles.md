# 数据建模原则

学完本节，你能回答：

- 范式化究竟在消除什么重复，而不只是“把一张表拆成多张表”？
- 反范式化为什么可能加快某条读取链路，却会引入一致性成本？
- MeetingToText 的任务、转写片段与统计字段应该如何按查询模式取舍？

> 整理旅行行李时，把护照、衣服、药品和充电器全部塞进一个透明大袋，取东西似乎最快；但护照被水杯打湿、药品过期、充电线缠成一团时，你会发现“少分几个袋子”并不等于更简单。反过来，如果每只袜子都单独装盒，寻找和搬运又会被包装成本淹没。数据建模也在做同一种取舍：哪些事实必须分开保管，哪些结果值得为了读取效率而有意识地冗余。

范式不是拆表竞赛，反范式也不是性能捷径。二者真正讨论的是：**同一事实保存几份、更新由谁负责、读取要付出多少组合成本**。

## 只凭“表越少越快”做决定：缺了什么

**1. 重复事实会产生更新异常**

任务文件名若复制到每条转写片段，重命名一次就要修改很多行；漏改一条，接口便可能返回两个文件名。

```text
task_id=t1, filename=meeting.wav, segment=1
task_id=t1, filename=renamed.wav, segment=2
```

**2. 拆表也会增加读取成本**

任务与片段分表后，查询完整转写需要 `JOIN` 或多次查询。若没有外键索引、加载策略或清晰事务边界，“更规范”同样可能带来性能和复杂度问题。

**3. 冗余字段不会自动保持正确**

在 `tasks` 保存 `segment_count` 能减少实时 `COUNT`，但新增或删除片段时必须同步更新。应用双写、触发器和异步汇总各有一致性边界。

这些问题的根因不是范式层级不够高，而是：**团队没有明确事实的唯一来源，也没有用真实查询模式衡量拆分与冗余的代价**。

### 从“按感觉拆表”到“按依赖与查询做选择”

上述问题——更新异常、连接成本、冗余漂移——需要统一的决策顺序：**先按数据依赖建立可靠模型，再针对已经观测到的热点读取做可维护的冗余**。

## 对照式实验：同一业务的单表与两表

下面在同一 SQLite 数据库中建立两套简化结构：方案 A 把任务信息复制到片段行，方案 B 把任务和片段分开并用外键关联。示例会比较更新行数、连接方式和冗余统计字段；其中微型数据集的耗时只用于观察查询形状，不能用来推导生产性能结论。

```{code-cell} ipython3
import sqlite3
import time

conn = sqlite3.connect(":memory:")
conn.row_factory = sqlite3.Row
conn.execute("PRAGMA foreign_keys = ON")

# 方案 A：单表冗余，查询快但更新需改多行
conn.executescript("""
CREATE TABLE tasks_denorm (
    id TEXT PRIMARY KEY,
    filename TEXT NOT NULL,
    status TEXT NOT NULL,
    speaker TEXT NOT NULL,
    text TEXT NOT NULL
);
""")
conn.executemany("INSERT INTO tasks_denorm VALUES (?, ?, ?, ?, ?)", [
    ("t1", "meeting.wav", "completed", "Alice", "hello"),
    ("t1_dup", "meeting.wav", "completed", "Bob", "world"),
])
denorm_rows = conn.execute("SELECT * FROM tasks_denorm WHERE filename='meeting.wav'").fetchall()
print("denorm rows:", len(denorm_rows))
assert len(denorm_rows) == 2

# 方案 B：两表加外键，更新易但查询需连接
conn.executescript("""
CREATE TABLE tasks_norm (
    id TEXT PRIMARY KEY,
    filename TEXT NOT NULL,
    status TEXT NOT NULL
);
CREATE TABLE segments_norm (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    task_id TEXT NOT NULL REFERENCES tasks_norm(id) ON DELETE CASCADE,
    speaker TEXT NOT NULL,
    text TEXT NOT NULL
);
CREATE INDEX idx_segments_task ON segments_norm(task_id);
""")
conn.execute("INSERT INTO tasks_norm VALUES (?, ?, ?)", ("t1", "meeting.wav", "completed"))
conn.executemany("INSERT INTO segments_norm (task_id, speaker, text) VALUES (?, ?, ?)", [
    ("t1", "Alice", "hello"),
    ("t1", "Bob", "world"),
])
conn.commit()

# 查询形状观察：单表直查 vs 两表连接，各跑 500 次
def bench(sql: str, n: int = 500) -> float:
    t0 = time.perf_counter()
    for _ in range(n):
        conn.execute(sql).fetchall()
    return (time.perf_counter() - t0) / n * 1000

t_denorm = bench("SELECT * FROM tasks_denorm WHERE filename='meeting.wav'")
t_norm = bench("SELECT t.filename, s.speaker, s.text FROM tasks_norm t JOIN segments_norm s ON s.task_id = t.id WHERE t.id='t1' ORDER BY s.id")
print(f"avg ms denorm: {t_denorm:.3f} | norm join: {t_norm:.3f}")

norm_rows = conn.execute("""
SELECT t.filename, s.speaker, s.text
FROM tasks_norm t JOIN segments_norm s ON s.task_id = t.id
WHERE t.id = 't1' ORDER BY s.id
""").fetchall()
print("norm join:", [(r["speaker"], r["text"]) for r in norm_rows])
assert len(norm_rows) == 2

# 更新异常度量：改文件名，单表需改多行，两表只改一行
conn.execute("UPDATE tasks_denorm SET filename = ? WHERE filename = ?", ("renamed.wav", "meeting.wav"))
print("denorm after rename:", conn.execute("SELECT COUNT(*) FROM tasks_denorm WHERE filename='renamed.wav'").fetchone()[0])

conn.execute("UPDATE tasks_norm SET filename = ? WHERE id = ?", ("renamed.wav", "t1"))
conn.commit()
print("norm after rename:", conn.execute("SELECT filename FROM tasks_norm WHERE id='t1'").fetchone()[0])
assert conn.execute("SELECT filename FROM tasks_norm WHERE id='t1'").fetchone()[0] == "renamed.wav"

# 冗余的维护成本：统计每任务片段数，单表需额外列且易陈旧
counts = conn.execute("""
SELECT t.id, COUNT(s.id) AS cnt FROM tasks_norm t LEFT JOIN segments_norm s ON s.task_id = t.id GROUP BY t.id
""").fetchall()
print("counts:", [(r["id"], r["cnt"]) for r in counts])
assert counts[0]["cnt"] == 2

conn.execute("ALTER TABLE tasks_denorm ADD COLUMN segment_count INTEGER DEFAULT 0")
conn.execute("INSERT INTO tasks_denorm (id, filename, status, speaker, text) VALUES (?, ?, ?, ?, ?)",
             ("t2", "other.wav", "pending", "Alice", "foo"))
print("denorm segment_count stale:", conn.execute("SELECT segment_count FROM tasks_denorm WHERE id='t2'").fetchone()[0])

# 外键级联：删任务自动清片段
conn.execute("DELETE FROM tasks_norm WHERE id='t1'")
print("segments after delete:", conn.execute("SELECT COUNT(*) FROM segments_norm").fetchone()[0])
assert conn.execute("SELECT COUNT(*) FROM segments_norm").fetchone()[0] == 0

conn.close()
print("建模校验通过：更新异常与连接代价均可度量")
# 预期输出:
# denorm rows: 2
# avg ms denorm: ... | norm join: ...
# norm join: [('Alice', 'hello'), ('Bob', 'world')]
# denorm after rename: 2
# norm after rename: renamed.wav
# counts: [('t1', 2)]
# denorm segment_count stale: 0
# segments after delete: 0
# 建模校验通过：...
```

观测重点不是哪一个毫秒数更小：如此小的数据集会受缓存、SQLite 版本和机器状态影响，不能代表生产负载。真正稳定的差异是，冗余方案修改文件名需要触及多行；规范化方案只修改任务表一行，再通过关联读取片段。这个“同一事实改一处还是改多处”的差异，才是拆表的核心动因。

```{code-cell} ipython3
import gc, tempfile, pathlib
from m2t.store import TaskStore

tmpdir = tempfile.TemporaryDirectory()
store = TaskStore(pathlib.Path(tmpdir.name) / "modeling.db")
store.create("t1", "a.wav")
store.create("t2", "b.wav")
store.update("t1", status="completed", full_text="hello world")
rows = store.list_tasks(limit=10)
print("store rows:", [(r["id"], r["status"], r["full_text"][:5]) for r in rows])
assert len(rows) == 2
print("get t1:", store.get("t1")["status"], store.get("t1")["full_text"])
assert store.get("t1")["full_text"] == "hello world"
del store
gc.collect()  # Windows 上先回收尚未显式关闭的 SQLite 连接，再删除临时文件
tmpdir.cleanup()
print("TaskStore 建模校验通过：单表加索引满足当前查询模式")
# 预期输出:
# store rows: [('t2', ...), ('t1', ...)] 或相反取决于写入时序
# get t1: completed hello world
# TaskStore 建模校验通过：...
```

## 逐层拆解：何时拆表，何时冗余

刚才的度量已把权衡跑出来了，再补命名：

- **范式化**：让同一业务事实尽量只有一个权威存放位置，通过主键与外键关联，减少更新异常。
- **反范式化**：为明确的读取路径复制字段或预计算结果，用额外写入与一致性维护换取更直接的读取。

在本节的教学语境中，可以这样递进理解前三个范式：1NF 要求每个位置保存一个可直接比较和约束的值，不要把需要独立查询的说话人列表塞进逗号字符串；2NF 关注组合主键下的部分依赖，`(task_id, segment_no)` 决定片段文本，但 `task_filename` 只依赖 `task_id`；3NF 再消除非主键字段之间的传递依赖，例如 `speaker_id → speaker_name`。严格定义以函数依赖为基础，不是简单按“表拆得多不多”判断。

事务型数据通常先以一致、可约束的规范化模型为默认起点。只有当查询计划、延迟指标或成本数据证明某条读取链路成为瓶颈时，再考虑缓存、物化视图、搜索索引或冗余列。关键是明确谁为冗余的一致性买单：同一事务内更新、数据库触发器、异步任务，还是业务允许的短暂不一致。

MeetingToText 的取舍可直接套用：

- 任务 `tasks(id, filename, status, created_at, full_text)` 在当前需求下可支持按 ID 点查与按创建时间列表。
- 片段若需要按说话人、时间戳独立查询和编辑，可拆为 `segments(task_id, start, end, speaker, text)`，并为 `task_id` 建外键索引。
- 若任务列表中的片段数已被证实是高频瓶颈，可在 `tasks` 冗余 `segment_count`，但必须同时定义更新机制、失败补偿与一致性监控。

回到收拾行李的比喻：护照和水杯分开放，是为了避免不同生命周期的物品互相伤害；常用充电线放在外袋，是为已知高频动作做的有意识优化。数据库也是如此：先让事实各归其位，再为真实热点安排更短路径。无法说明一致性由谁维护的冗余，不是优化，而是一笔尚未记账的技术债。
