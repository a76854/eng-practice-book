# 数据建模

学完本节，你能回答：

- 程序里的数据为什么要存进数据库，只写进文件够不够？
- 把学生、课程、教师塞进一张表，为什么越用越别扭？
- 实体、属性、关系分别是什么，它们在 ER 图上怎么表达？
- 拆出来的表之间靠什么相互关联，主键与外键各承担什么？
- 三个范式各在消除什么，怎么用一句话判断表有没有达标？

> 程序里的数据像写在黑板上的板书，下课铃一响就被擦掉。选课名单、成绩单要是也跟着擦掉，学期末就什么也不剩了。要让它们留下来，得抄进账本；账本设几栏、几本账之间怎么对得上，动笔之前就要想清楚。

写程序的时候，数据活在内存里。变量一赋值，数据就有了；列表一追加，数据就多了。一切看起来很自然。但有一个问题很少有人在一开始就认真想过：程序一旦退出，这些数据去哪了？

答案是：什么都没了。进程结束，内存释放，变量和列表一起消失。你花了一个下午录入的测试数据，关掉终端再打开，干干净净，像什么都没发生过一样。

真实系统的数据不能这么短命。学生选的课、录进去的成绩，要一直留着，直到学期结束、甚至毕业以后。后端的第一要务，就是让数据活过程序的一生。

这一节先回答“为什么需要数据库”，再讲动手建库之前必须想明白的一件事：数据怎么组织。

## 数据持久化

先停下来想一想：程序里的数据，凭什么活到明天？

假设你写了一个选课系统的 demo。学生登录、选课、录入成绩，一切正常。可到了晚上你关掉程序，第二天再打开，昨天的选课记录全没了。原因很简单：数据存在内存里，进程结束就清零。

要让选课名单活下来，第一步是把它存到程序之外的地方。

第一反应是存文件——不就是一张表嘛。写进一个 CSV 文件，程序启动时读回来，退出时写回去。数据确实活下来了。可真的用起来，别扭的地方一个接一个：

想查“张三这学期选了几门课”，没有现成的查询，你得自己写代码逐行翻文件。教务和老师同时打开文件改名单，后保存的人直接把先保存的人覆盖掉。学号写错、成绩填 150 分，文件照单全收，没有任何人拦着。选课记录里的课程号在课程文件里根本不存在，也没有任何人发现。

如果只是数据量小、一个人用、没有并发，文件勉强够用。但只要是正经系统，上面这四个问题迟早会全部遇到。它们指向同一个答案：需要数据库。

| 载体 | 数据能活多久 | 查询能力 | 并发写入 | 数据约束 |
|---|---|---|---|---|
| 内存 | 进程结束就消失 | 程序内筛选 | 无保护 | 无 |
| 文件 | 长期保存 | 需自己解析 | 互相覆盖 | 无 |
| 数据库 | 长期保存 | 查询语言 | 事务保证 | 表结构约束 |

数据库是一种专门管数据的软件。你把数据放进有结构的表里，它给你提供一套查询语言，用事务保证多人同时写不会乱，用约束拒绝格式错误的数据。它让数据活得比程序久，而且靠得住。

于是选课系统改用数据库。

## 一张大表

知道了数据库，是不是就可以马上开建了？

先不急着动手。建库之前还有一道题要答：数据怎么组织。这道题答错了，后面所有查询都会别扭。

最直觉的做法，是把所有东西塞进一张表。选课业务里涉及三类对象：学生、课程、任课教师。把它们连同选课信息并成一张大表 `records`，一行就是一次选课：

| 学号 | 姓名 | 院系 | 课程号 | 课程名 | 学分 | 教师工号 | 教师姓名 | 教师办公室 | 成绩 | 学期 |
|---|---|---|---|---|---|---|---|---|---|---|
| 20240101 | 张三 | 计算机 | C101 | 数据库原理 | 3 | T001 | 李国华 | 理科楼301 | 88 | 2025春 |
| 20240102 | 李四 | 软件 | C101 | 数据库原理 | 3 | T001 | 李国华 | 理科楼301 | 92 | 2025春 |
| 20240101 | 张三 | 计算机 | C102 | 操作系统 | 4 | T002 | 王慧 | 理科楼205 | 78 | 2025春 |
| 20240103 | 王五 | 计算机 | C102 | 操作系统 | 4 | T002 | 王慧 | 理科楼205 | 60 | 2025春 |
| 20240201 | 赵六 | 软件 | C103 | 编译原理 | 3 | T003 | 陈明 | 工科楼410 | 85 | 2025秋 |

能存，也能查。看上去一切正常。

但再仔细看一眼：这张表的主键是什么？学号会重复，课程号也会重复，没有任何一个单列能唯一标识一行。只有把（学号, 课程号）合在一起才唯一。这说明什么？说明这一行里同时住着好几个不同层次的东西：学生信息、课程信息、教师信息、选课事实，硬塞进一行，连“这一行到底是什么”都说不清。

学生不多的时候，这只是一点“设计上的不讲究”。等学生多起来、课程多起来，问题就开始暴露了。

## 这张表开始不好管

问题不是从第一行数据开始的，而是从重复开始的。

盯着上面这张表看，李国华的办公室在每一行 C101 的记录里都写了一遍，张三的院系在他的每门选课里都写了一遍。数据少的时候你感觉不到，等选课记录到了上千条，同一份信息被复制了几百次，各种异常就来了：

**冗余**。同一份事实在多行重复存储。李国华的办公室，几百行选课记录里各写一遍。

**更新异常**。改一处要改很多行，漏改就不一致。李国华搬到理科楼 502，你要改所有包含 C101 的行——漏一行，数据库里就出现两个办公室地址。

**插入异常**。事实不完整就存不进去。李国华还没排课，想先登记他的教师信息——没有课程就无法插入这张表。新生还没选课，同样进不来。

**删除异常**。删数据时连带删掉别的信息。2025 秋编译原理没人选，你删掉这几行，陈明老师的信息也一起消失了。

一张表把“学生、课程、教师”三件事揉成了一团。每一份事实都存了多份，改一处牵动多处，删一处连坐一片。这不是数据量大了才出现的困难，而是结构性的病根。要治本，就要把这张大表拆开。

## 拆

你决定拆表。但拆成几张、每张放什么，不能拍脑袋。

动手之前先回答三个问题：业务里有哪几类对象？每类对象有哪些特征？对象之间是什么关系？这三个问题，就是数据建模的全部。

| 概念 | 含义 | 选课业务里的答案 |
|---|---|---|
| 实体 | 现实中可区分的一类对象 | 学生、课程、教师 |
| 属性 | 实体的特征，不可再分 | 学号、姓名、院系；课程号、课程名、学分；工号、姓名、办公室 |
| 关系 | 实体之间的关联，本身可带属性 | 选课：学生与课程的关联，带成绩与学期 |

回到刚才的大表，把 11 列按这三类对象各归各位，拆成四张表：

- 学生的列进 `student`：学号、姓名、院系
- 教师的列进 `teacher`：工号、姓名、办公室
- 课程的列进 `course`：课程号、课程名、学分、教师工号
- 选课的事实进 `enrollment`：谁选了哪门课、得了多少分、哪个学期

每一份事实，从此只存一处。

## 用 ER 图画学生选课

光在脑子里拆还不够。建模需要一张能讨论、能改的图，这就是 ER 图：实体画成框，属性写在框内，关系画成连线。

选课业务画出来是这样：

```{mermaid}
erDiagram
    STUDENT {
        string id PK "学号，主键"
        string name "姓名"
        string dept "院系"
    }
    TEACHER {
        string id PK "教师工号，主键"
        string name "姓名"
        string office "办公室"
    }
    COURSE {
        string id PK "课程号，主键"
        string title "课程名"
        int credits "学分"
        string teacher_id FK "外键，指向 TEACHER.id"
    }
    ENROLLMENT {
        string student_id FK "外键，指向 STUDENT.id"
        string course_id FK "外键，指向 COURSE.id"
        int score "成绩，可空"
        string semester "学期"
    }
    STUDENT ||--o{ ENROLLMENT : "选课"
    COURSE ||--o{ ENROLLMENT : "被选"
    TEACHER ||--o{ COURSE : "讲授"
```

图上有三条连线，每条都表达了关系与基数：

- `STUDENT ||--o{ ENROLLMENT`：一名学生对应零到多条选课记录
- `COURSE ||--o{ ENROLLMENT`：一门课程对应零到多条选课记录
- `TEACHER ||--o{ COURSE`：一名教师讲授零到多门课程

注意一个细节：学生和课程原本是多对多的关系——一个学生选多门课，一门课被多个学生选。多对多不能直接用外键表达，所以中间加了一张 `enrollment` 关系表，把一个多对多拆成了两个一对多。教师和课程是一对多，外键 `teacher_id` 直接放在 `course` 这一端就够了。

ER 图的每个元素都有对应的表规则：

| ER 元素 | 表规则 |
|---|---|
| 实体 | 一张表，实体名即表名 |
| 属性 | 表的列 |
| 主键 | PRIMARY KEY |
| 关系（1 对 N） | N 端加外键指向 1 端主键 |
| 关联实体的属性 | 关联表中的普通列 |

把图画清楚，拆表就有了依据。`student`、`teacher`、`course` 各是一张表，`enrollment` 用两个外键把三张表串起来。框与线各自落位，怎么用 SQL 一句句建出来，是建库阶段的事。

## 拆分到什么程度

拆到什么程度才算合理？有一个递进的标尺叫范式化。

它逐级消除冗余，每一级回答一个问题：

| 范式 | 消除的问题 | 一句话判别 |
|---|---|---|
| 第一范式（1NF） | 列里再分 | 一个字段里是不是塞了多个值？ |
| 第二范式（2NF） | 非主键列只部分依赖主键 | 联合主键下，有没有字段只依赖其中一列？ |
| 第三范式（3NF） | 非主键列传递依赖 | 有没有字段依赖另一个非主键字段？ |

光看定义有点抽象，跟着三个例子走一遍。

## 第一范式：字段里不塞多个值

先看一个违反第一范式的例子。一张表存学生的选课，把一名学生选的几门课塞进一个字段：

| 学号 | 姓名 | 所选课程 |
|---|---|---|
| 20240101 | 张三 | 数据库原理，操作系统 |
| 20240102 | 李四 | 数据库原理 |

`所选课程` 这个字段里用逗号装了多个值——这就是“列里再分”。问题在哪？如果你想查“谁选了操作系统”，只能先把 `所选课程` 拆开再匹配，没法直接用 `WHERE 所选课程 = '操作系统'` 来查。

修法是把每门课拆成一行：

| 学号 | 姓名 | 所选课程 |
|---|---|---|
| 20240101 | 张三 | 数据库原理 |
| 20240101 | 张三 | 操作系统 |
| 20240102 | 李四 | 数据库原理 |

现在每个字段都是单一值，谁选了操作系统可以直接查。代价是学号和姓名开始重复。更彻底的拆法是把选课单独成表，就是前面 ER 图里的 `enrollment`。

第一范式的核心就一句：字段里不要塞列表。

## 第二范式：字段只依赖整个主键

再来看第二范式。假设选课表用 (学号, 课程号) 做联合主键，却把课程名也放了进来：

| 学号 | 课程号 | 课程名 | 成绩 |
|---|---|---|---|
| 20240101 | C101 | 数据库原理 | 88 |
| 20240102 | C101 | 数据库原理 | 92 |

课程名只依赖课程号，不依赖学号——它只依赖联合主键的一部分，这叫“部分依赖”。问题在哪？课程改名的时候，所有选了这门课的行都要跟着改，漏一行就不一致。

修法是把课程名挪回课程表，选课表只留联合主键和成绩：

| 学号 | 课程号 | 成绩 |
|---|---|---|
| 20240101 | C101 | 88 |
| 20240102 | C101 | 92 |

第二范式的核心就一句：字段要么依赖整个主键，要么别放在这张表里。

## 第三范式：字段不依赖另一个非主键字段

最后看第三范式。课程表里既存教师工号，又存教师办公室：

| 课程号 | 课程名 | 教师工号 | 教师办公室 |
|---|---|---|---|
| C101 | 数据库原理 | T001 | 理科楼301 |
| C102 | 操作系统 | T002 | 理科楼205 |

办公室依赖的是教师工号，不是课程号——它通过教师工号间接依赖课程号，这叫“传递依赖”。问题在哪？李国华搬办公室，他名下所有课程行都要改。

修法是把教师信息挪进教师表，课程表只留外键：

| 课程号 | 课程名 | 教师工号 |
|---|---|---|
| C101 | 数据库原理 | T001 |

办公室只存在 `teacher` 表一处，课程表通过工号引用。

第三范式的核心就一句：非主键字段之间别产生依赖关系。

**范式化的目标是减少冗余，但减少冗余不总是最优的。走多高范式要看读写比例。**

举个例子：一张订单表，你每次都同时查订单和客户信息。如果严格遵循第三范式，订单表只存 `customer_id`，每次查询都要做一次 JOIN。如果客户信息很少变动，把客户姓名直接冗余到订单表里，可以减少一次 JOIN，查询变快——代价是客户改名时你需要更新多行。

这就是典型的“用冗余换速度”。范式化是起点，不是终点。第三章“读写分离与反范式化”会展开讲什么时候该打破范式、什么时候该刻意冗余。这一节的任务是先把基础范式走通——在不知道规则之前，谈不上打破规则。

## 本节小结

- 数据活在内存里会随进程消失，文件又扛不住查询、并发与约束，所以需要数据库。
- 把学生、课程、教师塞进一张大表，连主键都说不清，冗余、更新异常、插入异常、删除异常随之而来。
- 建模用实体、属性、关系三要素描述现实世界，画成 ER 图后再落成表。
- 学生与课程的多对多经关系表拆成两个一对多，教师与课程的一对多由课程表的外键表达。
- 范式化给拆表一个递进的标尺：列不拆分、字段只依赖整个主键、不依赖另一个非主键字段，本质是让每一份事实只存一处。知道规则之后，才有资格讨论什么时候打破规则。

> 表在动手建之前想好怎么拆。拆得清楚，存得才不乱。
