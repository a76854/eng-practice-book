# 数据建模

学完本节，你能回答：

- 为什么“先把所有字段放进一张表”会产生更新、插入和删除异常？
- 实体、属性和关系分别对应现实世界中的什么？
- ER 图上的实体、主键、关系和基数如何落到表、列、外键与约束？

> 图书馆若只用一张 Excel 记录所有事情，每借出一本书，就把读者姓名、手机号、书名、作者和出版社重新抄一遍。起初只有几十条记录，看起来非常省事；等读者换了手机号、同一本书被借了上百次，管理员才发现：改一条不够，少改一条就会出现两个版本的“同一个读者”。数据库建模做的事情，就是先分清“读者是谁、图书是谁、借阅是哪次关系”，再决定它们应该如何关联。

初学者最容易把数据库理解成“能存行和列的文件”，于是拿到需求便立即建表。问题是，字段能被塞进去，不代表事实被表达正确。建模真正要解决的不是 SQL 语法，而是：**一个事实应该存在哪里，以及谁有权引用它**。

## 一张大表能跑：缺了什么

下面这张表把学生、课程和选课事实全部混在一起：

```text
records(student_id, student_name, student_dept,
        course_id, course_title, course_credits, score, semester)
```

**1. 同一事实没有唯一存放位置**

学生姓名和院系会在每条选课记录中重复。一名学生选十门课，同一份学生信息就被复制十次。

```text
S001 张三 计算机 C101 数据库 88
S001 张三 计算机 C102 操作系统 91
```

**2. 一次修改可能留下多个版本**

学生转专业时必须更新所有相关行；只漏掉一行，数据库便同时声称张三属于两个院系。这不是某条 `UPDATE` 写错，而是模型允许同一事实散落多处。

```sql
UPDATE records SET student_dept = '软件工程' WHERE student_id = 'S001';
```

**3. 不相关事实被迫一起出生、一起消失**

尚未选课的新生没有课程字段可填；删除某门课最后一条选课记录，又可能连课程名称和学分一起删掉。实体的生命周期被关系记录绑在了一起。

这些问题并不是“一张表一定错误”。如果一行本来就是一个完整、不可再拆的业务事实，单表完全合理。系统性问题在于：**学生、课程和选课拥有不同身份与生命周期，却没有被建模为不同对象**。

### 从字段清单到事实地图

上述问题——信息重复、更新不一致、生命周期纠缠——看似分别发生在写入、修改和删除阶段，但解决思路是统一的：**先识别实体与关系，再用约束把这张事实地图变成数据库可执行的规则**。

## 逐层拆解：实体、属性与关系

- **实体（Entity）**：可被独立识别和管理的对象集合，如学生、课程。
- **属性（Attribute）**：描述实体或关系的特征，如学生姓名、课程学分、选课分数。
- **关系（Relationship）**：实体之间发生的事实，如“学生选择课程”；关系自身也可以拥有学期、分数等属性。

建模会把混杂字段拆成实体表和关系表：主键标识“它是谁”，外键说明“它引用谁”，`NOT NULL / UNIQUE / CHECK` 等约束说明“什么数据才算合法”。ER 图就是落库前的图形化契约。

## 对照一：学生选课关系

以最经典的学生选课为例：学生（STUDENT）可选多门课程（COURSE），一门课程可被多名学生选，选课本身是独立事实，需记录分数与学期，故抽象为关联实体 ENROLLMENT。

```{mermaid}
erDiagram
    STUDENT {
        string id PK "学号，主键"
        string name "姓名"
        string dept "院系"
        date enroll_date "入学日期"
    }
    COURSE {
        string id PK "课程号，主键"
        string title "课程名"
        int credits "学分"
        string dept "开课院系"
    }
    ENROLLMENT {
        string student_id FK "学号，外键 -> STUDENT.id"
        string course_id FK "课程号，外键 -> COURSE.id"
        int score "分数，可空"
        string semester "学期"
    }
    STUDENT ||--o{ ENROLLMENT : "选课"
    COURSE ||--o{ ENROLLMENT : "被选"
```

关系解读：

- `STUDENT ||--o{ ENROLLMENT` 表示一名学生可对应零至多条选课记录（`||` 为“ exactly one”端是学生侧，`o{` 为“zero or many”端是选课侧）。
- `COURSE ||--o{ ENROLLMENT` 同理。
- 学生与课程之间是**多对多**，通过 ENROLLMENT 这张关联表解耦为两个**一对多**。

### 从 ER 图映射到表结构

ER 图的每个元素都有确定的落盘规则：

| ER 元素 | 关系表规则 |
|---|---|
| 实体 | 一张表，实体名即表名 |
| 实体的属性 | 表的列，选合适类型 |
| 主键（PK） | `PRIMARY KEY`，实体标识 |
| 关系（1:N） | N 端加外键指向 1 端主键 |
| 关联实体的属性 | 关联表中的普通列 |

落到 SQL：

```sql
-- 实体 STUDENT -> 表 student
CREATE TABLE student (
    id TEXT PRIMARY KEY,
    name TEXT NOT NULL,
    dept TEXT NOT NULL,
    enroll_date TEXT NOT NULL
);

-- 实体 COURSE -> 表 course
CREATE TABLE course (
    id TEXT PRIMARY KEY,
    title TEXT NOT NULL,
    credits INTEGER NOT NULL CHECK (credits > 0),
    dept TEXT NOT NULL
);

-- 关联实体 ENROLLMENT -> 表 enrollment
-- 联合主键保证同一学生在同一学期不能重复选择同一课程
CREATE TABLE enrollment (
    student_id TEXT NOT NULL REFERENCES student(id) ON DELETE CASCADE,
    course_id TEXT NOT NULL REFERENCES course(id) ON DELETE CASCADE,
    score INTEGER CHECK (score BETWEEN 0 AND 100),
    semester TEXT NOT NULL,
    PRIMARY KEY (student_id, course_id, semester)
);
```

要点：

- `student.id` 与 `course.id` 用 `PRIMARY KEY` 保证唯一标识。
- `enrollment.student_id` / `course_id` 用 `REFERENCES ... ON DELETE CASCADE` 保证选课必有合法的学生与课程，删学生自动清理其选课。
- `name`、`semester` 等用 `NOT NULL` 拒绝无意义的空数据；`score` 用 `CHECK` 限制合法区间。

## 对照二：医院挂号关系

再看一个更贴近真实业务的例子：医院信息系统（HIS）。核心流程是患者（PATIENT）找医生（DOCTOR）挂号（REGISTRATION），一次挂号可开多张处方（PRESCRIPTION），处方关联药品信息。

```{mermaid}
erDiagram
    PATIENT {
        string id PK "患者编号"
        string name "姓名"
        string gender "性别"
        date birth_date "出生日期"
        string phone "手机号"
    }
    DOCTOR {
        string id PK "工号"
        string name "姓名"
        string dept "科室"
        string title "职称"
    }
    REGISTRATION {
        string id PK "挂号单号"
        string patient_id FK "患者外键 -> PATIENT.id"
        string doctor_id FK "医生外键 -> DOCTOR.id"
        datetime reg_time "挂号时间"
        string status "状态"
    }
    PRESCRIPTION {
        string id PK "处方编号"
        string registration_id FK "挂号外键 -> REGISTRATION.id"
        string drug_name "药品名"
        int quantity "数量"
        string dosage "用法用量"
    }
    PATIENT ||--o{ REGISTRATION : "挂号"
    DOCTOR ||--o{ REGISTRATION : "接诊"
    REGISTRATION ||--o{ PRESCRIPTION : "开具"
```

关系解读：

- 患者与医生均为**一对多**面向挂号：一位患者可多次挂号，一位医生可接诊多次挂号，但一次挂号只对应一位患者与一位医生。
- 挂号与处方是**一对多**：一次挂号可开零至多张处方，处方通过 `registration_id` 外键归属到具体挂号单。

### ER → CREATE TABLE 映射（医院 HIS）

同样按“实体-表、属性-列、关系-外键”落盘：

```sql
-- 实体 PATIENT -> 表 patient
CREATE TABLE patient (
    id TEXT PRIMARY KEY,
    name TEXT NOT NULL,
    gender TEXT NOT NULL CHECK (gender IN ('男','女')),
    birth_date TEXT NOT NULL,
    phone TEXT NOT NULL UNIQUE
);

-- 实体 DOCTOR -> 表 doctor
CREATE TABLE doctor (
    id TEXT PRIMARY KEY,
    name TEXT NOT NULL,
    dept TEXT NOT NULL,
    title TEXT NOT NULL
);

-- 关系 + 实体 REGISTRATION -> 表 registration（带两个外键）
CREATE TABLE registration (
    id TEXT PRIMARY KEY,
    patient_id TEXT NOT NULL REFERENCES patient(id) ON DELETE RESTRICT,
    doctor_id TEXT NOT NULL REFERENCES doctor(id) ON DELETE RESTRICT,
    reg_time TEXT NOT NULL DEFAULT (datetime('now')),
    status TEXT NOT NULL CHECK (status IN ('待就诊','已就诊','已取消'))
);

-- 子实体 PRESCRIPTION -> 表 prescription（外键指向 registration）
CREATE TABLE prescription (
    id TEXT PRIMARY KEY,
    registration_id TEXT NOT NULL REFERENCES registration(id) ON DELETE CASCADE,
    drug_name TEXT NOT NULL,
    quantity INTEGER NOT NULL CHECK (quantity > 0),
    dosage TEXT NOT NULL
);
CREATE INDEX idx_prescription_registration ON prescription(registration_id);
```

设计权衡：

- 本示例假设医院以手机号作为不可重复的联系方式，因此给 `patient.phone` 加 `UNIQUE`；真实系统不能把手机号直接当作患者身份，应由业务规则决定唯一键。`gender` 与 `status` 的枚举同样是为演示约束而做的简化。
- `registration` 对患者与医生的外键用 `ON DELETE RESTRICT` —— 不允许直接删除仍有挂号的患者或医生，避免悬空引用。
- `prescription` 对 `registration` 用 `ON DELETE CASCADE` —— 挂号单作废时自动清理处方，符合业务级联语义。
- 为 `prescription.registration_id` 建索引，加速“查某次挂号的所有处方”这一高频查询。

两张 ER 图的共性：先用图形把“谁与谁有何关系”说清楚，再把每个框、每条线翻译为建表语句中的约束。约束不是事后补丁，而是模型在数据库层的可执行契约。

## 可运行示例：让 ER 约束真正拒绝脏数据

下面用标准库 `sqlite3` 在内存库中复现学生系统与 HIS 的核心表，并验证三种约束：主键唯一、非空、外键。

```{code-cell} ipython3
import sqlite3

# 建库并开启外键约束（SQLite 默认关闭，需显式开启）
conn = sqlite3.connect(":memory:")
conn.execute("PRAGMA foreign_keys = ON")
print("foreign_keys:", conn.execute("PRAGMA foreign_keys").fetchone()[0])
assert conn.execute("PRAGMA foreign_keys").fetchone()[0] == 1

# --- 1. 建表：学生系统 ---
conn.executescript("""
CREATE TABLE student (
    id TEXT PRIMARY KEY,
    name TEXT NOT NULL,
    dept TEXT NOT NULL,
    enroll_date TEXT NOT NULL
);
CREATE TABLE course (
    id TEXT PRIMARY KEY,
    title TEXT NOT NULL,
    credits INTEGER NOT NULL CHECK (credits > 0),
    dept TEXT NOT NULL
);
CREATE TABLE enrollment (
    student_id TEXT NOT NULL REFERENCES student(id) ON DELETE CASCADE,
    course_id TEXT NOT NULL REFERENCES course(id) ON DELETE CASCADE,
    score INTEGER CHECK (score BETWEEN 0 AND 100),
    semester TEXT NOT NULL,
    PRIMARY KEY (student_id, course_id, semester)
);
""")
print("student/course/enrollment tables created")

# --- 2. 建表：医院 HIS 核心表 ---
conn.executescript("""
CREATE TABLE patient (
    id TEXT PRIMARY KEY,
    name TEXT NOT NULL,
    gender TEXT NOT NULL CHECK (gender IN ('男','女')),
    birth_date TEXT NOT NULL,
    phone TEXT NOT NULL UNIQUE
);
CREATE TABLE doctor (
    id TEXT PRIMARY KEY,
    name TEXT NOT NULL,
    dept TEXT NOT NULL,
    title TEXT NOT NULL
);
CREATE TABLE registration (
    id TEXT PRIMARY KEY,
    patient_id TEXT NOT NULL REFERENCES patient(id) ON DELETE RESTRICT,
    doctor_id TEXT NOT NULL REFERENCES doctor(id) ON DELETE RESTRICT,
    reg_time TEXT NOT NULL DEFAULT (datetime('now')),
    status TEXT NOT NULL CHECK (status IN ('待就诊','已就诊','已取消'))
);
CREATE TABLE prescription (
    id TEXT PRIMARY KEY,
    registration_id TEXT NOT NULL REFERENCES registration(id) ON DELETE CASCADE,
    drug_name TEXT NOT NULL,
    quantity INTEGER NOT NULL CHECK (quantity > 0),
    dosage TEXT NOT NULL
);
""")
print("patient/doctor/registration/prescription tables created")

# --- 3. 正常写入 ---
conn.execute("INSERT INTO student VALUES (?, ?, ?, ?)", ("S001", "张三", "计算机", "2024-09-01"))
conn.execute("INSERT INTO student VALUES (?, ?, ?, ?)", ("S002", "李四", "软件", "2024-09-01"))
conn.execute("INSERT INTO course VALUES (?, ?, ?, ?)", ("C101", "数据库", 3, "计算机"))
conn.execute("INSERT INTO course VALUES (?, ?, ?, ?)", ("C102", "操作系统", 4, "计算机"))
conn.execute("INSERT INTO enrollment VALUES (?, ?, ?, ?)", ("S001", "C101", 88, "2025春"))
conn.execute("INSERT INTO patient VALUES (?, ?, ?, ?, ?)", ("P001", "王五", "男", "1990-01-10", "13800000001"))
conn.execute("INSERT INTO doctor VALUES (?, ?, ?, ?)", ("D001", "赵医生", "内科", "主任医师"))
conn.execute("INSERT INTO registration VALUES (?, ?, ?, datetime('now'), ?)", ("R001", "P001", "D001", "待就诊"))
conn.execute("INSERT INTO prescription VALUES (?, ?, ?, ?, ?)", ("RX001", "R001", "阿莫西林", 2, "口服 每日3次"))
conn.commit()
print("valid inserts ok:", conn.execute("SELECT COUNT(*) FROM enrollment").fetchone()[0], "enrollments")

# --- 4. 约束验证：主键唯一 ---
try:
    conn.execute("INSERT INTO student VALUES (?, ?, ?, ?)", ("S001", "重复学号", "计算机", "2024-09-01"))
    conn.commit()
    raise AssertionError("应触发主键冲突")
except sqlite3.IntegrityError as e:
    print("PK 校验通过:", e)
    conn.rollback()

# --- 5. 约束验证：非空 ---
try:
    conn.execute("INSERT INTO student VALUES (?, ?, ?, ?)", ("S003", None, "计算机", "2024-09-01"))
    conn.commit()
    raise AssertionError("应触发非空约束")
except sqlite3.IntegrityError as e:
    print("NOT NULL 校验通过:", e)
    conn.rollback()

# --- 6. 约束验证：外键 ---
try:
    conn.execute("INSERT INTO enrollment VALUES (?, ?, ?, ?)", ("S999", "C101", 90, "2025春"))
    conn.commit()
    raise AssertionError("应触发外键约束")
except sqlite3.IntegrityError as e:
    print("FK 校验通过（学生不存在）:", e)
    conn.rollback()

try:
    conn.execute("INSERT INTO prescription VALUES (?, ?, ?, ?, ?)", ("RX002", "R999", "头孢", 1, "口服"))
    conn.commit()
    raise AssertionError("应触发外键约束")
except sqlite3.IntegrityError as e:
    print("FK 校验通过（挂号不存在）:", e)
    conn.rollback()

# --- 7. 级联与受限删除 ---
# enrollment 对 student 是 CASCADE：删学生自动清选课
conn.execute("DELETE FROM student WHERE id='S001'")
print("after delete S001, enrollment count:", conn.execute("SELECT COUNT(*) FROM enrollment").fetchone()[0])
assert conn.execute("SELECT COUNT(*) FROM enrollment").fetchone()[0] == 0

# registration 对 patient 是 RESTRICT：仍有挂号时不可删患者
try:
    conn.execute("DELETE FROM patient WHERE id='P001'")
    conn.commit()
    raise AssertionError("应触发 RESTRICT")
except sqlite3.IntegrityError as e:
    print("RESTRICT 校验通过:", e)
    conn.rollback()

conn.close()
print("建表与约束校验全部通过：主键/外键/非空/级联均按 ER 设计生效")
# 预期输出:
# foreign_keys: 1
# student/course/enrollment tables created
# patient/doctor/registration/prescription tables created
# valid inserts ok: 1 enrollments
# PK 校验通过: UNIQUE constraint failed: student.id
# NOT NULL 校验通过: NOT NULL constraint failed: student.name
# FK 校验通过（学生不存在）: FOREIGN KEY constraint failed
# FK 校验通过（挂号不存在）: FOREIGN KEY constraint failed
# after delete S001, enrollment count: 0
# RESTRICT 校验通过: FOREIGN KEY constraint failed
# 建表与约束校验全部通过：...
```

逐层回看这个示例：ER 图的实体框落成表，身份属性落成主键，关系线落成外键，业务边界落成 `NOT NULL / UNIQUE / CHECK`。SQLite 的外键检查需要在每个连接上显式启用；否则 `REFERENCES` 虽然写进了表定义，却不会替应用拒绝悬空引用。

回到图书馆的比喻：读者信息只放在读者档案，图书信息只放在图书目录，每次借阅只记录“谁借了哪本书”。现在改手机号只改一处，删除一条借阅记录也不会让图书凭空消失。好的模型不是把表拆得越多越好，而是让每个事实都有清楚、唯一且可约束的归属。

