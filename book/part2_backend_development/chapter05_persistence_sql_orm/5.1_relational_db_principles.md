# 关系型数据库原理

> 学完本节，你能回答：为什么“存进去的数据”不等同于“存对了的数据”？ACID 如何保证并发与故障下的正确性？索引为什么能加速查询却拖慢写入？锁与 WAL 又在什么层面解决并发冲突？

## 为什么需要事务：从“半成品写入”说起

想象银行转账：从 A 账户扣 100 元，向 B 账户加 100 元。若第一步成功、第二步因断电失败，钱就凭空消失。事务（Transaction）就是把多条 SQL 打包为“要么全做、要么全不做”的原子单元。

类比写论文：点“保存”前你在内存中改了三段，断电后只有“已保存”的版本还在。事务的 `COMMIT` 就是“保存”，`ROLLBACK` 就是“撤销本次未保存的修改”。

## ACID：事务的四条契约

- **Atomicity 原子性**：事务内所有操作要么全部生效，要么全部不生效。用 `BEGIN` / `COMMIT` / `ROLLBACK` 划定边界，中间任何失败都回滚到起点。
- **Consistency 一致性**：事务前后数据库从一个合法状态到另一个合法状态，约束（`PRIMARY KEY` / `NOT NULL` / `CHECK` / `FOREIGN KEY`）始终成立。
- **Isolation 隔离性**：并发事务互不干扰的程度。SQLite 默认提供串行化语义的近似，通过锁与 WAL 实现；PostgreSQL/MySQL 则提供 `READ COMMITTED` / `REPEATABLE READ` 等多档可选。
- **Durability 持久性**：一旦 `COMMIT` 返回成功，数据即落盘，宕机后仍在。WAL（Write-Ahead Log）先写日志再写数据文件，确保崩溃可恢复。

> **与 `m2t/store.py` 的呼应**：`TaskStore._get_conn()` 中 `PRAGMA journal_mode=WAL` 与 `busy_timeout=5000` 正是持久性与隔离性的工程体现——WAL 让读不阻塞写，`busy_timeout` 让短暂锁冲突等待而非直接抛错。

## 索引：用空间换时间的目录

没有索引的查询是“翻遍整本书找一句话”；有索引是“先查目录再翻页”。`m2t/store.py` 的 `idx_tasks_created_at` 就是为 `ORDER BY created_at DESC` 加的目录。

- **B-Tree 索引**：最常见，适合等值与范围查询。
- **代价**：写入时需同步更新索引，索引越多写入越慢；索引本身占空间。
- **选择原则**：为高频 `WHERE` / `ORDER BY` / `JOIN` 列建索引，避免为低区分度或极少查询的列建索引。

## 锁概览：谁在什么时候挡住谁

- **共享锁 vs 排他锁**：读可并发（共享），写需独占（排他）。
- **行锁 vs 表锁**：行锁粒度细、并发高；表锁简单但易阻塞。
- **SQLite 的简版**：单写者多读者，写时短暂加排他锁，WAL 模式下读不阻塞写，这也是 `m2t` 能用 SQLite 支撑本地并发演示的原因。
- **乐观 vs 悲观**：乐观假设冲突少、提交时检查；悲观假设冲突多、操作前先加锁。选型取决于冲突概率与重试成本。

## 可运行示例：事务提交与回滚

示例（用 `sqlite3` 演示原子性与约束一致性，无网络）：

```{code-cell} ipython3
import sqlite3

# 使用 :memory: 内存库，保证示例自包含且可重复执行
conn = sqlite3.connect(":memory:")
conn.execute("PRAGMA journal_mode=WAL")
conn.execute("""
CREATE TABLE tasks (
    id TEXT PRIMARY KEY,
    filename TEXT NOT NULL,
    status TEXT NOT NULL DEFAULT 'pending',
    created_at TEXT NOT NULL DEFAULT (datetime('now')),
    full_text TEXT DEFAULT ''
)
""")
conn.execute("CREATE INDEX idx_tasks_created_at ON tasks(created_at DESC)")
conn.commit()

# 1) 提交：两条插入在同一事务中一并可见
conn.execute("BEGIN")
conn.execute("INSERT INTO tasks (id, filename) VALUES (?, ?)", ("t1", "a.wav"))
conn.execute("INSERT INTO tasks (id, filename) VALUES (?, ?)", ("t2", "b.wav"))
conn.commit()
cnt = conn.execute("SELECT COUNT(*) FROM tasks").fetchone()[0]
print("after commit:", cnt)
assert cnt == 2

# 2) 回滚：主键冲突触发异常，显式 ROLLBACK 回到事务起点
try:
    conn.execute("BEGIN")
    conn.execute("INSERT INTO tasks (id, filename) VALUES (?, ?)", ("t3", "c.wav"))
    # 重复主键 t1，触发 IntegrityError
    conn.execute("INSERT INTO tasks (id, filename) VALUES (?, ?)", ("t1", "dup.wav"))
    conn.commit()
except sqlite3.IntegrityError as e:
    print("integrity error:", e)
    conn.rollback()

cnt2 = conn.execute("SELECT COUNT(*) FROM tasks").fetchone()[0]
print("after rollback:", cnt2)
assert cnt2 == 2  # t3 未留下，体现原子性：要么全做要么全不做

# 3) 保存点（SAVEPOINT）：事务内的“子事务”，可局部回滚
conn.execute("BEGIN")
conn.execute("INSERT INTO tasks (id, filename) VALUES (?, ?)", ("t3", "c.wav"))
conn.execute("SAVEPOINT sp1")
conn.execute("INSERT INTO tasks (id, filename) VALUES (?, ?)", ("t4", "d.wav"))
conn.execute("ROLLBACK TO SAVEPOINT sp1")  # 仅撤销 t4
conn.execute("RELEASE SAVEPOINT sp1")
conn.commit()
rows = conn.execute("SELECT id FROM tasks ORDER BY id").fetchall()
print("ids after savepoint:", [r[0] for r in rows])
assert [r[0] for r in rows] == ["t1", "t2", "t3"]

# 4) 一致性：NOT NULL 约束拦截非法写入
try:
    conn.execute("INSERT INTO tasks (id, filename) VALUES (?, ?)", ("t5", None))
    conn.commit()
except sqlite3.IntegrityError as e:
    print("not-null violated:", e)
    conn.rollback()

conn.close()
print("ACID 校验通过：提交/回滚/保存点/约束均按预期")
# 预期输出:
# after commit: 2
# integrity error: UNIQUE constraint failed: tasks.id
# after rollback: 2
# ids after savepoint: ['t1', 't2', 't3']
# not-null violated: NOT NULL constraint failed: tasks.filename
# ACID 校验通过：提交/回滚/保存点/约束均按预期
```
