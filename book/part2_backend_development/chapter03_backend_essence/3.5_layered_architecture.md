# 分层架构落地

学完本节，你能回答：

- 为什么把校验、业务和 SQL 都写进路由，会让一个小功能越来越难改？
- 为什么 Controller—Service—Repository 值得作为中型后端的默认分工起点？
- 三层各自依赖什么、返回什么，测试时又应该替换哪一层？

> 医院如果让挂号窗口的工作人员同时负责问诊、开药和管理病历库，病人少时似乎非常高效：不用转交，一人从头办到底。但病人一多，窗口前就会排起长队；换一个病历系统，连挂号流程都得重学；诊断出了问题，也分不清是登记错误、医疗判断还是记录丢失。挂号、诊疗与病历管理的分工，不是为了增加手续，而是让每个角色只承担自己能解释、能测试、能替换的责任。

FastAPI 可以让我们很快写出一个路由函数。也正因为太方便，数据库查询、重复检查、状态流转和错误码常常被顺手塞进同一个函数。第一版代码从上到下都看得见，第二版还能勉强维护；当十几个路由都复制了相似规则时，一次存储变化就可能变成全项目搜索替换。

## 一个函数处理到底：缺了什么

下面是“万能路由”的典型形状：

```text
@app.post("/tasks")
    解析请求
    校验字段
    查询数据库判断重复
    写入数据库
    捕获数据库异常
    选择 HTTP 状态码
    拼装响应
```

它能完成需求，却把三种变化速度不同的代码绑在了一起。

**1. 业务规则只能通过 HTTP 测试**

“任务编号不能重复”本来是一条业务规则。如果它只存在于路由函数中，测试这条规则就必须构造请求、启动应用上下文，还可能连接数据库。

```text
想测一条 if → 被迫启动整条 Web 链路
```

测试变慢只是表面问题。更危险的是，未来 CLI 或后台任务要复用“创建任务”逻辑时，只能复制规则，或反过来调用自己的 HTTP 接口。

**2. HTTP 语义渗入业务核心**

当业务函数直接抛 `HTTPException(status_code=409)`，它就知道自己运行在 FastAPI 中。相同逻辑若被命令行调用，“HTTP 409”既没有意义，也让核心代码无法脱离框架独立测试。

```text
业务冲突 ≠ HTTP 409
业务冲突 --由 Controller 翻译--> HTTP 409
```

业务层应该表达“任务已存在”，表现层再决定它在 HTTP 中对应什么状态码。

**3. 存储实现变成业务的一部分**

Service 如果到处直接写 SQL 或调用某个 ORM 会话，数据库表名、事务和查询语法就散进业务代码。从 SQLite 换到 PostgreSQL，或在测试中改用内存替身时，业务逻辑也要跟着修改。

```text
业务规则 + SQL 细节 + HTTP 错误 = 三种变化被锁在同一处
```

这些问题并不是因为函数“行数太多”。一个很长但职责单一的函数未必糟糕；一个只有二十行却同时理解 HTTP、业务和数据库的函数，依然高度耦合。系统性根因是：**依赖方向没有边界，上层协议和下层实现都侵入了业务核心**。

### 从按文件切分到按职责切分

上述问题——业务难以独立测试、HTTP 污染核心、存储无法替换——看似对应测试、框架和数据库，但解决方案是统一的：**让依赖沿 Controller → Service → Repository 单向流动，每层只翻译相邻边界**。

## 两种结构：万能路由 vs 三层协作

旧方式把所有知识集中在路由：

```text
HTTP Request
     ↓
Route（HTTP + 业务 + SQL）
     ↓
Database
```

分层后，请求仍然走同样的业务流程，但责任被显式分开：

```text
HTTP Request
     ↓
Controller ── 翻译 HTTP 与应用调用
     ↓
Service ───── 执行业务规则与编排
     ↓
Repository ── 翻译领域操作与持久化
     ↓
SQLite / PostgreSQL / 内存替身
```

这不是要求每个项目机械地创建三个类。它首先是一条依赖原则：**业务规则不应依赖 HTTP，业务编排不应依赖某个具体数据库实现**。当项目只有一个简单只读接口时，三层文件可能显得多余；当规则需要被多个入口复用、存储需要替换、测试开始变慢时，分层的收益会迅速出现。

## 逐层拆解：每一层守什么

### Controller：HTTP 的翻译官

Controller 只理解 Web 协议：

- 用路由、方法和 Pydantic 模型接收请求。
- 调用 Service，不自行实现业务规则。
- 把业务异常翻译为状态码和错误体。
- 把应用结果转换成响应模型。

“薄 Controller”不是追求越短越好，而是要求其中每一行都与 HTTP 边界有关。若删除 FastAPI 后某段逻辑仍然有业务意义，它通常应该下沉到 Service。

### Service：领域规则的编排者

Service 表达系统真正要做的事：

- 检查任务能否创建、状态能否流转。
- 组织一个或多个 Repository 或外部服务完成用例。
- 定义应用层异常，如“任务已存在”“任务不存在”。
- 必要时划定事务边界，但不处理 HTTP 状态码。

Service 应该能被 HTTP 路由、CLI、定时任务和单元测试直接调用。入口变了，业务规则不需要复制。

### Repository：持久化的翻译官

Repository 把领域友好的操作转换成存储动作：

- 对外提供 `create()`、`get()`、`list_all()` 等接口。
- 对内封装 SQL、ORM、文件或远程数据服务。
- 隐藏表结构和查询细节。
- 在测试中可以换成内存实现，在生产中换成 SQLite 或 PostgreSQL 实现。

Repository 不应决定“重复任务是否允许”，因为这是业务规则；它只负责准确执行读取和写入，并报告存储层结果。

## 目录落地：结构要表达依赖方向

一个最小目录可以这样组织：

```text
backend/app/
├── routers/
│   └── tasks.py          # Controller：HTTP 翻译
├── services/
│   └── task_service.py   # Service：业务规则
├── repositories/
│   └── task_repo.py      # Repository：存储适配
└── models/
    └── task_schemas.py   # 请求与响应契约
```

目录名本身不会自动带来分层。如果 `routers/tasks.py` 仍然直接操作数据库，或者 `task_service.py` 到处抛 `HTTPException`，只是把面条代码切成了多个文件。真正的判断标准是依赖：Controller 知道 Service，Service 只知道 Repository 的接口，Repository 不反向导入上层。

## 可运行示例：同一 Service 替换两种 Repository

下面用一段完整代码验证三个目标：Service 可以脱离 FastAPI 直接测试；Controller 只负责 HTTP 翻译；同一个 Service 可以在内存 Repository 与 `TaskStore` Repository 之间切换。

文件 `examples/layered_architecture_demo.py`：

```{code-cell} ipython3
import pathlib
import tempfile
from typing import Annotated, Protocol, TypedDict

from fastapi import Depends, FastAPI, HTTPException
from fastapi.testclient import TestClient
from pydantic import BaseModel, Field

from m2t.store import TaskStore

class TaskRow(TypedDict):
    id: str
    filename: str
    status: str

# Repository 接口：Service 依赖能力，不依赖具体存储
class TaskRepository(Protocol):
    def create(self, task_id: str, filename: str) -> None: ...
    def get(self, task_id: str) -> TaskRow | None: ...

class InMemoryTaskRepository:
    def __init__(self) -> None:
        self._rows: dict[str, TaskRow] = {}

    def create(self, task_id: str, filename: str) -> None:
        self._rows[task_id] = {
            "id": task_id,
            "filename": filename,
            "status": "pending",
        }

    def get(self, task_id: str) -> TaskRow | None:
        return self._rows.get(task_id)

class SqliteTaskRepository:
    def __init__(self, db_path: pathlib.Path) -> None:
        self._store = TaskStore(db_path)

    def create(self, task_id: str, filename: str) -> None:
        self._store.create(task_id, filename, full_text="")

    def get(self, task_id: str) -> TaskRow | None:
        row = self._store.get(task_id)
        if row is None:
            return None
        return {
            "id": row["id"],
            "filename": row["filename"],
            "status": row["status"],
        }

# Service：不导入 FastAPI，不知道 HTTP 状态码
class TaskAlreadyExistsError(Exception):
    pass

class TaskNotFoundError(Exception):
    pass

class TaskService:
    def __init__(self, repo: TaskRepository) -> None:
        self._repo = repo

    def create(self, task_id: str, filename: str) -> TaskRow:
        task_id = task_id.strip()
        filename = filename.strip()
        if not task_id or not filename:
            raise ValueError("task_id and filename must be non-empty")
        if self._repo.get(task_id) is not None:
            raise TaskAlreadyExistsError(task_id)
        self._repo.create(task_id, filename)
        row = self._repo.get(task_id)
        assert row is not None
        return row

    def get(self, task_id: str) -> TaskRow:
        row = self._repo.get(task_id)
        if row is None:
            raise TaskNotFoundError(task_id)
        return row

# 先直接单测 Service：不需要 HTTP，也不需要数据库
memory_service = TaskService(InMemoryTaskRepository())
unit_row = memory_service.create("unit-1", "unit.wav")
print("service unit test:", unit_row)
assert memory_service.get("unit-1")["status"] == "pending"

try:
    memory_service.create("unit-1", "again.wav")
except TaskAlreadyExistsError:
    print("service duplicate rule: passed")

# Controller 契约与依赖注入
class CreateTaskIn(BaseModel):
    task_id: str = Field(min_length=1)
    filename: str = Field(min_length=1)

class TaskOut(BaseModel):
    id: str
    filename: str
    status: str

http_service = TaskService(InMemoryTaskRepository())

def get_task_service() -> TaskService:
    return http_service

app = FastAPI(title="Layered Architecture Demo")

@app.post("/api/tasks", response_model=TaskOut)
def create_task(
    payload: CreateTaskIn,
    service: Annotated[TaskService, Depends(get_task_service)],
) -> TaskOut:
    try:
        row = service.create(payload.task_id, payload.filename)
    except TaskAlreadyExistsError as exc:
        raise HTTPException(status_code=409, detail="task already exists") from exc
    except ValueError as exc:
        raise HTTPException(status_code=422, detail=str(exc)) from exc
    return TaskOut(**row)

@app.get("/api/tasks/{task_id}", response_model=TaskOut)
def get_task(
    task_id: str,
    service: Annotated[TaskService, Depends(get_task_service)],
) -> TaskOut:
    try:
        row = service.get(task_id)
    except TaskNotFoundError as exc:
        raise HTTPException(status_code=404, detail="task not found") from exc
    return TaskOut(**row)

client = TestClient(app)

created = client.post(
    "/api/tasks",
    json={"task_id": "http-1", "filename": "meeting.wav"},
)
print("controller create:", created.status_code, created.json())
assert created.status_code == 200

missing = client.get("/api/tasks/missing")
print("controller missing:", missing.status_code, missing.json()["detail"])
assert missing.status_code == 404

# 换成 SQLite Repository：Service 代码完全不变
with tempfile.TemporaryDirectory() as directory:
    sqlite_repo = SqliteTaskRepository(pathlib.Path(directory) / "tasks.db")
    sqlite_service = TaskService(sqlite_repo)
    sqlite_row = sqlite_service.create("db-1", "stored.wav")
    print("sqlite repository:", sqlite_row)
    assert sqlite_service.get("db-1")["filename"] == "stored.wav"

# 预期输出：
# service unit test: {'id': 'unit-1', 'filename': 'unit.wav', 'status': 'pending'}
# service duplicate rule: passed
# controller create: 200 {'id': 'http-1', 'filename': 'meeting.wav', 'status': 'pending'}
# controller missing: 404 task not found
# sqlite repository: {'id': 'db-1', 'filename': 'stored.wav', 'status': 'pending'}
```

逐层看替换是如何发生的：

- `TaskRepository` 用 `Protocol` 描述 Service 需要的最小能力，Service 不关心实现来自内存还是 SQLite。
- `InMemoryTaskRepository` 让业务规则在毫秒级单元测试中运行，不需要文件和数据库初始化。
- `SqliteTaskRepository` 把 `TaskStore` 的返回结构适配成统一的 `TaskRow`，存储细节没有泄漏到 Service。
- `TaskService` 抛出应用层异常，不包含 FastAPI；Controller 再把它们分别翻译为 409、404 或 422。
- `Depends(get_task_service)` 把 Service 的创建方式留在路由之外，测试或生产配置可以替换依赖。

## 分层后的测试策略

三层应使用不同粒度的验证：

- **Controller 测试**：用 `TestClient` 验证路由、Pydantic 校验、状态码和响应 JSON。
- **Service 测试**：注入内存或 Fake Repository，集中覆盖业务分支，不启动 Web 服务。
- **Repository 测试**：连接临时或真实测试库，验证 SQL、映射、约束与事务。

这样一来，业务分支的大量用例可以保持快速，少量集成测试再确认层与层之间是否正确连接。分层不是为了让测试目录更漂亮，而是为了让错误更容易定位：路由错误看 Controller，规则错误看 Service，数据错误看 Repository。

回到医院的比喻：Controller 像挂号窗口，负责接收信息和解释流程；Service 像医生，根据规则做出业务判断；Repository 像病历系统，准确保存和取回记录。换掉病历软件，不该要求医生重写诊疗原则；增加线上挂号，也不该复制一套医疗规则。

三层架构不是必须永远保持三层的教条。小而稳定的只读接口可以合并，复杂事务也可能拆出领域层或应用层。真正值得保留的是边界判断：**协议变化停在 Controller，业务变化集中在 Service，存储变化封装在 Repository**。有了这条单向依赖，后续章节才能分别深化 HTTP、数据库与异步任务，而不让每次学习都推倒前面的代码。
