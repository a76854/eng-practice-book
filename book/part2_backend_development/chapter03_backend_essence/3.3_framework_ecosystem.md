# 框架生态谱系

学完本节，你能回答：

- 为什么 Python 已有 Django 和 Flask，仍会出现 FastAPI？
- 为什么框架功能越多不一定越适合当前项目？
- Django、Flask 与 FastAPI 分别把哪些工程责任交给框架，哪些留给团队？

> 装修房子有三种常见选择：精装房交钥匙就能住，但格局和材料多由开发商决定；毛坯房只有基本结构，水电、柜子和风格都由业主选择；模块化装修则预先提供一组标准组件，按接口快速组合。没有哪一种天然高级——赶时间入住、追求完全定制、还是希望标准化组装，会导向不同答案。Django、Flask 与 FastAPI，也是在“框架替你决定多少”这条轴上的不同落点。

初学框架时，我们很容易把它们理解成三套写法不同的路由工具，然后用“哪个更新、哪个更快、哪个教程更多”做选择。可一旦项目进入认证、数据库、校验、文档和部署阶段，真正拉开差异的并不是 `@app.get()` 与 `@app.route()` 的拼写，而是每个框架预先替团队做了哪些决定。

## 只看最小示例：缺了什么

三种框架都能用几行代码返回“Hello World”。如果比较到这里就结束，它们几乎没有区别：

```text
URL → 路由函数 → HTTP 响应
```

真实项目却不会停在一个路由。随着功能增加，框架与团队之间的责任分配开始决定工程成本。

**1. 把“代码少”误当成“项目简单”**

Flask 的最小应用很短，但数据库、认证、输入校验和目录约定仍然存在，只是需要团队自行选择与组合。首页只有十行代码，不代表完整项目只有十行复杂度。

```text
核心代码少 + 扩展选择多 + 团队约定缺失 = 胶合成本上升
```

如果没有统一规范，不同成员可能分别引入不同扩展、错误格式和目录结构，灵活最终变成碎片化。

**2. 把“功能齐全”误当成“没有代价”**

Django 自带 ORM、管理后台、认证和迁移，能迅速搭起完整站点。但当项目只需要少量 JSON API，或必须接入已有数据层时，这些约定未必都能产生收益。

```text
框架默认流程 ≠ 项目已有流程
```

偏离框架主路径越远，团队越需要理解内部机制并编写适配代码。开箱即用的另一面，是接受一组预先选择。

**3. 把“新框架”理解成“旧框架的替代品”**

FastAPI 在类型驱动、OpenAPI 和异步服务上提供了更直接的支持，但这并不意味着它自动取代 Django 的管理后台生态，也不意味着所有 Flask 小工具都应该重写。

```text
新能力解决新约束，不等于覆盖所有旧场景
```

这些误判的共同根因是：**只比较框架表面的 API，没有比较框架替团队承担了哪些工程责任**。框架谱系不是版本升级路线，而是责任分配方式的演进。

### 从“哪个框架更强”到“谁来负责什么”

上述问题——最小代码掩盖胶合成本、全栈能力带来约定成本、新旧关系被误读——看似各不相同，但解决方案是统一的：**把框架放到同一组工程责任上比较，明确每项能力由框架提供还是由团队组装**。

## 三种框架：三种责任分配方式

可以把 Python Web 框架放在一条连续谱上：

```text
框架承担更多                                            团队自行组合更多
Django（全栈约定） ───── FastAPI（类型化 API） ───── Flask（微核心）
```

这条线不是成熟度排名。它只说明默认责任的多少：Django 提供完整站点所需的大量组件；Flask 保留最小 WSGI 核心；FastAPI 聚焦现代 API 的契约、校验与异步基础，同时把 ORM、管理后台等选择留给团队。

## 逐层拆解：每个框架把什么装进“房子”

### Django：带完整生活系统的精装房

Django 采用“batteries-included”思路，把 ORM、迁移、认证、表单和管理后台等能力放进同一套框架约定中。

- **默认得到**：统一项目结构、ORM 与迁移、认证体系、模板和管理后台。
- **优先场景**：内容站、管理后台、CRUD 密集且希望快速形成统一规范的项目。
- **主要代价**：需要学习并遵守较多框架约定；深度定制或接入完全不同的数据模型时，适配成本会上升。

当需求与 Django 的默认路径一致时，“框架替你决定更多”意味着少做大量重复选择；当需求偏离主路径时，同一套约定也可能成为限制。

### Flask：从最小骨架开始的毛坯房

Flask 官方将其定位为轻量 WSGI Web 应用框架，核心围绕请求、路由、响应与上下文展开，其他能力主要通过扩展或普通 Python 库接入。[^1]

- **默认得到**：清晰、轻量的 Web 核心和较低的入门门槛。
- **优先场景**：原型、小工具、边界明确的微服务，以及希望看清每个组成部分的教学项目。
- **主要代价**：ORM、校验、认证和大型项目结构都要自行选型；团队必须维护扩展之间的兼容性与统一规范。

Flask 的“小”指核心职责克制，不代表它只能做小项目。它能扩展到复杂系统，只是规模增长后，原本由全栈框架承担的整合责任会落到团队手中。

### FastAPI：围绕 API 契约组装的模块化方案

FastAPI 基于 Starlette 提供 Web/ASGI 能力，基于 Pydantic 处理数据模型，并围绕 OpenAPI 自动生成接口描述和交互式文档。[^2]

- **默认得到**：类型驱动的参数解析、运行时校验、OpenAPI 文档、依赖注入与异步支持。
- **优先场景**：JSON API、AI 集成、I/O 密集服务，以及前后端需要通过 OpenAPI 并行协作的项目。
- **主要代价**：ORM、管理后台和部分业务组件仍需自行选择；团队还要理解类型模型与同步/异步边界。

FastAPI 的“现代”不是简单地指发布时间更晚，而是它把 Python 类型标注、数据校验和开放 API 标准放进了核心开发路径。

## 对照式选择：项目需要什么，框架提供什么

| 维度 | Django | Flask | FastAPI |
|---|---|---|---|
| 核心定位 | 完整 Web 站点 | 轻量 WSGI 核心 | 类型化 API 框架 |
| ORM/迁移 | 内置并深度集成 | 自行选择 | 自行选择 |
| 管理后台 | 内置 | 自行建设 | 自行建设 |
| 输入校验 | 表单/序列化体系 | 自行选择 | Pydantic 核心集成 |
| OpenAPI | 通常依赖额外组件 | 通常依赖额外组件 | 核心能力 |
| 异步路径 | 支持逐步增强 | WSGI 为核心 | ASGI 与异步为核心 |
| 团队主要责任 | 理解并遵守约定 | 选型并整合组件 | 设计类型契约并补齐业务组件 |

选择时可以按需求反推：

- 管理后台和关系型 CRUD 是主角，优先评估 Django。
- 应用很小、组合方式高度自定义，优先评估 Flask。
- API 契约、自动文档和异步 I/O 是主角，优先评估 FastAPI。

“优先评估”不等于直接定案。团队经验、存量组件、部署平台和验证成本仍然要进入最终决策。

## 可运行示例：观察 FastAPI 默认承担的责任

下面不把重点放在“又写一个 Hello World”，而是检查同一份类型声明如何同时参与路由解析、错误响应和 OpenAPI 文档。这正是 FastAPI 在框架谱系中选择承担的责任。

文件 `examples/framework_spectrum_demo.py`：

```{code-cell} ipython3
from typing import Annotated

from fastapi import FastAPI, Path, Query
from fastapi.testclient import TestClient
from pydantic import BaseModel, Field

class EchoOut(BaseModel):
    name: str = Field(description="回显名称")
    times: int = Field(ge=1, le=3)
    messages: list[str]

app = FastAPI(title="Framework Spectrum Demo", version="0.1.0")

@app.get("/echo/{name}", response_model=EchoOut, tags=["demo"])
def echo(
    name: Annotated[str, Path(min_length=1, max_length=20)],
    times: Annotated[int, Query(ge=1, le=3)] = 1,
) -> EchoOut:
    return EchoOut(
        name=name,
        times=times,
        messages=[name] * times,
    )

client = TestClient(app)

ok = client.get("/echo/m2t", params={"times": 2})
print("valid:", ok.status_code, ok.json())
assert ok.json()["messages"] == ["m2t", "m2t"]

invalid = client.get("/echo/m2t", params={"times": 9})
print("invalid:", invalid.status_code, invalid.json()["detail"][0]["type"])
assert invalid.status_code == 422

schema = app.openapi()
operation = schema["paths"]["/echo/{name}"]["get"]
print("operation id:", operation["operationId"])
print("response model:", operation["responses"]["200"]["content"]["application/json"]["schema"])

assert operation["tags"] == ["demo"]
assert "EchoOut" in schema["components"]["schemas"]

# 预期输出：
# valid: 200 {'name': 'm2t', 'times': 2, 'messages': ['m2t', 'm2t']}
# invalid: 422 less_than_equal
# operation id: echo_echo__name__get
# response model: {'$ref': '#/components/schemas/EchoOut'}
```

逐段看这份代码中谁承担了什么：

- `Path` 与 `Query` 把边界约束写在路由签名旁，框架负责解析并在失败时返回 422。
- `EchoOut` 同时是运行时响应模型和 OpenAPI 中的 JSON Schema 来源。
- `response_model` 让返回值接受统一验证，也让调用方提前知道响应形状。
- `app.openapi()` 证明文档不是另一份手写材料，而是从当前代码生成的契约。

如果用 Flask 实现同一需求，路由本身依然很短，但参数校验、错误体与 OpenAPI 需要额外方案；如果用 Django，实现方式则会更多地融入它的 URL、视图与序列化生态。差别不在“能不能做”，而在“默认由谁负责”。

回到装修的比喻：Django 把完整生活系统一起交付，Flask 留出最大的设计自由，FastAPI 则围绕 API 提供标准化模块。选框架不是挑功能最多的包装盒，而是决定哪些工程责任值得交给框架，哪些应该由团队掌握。
