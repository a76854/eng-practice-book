# 后端是什么

学完本节，你能回答：

- 最早的网页没有"后端"这个概念，内容是如何被送到浏览器里的？
- 什么需求迫使服务器从"返回写死的文件"变成"现场生成页面"？
- 前后端一体为什么后来要分离，分离真正解决的是什么问题？
- 分离之后，后端的职责边界划在哪四条线上？

> 后端与前端的关系，像餐厅的后厨与前厅。最早的后厨连摆盘也包了，菜做好直接端上桌。后来前厅有了自己的手艺，后厨只管把标准化的菜做出来，前厅再按堂食、外带与外卖各自摆盘。分工一旦划清，双方都能独立精进。

打开浏览器输入一个网址，几毫秒后页面铺满屏幕。这看似平常的一瞬，藏着 Web 系统最根本的分工问题：你看到的内容，是谁、在什么时候、以什么方式做出来的。这个问题在三十年前几乎没有争议，如今却足以决定一个团队的协作方式与一个系统的演进能力。理解后端，不能从一堆术语切入，而要从这个问题的历史演变讲起。

## 静态年代：只有文件，没有"后端"

上世纪九十年代初的 Web，是一张"文件网"。浏览器向服务器请求一个地址，服务器把磁盘上写好的 HTML 文件原样返回，浏览器负责把它渲染成页面。页面是静止的，所有访问者看到的是完全一样的内容。

这时的分工极其简单：服务器是守着文件的看门人，浏览器是把文件画出来的画师。没有人谈论"前端"还是"后端"，因为整件事只有一步，把一个写死的文档送到用户眼前。

## 动态内容：服务器开始"现场生成"

静态页面足够展示文档，却撑不起论坛与电子商务。当用户需要看到自己的订单、别人的最新发言时，服务器不能再返回同一份写死的文件了，它必须根据请求者的身份与此刻的数据，现场生成一份只属于这次访问的页面。

为了现场生成，人们让服务器运行程序：程序读取数据库里的数据，拼进 HTML 模板，再把成品返回。这就是后端的雏形，在服务器上运行、负责把数据变成页面的那段程序。与之相对，浏览器里负责排版与交互的那段代码，被称为前端。

自这一刻起，"前端"与"后端"才有了各自的名字与分工：前端管用户看到什么、点什么，后端管数据从哪来、怎么算、怎么给。

## 前后端一体：模板直出的黄金年代

最早的后端程序用 CGI 拼页面，之后 PHP、JSP、Jinja 等模板引擎把这件事做得极其顺手。后端从数据库取数据、填入模板、直出一份完整 HTML，路由、业务、渲染都在同一进程、同一份代码里完成。

这种一体化的形态有它朴素的好处：链路短、上手快、内容直出对首屏与搜索友好。但它也埋下一个结构性问题，渲染代码与业务代码纠缠在一起，改一个按钮的颜色，可能要连后端一起重新发布。那是一个 App 尚未普及、浏览器是唯一终端的年代，这个问题并不致命，于是这种一体化形态延续了很多年。

| 方面 | 一体化的表现 | 当时的代价 |
|---|---|---|
| 渲染 | 后端拼好 HTML 直出 | 页面与业务耦合，改动互相牵制 |
| 终端 | 只服务浏览器 | 尚无多终端压力，尚可接受 |
| 协作 | 前后端同仓同发布 | 团队小、节奏慢，问题不明显 |
| 测试 | 需解析 HTML 断言 | 自动化成本高，但不被重视 |

这张表里的每一项"代价"，在当时都不构成痛点，真正的转折来自终端的裂变。

## 为什么分离：一份数据，多种呈现

智能手机与单页应用改变了格局。同一个后端的数据，既要渲染成 Web 页面，又要喂给 iOS 与 Android，还要开放给第三方平台。后端辛辛苦苦拼出来的 HTML 只有浏览器认得，App 拿到手便是死路。

于是分工被重新划了一次：后端不再拼 HTML，只返回结构化的数据，最常用的是 JSON；渲染交给各终端自己完成。Web 前端、App、开放平台各自消费这同一份 JSON，按各自的方式呈现。

| 维度 | 一体：模板直出 | 分离：JSON 接口 | 带来的变化 |
|---|---|---|---|
| 渲染地点 | 服务端拼好 HTML | 后端返 JSON，前端渲染 | 一份数据可多端复用 |
| 契约形态 | HTML 即契约，随页面变动 | JSON Schema 即契约，相对稳定 | 可并行开发与自动测试 |
| 部署 | 前后端同进程同发布 | 前端可上 CDN，后端独立伸缩 | 各自独立演进 |
| 协作 | 改文案牵连后端 | 通过接口契约对齐 | 前后端解耦 |

分离的代价是要显式维护一份契约，新增字段需考虑兼容与版本。但这个代价换来了多端复用与独立演进的可能性，从整体看是一笔划算的交易。

## 分离之后：如何一句话定位后端

分离让系统稳定地分成三层：前端负责呈现与交互，存储负责持久化，后端夹在中间，负责接收请求、执行业务规则、读写存储，再把结构化数据返回。

这一定位落到职责上，是四条边界线：

| 职责 | 定义 | 容易失守的表现 |
|---|---|---|
| API 设计 | 对外契约：路径、方法、请求与响应形状 | 随意增删字段导致前端崩溃 |
| 业务逻辑 | 领域规则：校验、去重、状态流转 | 在路由函数里混写规则 |
| 数据流转 | 持久化与传输：请求到对象的映射、事务 | SQL 散落各处，无事务边界 |
| 安全防护 | 认证、授权、校验、限流与审计 | 只在前端校验，后端信任任意输入 |

四条边界让"后端守什么"变得可检查，也让改动能沿边界收敛：改校验不碰存储，换数据库不改路由。

## 本节小结

- 后端不是突然冒出来的概念，它诞生于服务器从"返回文件"转向"现场生成"的那一刻，职责是把数据变成用户能消费的东西。
- 前后端一体以模板直出为核心，优点是链路短、直出友好，代价是渲染与业务耦合，在多终端到来前并不致命。
- 多终端与单页应用迫使前后端分离，后端只返回 JSON，渲染下放给各终端，换来复用与独立演进。
- 分离后的系统是前端、后端、存储三层，后端守 API 设计、业务逻辑、数据流转与安全防护四条边界。
- 一句话定位后端：面向前端提供可编程数据接口、面向存储维护一致性与安全的服务层。
