# 后端是什么

学完本节，你能回答：

- 为什么“后端能返回一个网页”不等于前后端已经划清边界？
- 为什么 JSON API 值得作为多端应用的默认协作契约？
- API 设计、业务逻辑、数据流转与安全防护在一条请求中分别扮演什么角色？

> 一家餐厅如果让顾客直接走进后厨找厨师点菜，第一天也许很快：顾客少，厨师记性好，想吃什么当面说。但顾客一多，问题就来了——有人催菜、有人改口味、有人翻开冰箱自己拿食材，厨师既要做菜又要记账，还得判断谁能进仓库。前厅、后厨与仓库的分工，不是为了多设几道门，而是为了让点单、做菜和保管食材各有边界。现代 Web 系统中的前端、后端与存储也是如此。

许多初学者把“会写后端”等同于“能接收一个请求，再返回一些内容”。这个理解只看见了请求的起点和终点，却忽略了中间最重要的部分：谁负责解释输入、谁执行规则、谁维护数据一致性、谁阻止越权访问。后端真正的价值，不只是“返回 JSON”，而是**在前端与存储之间守住规则和边界**。

## 一个应用全包：缺了什么

最早接触 Web 开发时，我们常把页面模板、业务判断与数据库操作写在同一个处理函数中：

```text
浏览器请求
   ↓
路由函数：查数据库 → 判断状态 → 拼 HTML → 返回页面
   ↓
浏览器显示
```

这条链路短、反馈快，很适合个人网站或功能简单的内容站。但当系统需要同时服务网页、移动端和第三方调用者时，“一个函数全包”的便利会迅速变成协作成本。

**1. 展示与业务绑在一起**

后端返回的是拼好的 HTML，页面结构便成了接口的一部分。前端想调整交互，往往要改后端模板；后端想调整数据结构，又可能让页面渲染直接报错。

```text
TemplateNotFound: tasks/detail.html
```

错误表面上发生在模板，根因却可能是业务处理函数同时承担了查询、判断和展示三种职责。任何一处变化都会牵动整条链路。

**2. 新终端无法复用现有能力**

网页能理解 HTML，但移动 App、桌面客户端和自动化脚本更需要结构化数据。如果后端只会“返回页面”，同一个任务查询功能就要为不同终端重复实现。

```text
Web 需要任务列表 → 返回 HTML
App 需要任务列表 → 重新写一套接口
```

重复的不只是代码，还包括校验、权限与错误处理。一旦两套实现更新不同步，同一任务在不同终端可能呈现出不同状态。

**3. 存储细节容易泄漏到边界之外**

为了省事，前端可能直接依赖数据库字段名，甚至自行拼接查询条件。这样看似少写了一层代码，却把表结构变成了公开契约：数据库一改字段，所有调用方一起失效；权限控制也很难集中执行。

```text
OperationalError: no such column: task.file_path
```

这些问题并不是 HTML 或模板技术本身造成的。模板直出在内容站、后台管理等场景依旧合理。真正的系统性根因是：**展示、规则与存储之间缺少稳定的职责边界，调用方只能依赖具体实现，而不能依赖明确契约**。

### 从共享实现到共享契约

上述问题——展示与业务耦合、多端无法复用、存储细节外泄——看似发生在不同位置，但解决方案是统一的：**前后端不再共享页面实现，而是通过稳定的数据契约协作**。

## 两种协作方式：模板直出 vs JSON API

旧方式由后端同时负责数据与页面：

```text
浏览器 ──HTTP──> 后端（业务 + 数据 + HTML 模板）──> 数据库
```

前后端分离后，三层各自承担一种核心责任：

```text
前端（呈现与交互）
        │ HTTP + JSON
        ▼
后端（契约、规则与安全）
        │ 查询与事务
        ▼
存储（持久化与检索）
```

一句话定位后端：**后端是面向前端提供可编程数据接口、面向存储维护业务一致性与安全的服务层**。

| 维度 | 后端模板直出 | 前后端分离（JSON API） |
|---|---|---|
| 渲染地点 | 后端拼好 HTML | 前端根据 JSON 渲染 |
| 协作契约 | 页面模板与上下文变量 | HTTP 方法、状态码与 JSON 结构 |
| 多端复用 | 通常围绕 Web 页面 | Web、App、脚本可共用接口 |
| 发布方式 | 页面与后端经常一起发布 | 前后端可独立构建和部署 |
| 自动化测试 | 常需解析 HTML | 可直接断言状态码与 JSON |

这张表不是在宣布“模板直出已经过时”。如果产品以内容展示和后台表单为主，模板直出往往更简单。当前端交互频繁、需要多端复用或团队并行开发时，JSON API 才更能体现价值。工程选择的关键不是追求形式新，而是看哪种边界更符合协作约束。

## 逐层拆解：后端到底守哪些边界

前后端分离不是把 HTML 换成 JSON 就结束了。后端内部至少还要守住四条职责线，它们沿着一次请求依次协作。

**1. API 设计：定义对外承诺**

API 决定资源叫什么、使用什么 HTTP 方法、请求与响应有哪些字段、失败时返回什么状态码。契约一旦被前端和第三方使用，修改就会产生协作成本，因此要先设计边界，再填充实现。

页面路由与数据接口也应显式区分：

- `/tasks/123` 可以是前端页面地址，返回应用的 HTML 壳。
- `/api/tasks/123` 是后端数据接口，返回任务 JSON。

统一的 `/api` 前缀让网关能够对数据接口集中配置鉴权、限流与审计，也避免前端路由和后端路由争抢同一 URL 空间。

**2. 业务逻辑：执行领域规则**

“任务编号不可重复”“只有创建者能删除任务”“完成的任务不能重新进入处理中”都属于业务规则。它们不应依赖某个按钮或某张数据库表，而应由后端集中执行，保证不同调用方得到一致结论。

**3. 数据流转：维护状态与一致性**

数据从请求体进入系统，要经过输入模型、领域对象、数据库记录，再转换成响应模型。后端负责这些映射以及事务边界，存储层则负责可靠地保存与检索，而不是向前端暴露表结构。

**4. 安全防护：为每道边界设门**

认证回答“你是谁”，授权回答“你能做什么”，输入校验判断“数据是否合法”，限流与审计则处理滥用和追踪。安全不是请求末尾补上的一个 `if`，而是贯穿入口、业务和落库前的检查点。

理想的单向链路可以概括为：

```text
HTTP 契约 → 输入校验 → 业务编排 → 持久化 → 响应映射
       ↘──────── 安全与审计贯穿全链路 ────────↗
```

## 可运行示例：让四条职责线各就各位

下面用一个最小任务接口验证这条链路。示例复用 `m2t.store.TaskStore` 作为存储边界，使用 `TestClient` 在进程内发起请求，不需要启动真实网络服务。

文件 `examples/backend_boundary_demo.py`：

```{code-cell} ipython3
import pathlib
import tempfile
from typing import Annotated

from fastapi import Depends, FastAPI, Header, HTTPException, status
from fastapi.testclient import TestClient
from pydantic import BaseModel, Field

from m2t.store import TaskStore

# Repository：封装存储细节
tmpdir = tempfile.TemporaryDirectory()
store = TaskStore(pathlib.Path(tmpdir.name) / "tasks.db")

# Service：只表达业务规则，不依赖 HTTP
class TaskService:
    def __init__(self, store: TaskStore):
        self.store = store

    def create(self, task_id: str, filename: str) -> dict:
        if not task_id.strip() or not filename.strip():
            raise ValueError("task_id and filename must be non-empty")
        if self.store.get(task_id) is not None:
            raise ValueError("task already exists")
        self.store.create(task_id, filename, full_text="")
        row = self.store.get(task_id)
        assert row is not None
        return row

service = TaskService(store)

# API 契约：声明请求与响应的形状
class CreateTaskIn(BaseModel):
    task_id: str = Field(min_length=1)
    filename: str = Field(min_length=1)

class TaskOut(BaseModel):
    id: str
    filename: str
    status: str

# 安全边界：集中校验请求头
def verify_api_key(
    x_api_key: Annotated[str | None, Header()] = None,
) -> None:
    if x_api_key != "demo-secret":
        raise HTTPException(status_code=401, detail="invalid api key")

app = FastAPI(title="Backend Boundary Demo")

@app.post(
    "/api/tasks",
    response_model=TaskOut,
    status_code=status.HTTP_201_CREATED,
)
def create_task(
    payload: CreateTaskIn,
    _: None = Depends(verify_api_key),
) -> TaskOut:
    try:
        row = service.create(payload.task_id, payload.filename)
    except ValueError as exc:
        code = 409 if "exists" in str(exc) else 422
        raise HTTPException(status_code=code, detail=str(exc)) from exc
    return TaskOut(**row)

@app.get("/api/tasks/{task_id}", response_model=TaskOut)
def get_task(task_id: str) -> TaskOut:
    row = store.get(task_id)
    if row is None:
        raise HTTPException(status_code=404, detail="task not found")
    return TaskOut(**row)

# 本地验证：契约、安全、业务与存储依次生效
client = TestClient(app)

unauthorized = client.post(
    "/api/tasks",
    json={"task_id": "t1", "filename": "meeting.wav"},
)
print("without key:", unauthorized.status_code)
assert unauthorized.status_code == 401

created = client.post(
    "/api/tasks",
    json={"task_id": "t1", "filename": "meeting.wav"},
    headers={"x-api-key": "demo-secret"},
)
print("created:", created.status_code, created.json())
assert created.status_code == 201

duplicate = client.post(
    "/api/tasks",
    json={"task_id": "t1", "filename": "meeting.wav"},
    headers={"x-api-key": "demo-secret"},
)
print("duplicate:", duplicate.status_code)
assert duplicate.status_code == 409

queried = client.get("/api/tasks/t1")
print("queried:", queried.status_code, queried.json())
assert queried.json()["filename"] == "meeting.wav"

tmpdir.cleanup()

# 预期输出：
# without key: 401
# created: 201 {'id': 't1', 'filename': 'meeting.wav', 'status': 'pending'}
# duplicate: 409
# queried: 200 {'id': 't1', 'filename': 'meeting.wav', 'status': 'pending'}
```

逐层回看这个示例：Pydantic 模型定义了 API 契约，依赖函数守住安全入口，`TaskService` 集中执行业务规则，`TaskStore` 隔离持久化细节，路由函数只负责把 HTTP 与内部调用互相翻译。任何一层都没有独自“完成整个后端”，但它们共同构成了可测试、可替换的请求闭环。

回到餐厅的比喻：前端是接待顾客的前厅，存储是保管原料和账目的仓库，后端则是连接两者的后厨与调度系统。JSON API 像格式统一的点菜单，四条职责线则确保每张订单都被正确解释、执行、记录和授权。分层并不是把简单事情复杂化，而是让复杂系统仍能说清“谁应该为哪一步负责”。
