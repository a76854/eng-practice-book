# 为何选择 FastAPI

学完本节，你能回答：

- 为什么“性能高、语法新”不足以成为选择 FastAPI 的理由？
- 为什么异步支持、自动文档与类型校验恰好对应本课程的核心约束？
- Pydantic 模型、路由签名与 OpenAPI 在前后端协作链路中分别扮演什么角色？

> 快递中转站的价值，不是传送带转得最快，而是它能否处理这批货物：有些包裹要等待海关结果，有些要核对易碎标签，有些还要把运单同步给多个配送方。若只看传送带空转速度，很可能选出一个“跑得快却接不住业务”的系统。MeetingToText 的后端也是一座中转站——它要等待音频上传、ASR 和 LLM，还要让前端随时知道数据格式，并在脏输入进入业务前把它拦下。

上一节已经说明，Django、Flask 与 FastAPI 没有脱离场景的绝对排名。现在把场景收窄到本课程：任务从音频上传开始，要经过持久化、ASR、文本处理和 LLM 生成纪要；前端与后端并行开发；学生还需要看得见、测得到每一道数据边界。框架选型必须解释它如何降低这条链路的主要成本。

## 只凭“现代、高性能”选框架：缺了什么

FastAPI 经常被贴上“快”“异步”“自动文档”等标签。标签可以帮助记忆，却不能代替选型论证。如果不知道项目为什么需要这些能力，技术优势很容易变成装饰。

**1. 把框架吞吐当成业务吞吐**

MeetingToText 的主要等待来自上传、数据库、ASR 和 LLM，而不是路由函数里几行 Python 的执行时间。如果外部 ASR 调用需要数秒，即使框架把路由开销再降低一半，用户也几乎感受不到。

```text
请求总耗时 = 路由开销 + 数据库等待 + ASR 等待 + LLM 等待
```

真正有价值的是：等待外部 I/O 时能否释放执行机会去处理其他请求。异步解决的是“等待期间如何调度”，不是自动让 ASR 计算本身变快。

**2. 把接口文档当成上线前补写的说明书**

如果后端代码、接口文档和前端类型定义分别维护，同一个字段可能出现三种版本：后端已经把 `language` 改成可选，文档仍写必填，前端生成代码又保留旧枚举。

```text
代码已更新 + 文档未更新 = 契约漂移
```

问题不是团队“不认真写文档”，而是同一事实存在多个维护入口，变化无法自动同步。

**3. 把输入校验散落到业务函数**

手动读取字典后再写 `if`，第一版看起来直接；字段一多，长度、格式、枚举和嵌套结构会散落在路由与 Service 中。不同接口可能对同一个任务编号执行不同规则。

```text
payload.get("task_id") → 多处判断 → 多种错误格式
```

这些问题的系统性根因是：**项目的主要约束没有落到同一条可执行链路中**。等待、契约与校验分别靠临时方案处理，框架就只是一个路由装饰器，而不是工程协作的基础设施。

### 从功能标签到约束映射

上述问题——吞吐指标错位、文档与代码漂移、校验规则分散——看似属于性能、协作和质量三个方向，但解决方案是统一的：**让框架的核心能力直接承接项目的核心约束，并能用代码和测试验证这种对应关系**。

## 旧链路与新链路：变化发生在哪里

旧方式把三项责任分开维护：

```text
手动解析 JSON → 路由中手写校验 → 同步等待外部服务
       ↘ 另一份接口文档 ↘ 前端再维护一份类型
```

FastAPI + Pydantic 推荐的链路是：

```text
Python 类型与 Pydantic 模型
        ├──> 运行时输入/输出校验
        ├──> OpenAPI / JSON Schema
        ├──> 编辑器与静态检查提示
        └──> 前端客户端或类型生成

async 路由 ──await──> 可等待的数据库 / ASR / LLM 客户端
```

这就是本课程选择 FastAPI 的核心理由：同一份类型化代码同时服务运行时、文档与协作，而异步路径能自然表达长时间的 I/O 等待。

## 逐层拆解：三项能力如何对应三条约束

### 异步支持：让等待期间仍能接待其他请求

Python 官方将 `asyncio` 定位为适合 I/O 密集和高层网络代码的并发基础。[^1] FastAPI 同时支持 `def` 和 `async def`：调用库提供可等待接口时使用 `async def` 与 `await`；依赖是阻塞式接口时可以保留普通 `def`。[^2]

```text
同步思路：请求 A 等待 ASR ─────────> 返回后才继续

异步思路：请求 A await ASR
                 ├──> 等待期间处理请求 B
                 └──> ASR 返回后恢复请求 A
```

需要明确三条边界：

- `async` 主要提高 I/O 等待期间的资源利用率，不会让 CPU 密集的音频计算自动并行。
- 只有底层调用支持异步，`await` 才能真正让出执行机会；把阻塞函数直接放进 `async def` 仍会阻塞事件循环。
- 是否获得收益要看端到端压测，而不是只看框架微基准。

因此本书把异步视为与 ASR、LLM、数据库调用相匹配的编程模型，而不是“所有函数都加 `async`”的格式要求。

### 自动文档：让契约从代码中生成

FastAPI 根据路径、参数、Pydantic 模型和响应声明生成 OpenAPI，并默认提供 Swagger UI 与 ReDoc。[^3] 这意味着字段增加、约束变化和响应模型调整会进入同一份机器可读契约。

自动生成并不等于“无需设计 API”。它只减少代码与文档的重复维护：资源命名、兼容性、状态码和版本策略仍然需要工程师判断。正确顺序是先设计契约，再让框架保证实现与文档来自同一来源。

### 类型与校验：让非法输入停在边界

Pydantic 模型把字段类型、默认值、长度、格式和自定义规则集中定义。请求到达时，FastAPI 先解析并验证；失败返回结构化 422，成功后业务代码拿到的是已经通过模型检查的对象。

这里也要区分两种“类型安全”：

- Python 类型标注配合编辑器和 `mypy`，主要在开发与提交前发现调用错误。
- Pydantic 在运行时处理来自 HTTP 的不可信数据，发现非法值并生成错误详情。

二者相互补充，却不能混为一谈。静态标注不会自动拒绝网络输入，运行时校验也不会证明业务逻辑一定正确。

## 可运行示例：一份模型贯通校验、异步与文档

下面的最小应用同时验证三项能力：异步路由等待一个模拟外部服务，Pydantic 在请求入口校验字段，OpenAPI 从同一份模型生成。整个过程使用 `TestClient` 在本地完成，不依赖真实 ASR 或网络。

文件 `examples/fastapi_choice_demo.py`：

```{code-cell} ipython3
import asyncio
from enum import Enum

from fastapi import FastAPI, HTTPException
from fastapi.testclient import TestClient
from pydantic import BaseModel, Field, field_validator

class TaskStatus(str, Enum):
    pending = "pending"
    done = "done"

class TaskCreate(BaseModel):
    task_id: str = Field(min_length=1, max_length=64, description="任务 ID")
    filename: str = Field(min_length=1, max_length=128, description="音频文件名")
    language: str = Field(
        default="zh",
        pattern=r"^[a-z]{2}(-[A-Z]{2})?$",
        description="BCP 47 风格的简化语言标签",
    )

    @field_validator("task_id")
    @classmethod
    def task_id_has_no_spaces(cls, value: str) -> str:
        if " " in value:
            raise ValueError("task_id must not contain spaces")
        return value

class TaskOut(BaseModel):
    id: str
    filename: str
    language: str
    status: TaskStatus

async def reserve_asr_slot() -> None:
    # 模拟可等待的外部 I/O；等待时事件循环可处理其他工作
    await asyncio.sleep(0)

tasks: dict[str, TaskOut] = {}
app = FastAPI(title="FastAPI Choice Demo", version="0.1.0")

@app.post("/api/tasks", response_model=TaskOut, tags=["tasks"])
async def create_task(payload: TaskCreate) -> TaskOut:
    if payload.task_id in tasks:
        raise HTTPException(status_code=409, detail="task already exists")
    await reserve_asr_slot()
    task = TaskOut(
        id=payload.task_id,
        filename=payload.filename,
        language=payload.language,
        status=TaskStatus.pending,
    )
    tasks[task.id] = task
    return task

client = TestClient(app)

created = client.post(
    "/api/tasks",
    json={"task_id": "t1", "filename": "meeting.wav", "language": "zh-CN"},
)
print("created:", created.status_code, created.json())
assert created.status_code == 200

invalid_id = client.post(
    "/api/tasks",
    json={"task_id": "bad id", "filename": "a.wav"},
)
print("invalid id:", invalid_id.status_code)
assert invalid_id.status_code == 422

invalid_language = client.post(
    "/api/tasks",
    json={"task_id": "t2", "filename": "a.wav", "language": "not-a-lang"},
)
print("invalid language:", invalid_language.status_code)
assert invalid_language.status_code == 422

schema = app.openapi()
task_schema = schema["components"]["schemas"]["TaskCreate"]
operation = schema["paths"]["/api/tasks"]["post"]

print("documented fields:", sorted(task_schema["properties"]))
print("operation tags:", operation["tags"])

assert task_schema["properties"]["task_id"]["maxLength"] == 64
assert operation["tags"] == ["tasks"]

# 预期输出：
# created: 200 {'id': 't1', 'filename': 'meeting.wav', 'language': 'zh-CN', 'status': 'pending'}
# invalid id: 422
# invalid language: 422
# documented fields: ['filename', 'language', 'task_id']
# operation tags: ['tasks']
```

逐段看每个声明在链路中的作用：

- `TaskCreate` 是请求契约；`Field` 与 `field_validator` 同时驱动运行时校验和 OpenAPI 字段描述。
- `TaskOut` 是响应契约；`response_model` 防止接口悄悄返回未声明结构。
- `async def create_task` 与 `await reserve_asr_slot()` 表达了“此处需要等待可异步 I/O”。
- `tags=["tasks"]` 与路径声明进入 OpenAPI，前端工具可以据此组织接口和生成客户端。
- `TestClient` 从使用者视角验证状态码与 JSON，不需要真的占用网络端口。

## 为什么不是 Django 或 Flask

现在可以给出带前提的结论：

- 如果课程核心是管理后台和传统 CRUD，Django 内置能力可能让整体成本更低。
- 如果只演示一个极小路由，且不需要模型、OpenAPI 与异步协作，Flask 会更直接。
- 当前课程需要串联 Python AI 生态、I/O 等待、前后端契约和类型校验，因此 FastAPI 把最多关键约束放在同一条代码链路中。

这不是“FastAPI 比另外两者更好”，而是“它与本项目约束的重合面积更大”。一旦约束变化，结论也必须允许变化。

回到快递中转站：异步支持让传送带等待海关时仍能处理别的包裹，Pydantic 像入口的尺寸与标签检查，OpenAPI 则是所有配送方共享的电子运单。三项能力单独看都不是魔法，组合起来却恰好覆盖了 MeetingToText 的主要协作成本。

框架选定之后，下一道问题不再是“用哪个工具”，而是“代码应该如何分工”。如果路由、业务和数据库仍写在同一个函数里，再合适的框架也会长成难以测试的面条。下一节将把 FastAPI 应用落到 Controller—Service—Repository 三层。
