# Python GIL 真相与适用场景

> 学完本节，你能回答：GIL 保护的是什么，为什么存在？它在 I/O 密集与 CPU 密集任务中的影响有何不同？何时该用 `threading`，何时该用 `multiprocessing` 或 C 扩展？

## 先动手：同一代码在 I/O 与 CPU 上的耗时为何相反

别先背锁的比喻，先看两组计时。第一组是 50 毫秒等待，第二组是纯 Python 循环，线程与进程的耗时对比会直接告诉你 GIL 何时是瓶颈。

```{code-cell} ipython3
import time
import threading

def io_wait(n: int = 4, delay: float = 0.05) -> float:
    t0 = time.perf_counter()
    for _ in range(n):
        time.sleep(delay)
    return time.perf_counter() - t0

def threaded_io(n: int = 4, delay: float = 0.05) -> tuple[float, list[str]]:
    results: list[str] = []
    threads: list[threading.Thread] = []
    def _task(tid: int):
        time.sleep(delay)
        results.append(f"done-{tid}")
    t0 = time.perf_counter()
    for i in range(n):
        th = threading.Thread(target=_task, args=(i,))
        threads.append(th)
        th.start()
    for th in threads:
        th.join()
    elapsed = time.perf_counter() - t0
    return elapsed, sorted(results)

t_serial = io_wait(4, 0.05)
print(f"serial I/O elapsed: {t_serial:.3f}s")
assert 0.15 < t_serial < 0.40

t_thread, res = threaded_io(4, 0.05)
print(f"threaded I/O elapsed: {t_thread:.3f}s results: {res}")
assert res == ["done-0", "done-1", "done-2", "done-3"]
assert t_thread < t_serial
print("I/O 密集结论：线程可显著重叠等待")
# 预期输出:
# serial I/O elapsed: 0.20x s
# threaded I/O elapsed: 0.05x s
# I/O 密集结论：...
```

```{code-cell} ipython3
import time
import threading
import concurrent.futures

LOOP_N = 1_000_000

def cpu_work(n: int = LOOP_N) -> int:
    s = 0
    for i in range(n):
        s += i & 0xFF
    return s

expected = cpu_work(LOOP_N)
print("single cpu_work result:", expected)

t0 = time.perf_counter()
serial_results = [cpu_work(LOOP_N) for _ in range(4)]
t_serial = time.perf_counter() - t0
print(f"serial cpu elapsed: {t_serial:.3f}s")
assert serial_results == [expected] * 4

t0 = time.perf_counter()
thread_results: list[int] = []
threads: list[threading.Thread] = []
def _twork():
    thread_results.append(cpu_work(LOOP_N))
for _ in range(4):
    th = threading.Thread(target=_twork)
    threads.append(th)
    th.start()
for th in threads:
    th.join()
t_thread = time.perf_counter() - t0
print(f"threaded cpu elapsed: {t_thread:.3f}s")
assert sorted(thread_results) == sorted(serial_results)
assert t_thread >= t_serial * 0.6

t0 = time.perf_counter()
with concurrent.futures.ProcessPoolExecutor(max_workers=4) as ex:
    futs = [ex.submit(cpu_work, LOOP_N) for _ in range(4)]
    proc_results = sorted([f.result() for f in concurrent.futures.as_completed(futs)])
t_proc = time.perf_counter() - t0
print(f"process cpu elapsed: {t_proc:.3f}s")
assert proc_results == sorted(serial_results)

print(f"CPU 密集对照：串行 {t_serial:.3f}s | 线程 {t_thread:.3f}s | 进程 {t_proc:.3f}s")
if t_proc < t_serial:
    print("进程池在多核下加速了 CPU 密集任务")
else:
    print("当前核数有限，进程未显著快于串行，但结果一致即符合预期")
# 预期输出:
# single cpu_work result: ...
# serial cpu elapsed: ...
# threaded cpu elapsed: ...
# process cpu elapsed: ...
```

观测小结：I/O 任务线程耗时约为四分之一，CPU 任务线程耗时与串行相近，进程在多核下才可能加速。这就是 GIL 的边界。

## 从耗时命名原理：GIL 在保护什么

GIL 是一把全局解释器锁，保证同一时刻只有一个线程在执行 Python 字节码，保护的是解释器对 Python 对象引用计数与内存管理的正确性。它不是设计失误，而是用单把大锁换实现简洁与单线程性能的取舍。

关键推论可从计时中读出：

* 同一时刻只有一个线程在跑 Python 代码，所以纯 Python 循环的四线程难以快于串行
* 线程进入 `time.sleep` 或 `socket.recv` 或文件读写等阻塞调用时会释放锁，让别的线程得以执行，这就是 I/O 密集可用多线程的根因
* C 扩展如 NumPy 的数值循环可在 C 层自主释放锁，实现并行计算

不同语言有不同取舍，Java 用细粒度锁与 GC，Go 用协程与调度器，Python 在 3.13 引入可选的无 GIL 构建供评估，本书以 3.12 的经典 GIL 为基线。

## 何时受影响：选型一句话

I/O 密集等待多计算少，线程在等待时释放锁，可并发重叠，优先用线程或协程。CPU 密集纯 Python 循环受限，适合用 `multiprocessing` 或下沉到 C 或 NumPy。协程仍是单线程，CPU 密集的协程会阻塞事件循环。进程有启动与序列化开销，任务粒度太小反而更慢。

> 环境约定：本书面向 Linux，`threading` 与 `multiprocessing` 均为标准库，`multiprocessing` 需 `if __name__ == "__main__":` 守卫，示例中通过 `ProcessPoolExecutor` 避免该问题。

```bash
.venv/bin/python -c "import concurrent.futures; print('process pool ok')"
```
