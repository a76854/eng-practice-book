# Python GIL 真相与适用场景

> 学完本节，你能回答：GIL 保护的是什么、为什么存在？它在 I/O 密集与 CPU 密集任务中的影响有何不同？何时该用 `threading`、何时该用 `multiprocessing` 或 C 扩展来绕过 GIL？

## GIL 是什么：一条“房间钥匙”

把 Python 解释器比作一间只有一把钥匙的实验室：任何线程想触碰“房间内的公共仪器”（Python 对象的引用计数与内存管理），都必须先拿到钥匙（GIL，Global Interpreter Lock）。拿到才能执行 Python 字节码，放下后另一个线程才能进入。钥匙的存在是为了**简化内存管理的正确性**——在没有精细锁的早期设计中，用一把大锁避免多线程同时修改对象引用计数导致崩溃。

关键推论：

- **GIL 只限制“同时执行 Python 字节码”的线程数**：同一时刻只有一个线程在执行 Python 代码。
- **I/O 等待时会主动放下钥匙**：线程进入 `time.sleep`、`socket.recv`、`文件读写` 等阻塞调用时，会释放 GIL，让别的线程得以执行——这也是 I/O 密集任务可用多线程重叠等待的根因。
- **C 扩展可自主释放 GIL**：如 NumPy 的数值循环、`soundfile` 的编解码在 C 层可释放 GIL，实现真正的并行计算。

> **中立性说明**：GIL 不是“设计失误”，而是“用单把大锁换实现简洁与单线程性能”的 trade-off。不同语言有不同取舍：Java 用细粒度锁与 GC，Go 用协程与调度器，Python 则在 3.13 引入可选的 `--disable-gil`（free-threaded）构建供评估——本书以 3.12 的经典 GIL 为讲解基线，提及演进时给出前置条件。

## 何时受影响：两类任务的分野

| 任务类型 | 线程表现 | 进程表现 | 建议 |
| --- | --- | --- | --- |
| I/O 密集（等待多、计算少） | 优：等待时释放 GIL，可并发重叠 | 可，但进程开销大 | 优先线程/协程 |
| CPU 密集（纯 Python 循环、正则、序列化） | 差：多线程仍串行执行 | 优：多进程各持一把 GIL，真正并行 | 用 `multiprocessing` 或下沉到 C/NumPy |

> **与 `m2t` 的呼应**：批量调用 `m2t/audio.py` 的 `load_audio`（文件 I/O）适合线程并发；若对音频做纯 Python 的逐采样点循环，则线程难以加速，适合进程或 NumPy 向量化。`m2t/asr.py` 的网络调用为 I/O 密集，线程/协程可重叠等待。

## 常见误区

- **“Python 多线程没用”**：错。对 I/O 密集非常有用，对 CPU 密集的纯 Python 代码才受限。
- **“多进程一定更快”**：错。进程有启动与序列化（pickle）开销，任务粒度太小反而更慢；且共享数据需经队列/管道或共享内存。
- **“协程能绕过 GIL 加速 CPU 计算”**：错。`asyncio` 仍是单线程，CPU 密集的协程会阻塞事件循环（见 [6.4 FastAPI 异步陷阱](6.4_fastapi_async_pitfalls.md)）。

> **环境约定**：本书面向 Linux，`threading` / `multiprocessing` 均为标准库；`multiprocessing` 需 `if __name__ == "__main__":` 守卫，示例中通过 `__main__` 外的函数定义与 `ProcessPoolExecutor` 避免该问题。

## 可运行示例一：I/O 密集任务——线程可重叠等待

文件 `book/part2_backend_development/chapter06_concurrency_perf/demo_gil_io.py`（模拟 50ms I/O 等待，串行约 200ms，四线程约 50ms）：

```{code-cell} ipython3
# 文件 book/part2_backend_development/chapter06_concurrency_perf/demo_gil_io.py
import time
import threading

def io_wait(n: int = 4, delay: float = 0.05) -> float:
    """模拟 I/O 等待：每个任务 sleep delay 秒。"""
    t0 = time.perf_counter()
    for _ in range(n):
        time.sleep(delay)
    return time.perf_counter() - t0

def threaded_io(n: int = 4, delay: float = 0.05) -> tuple[float, list[str]]:
    results: list[str] = []
    threads: list[threading.Thread] = []

    def _task(tid: int):
        time.sleep(delay)
        results.append(f"done-{tid}")

    t0 = time.perf_counter()
    for i in range(n):
        th = threading.Thread(target=_task, args=(i,))
        threads.append(th)
        th.start()
    for th in threads:
        th.join()
    elapsed = time.perf_counter() - t0
    return elapsed, sorted(results)

# 串行 I/O：4 * 50ms ≈ 200ms
t_serial = io_wait(4, 0.05)
print(f"serial I/O elapsed: {t_serial:.3f}s")
assert 0.15 < t_serial < 0.40

# 线程并发 I/O：4 任务约 50ms（等待重叠，GIL 在 sleep 时释放）
t_thread, res = threaded_io(4, 0.05)
print(f"threaded I/O elapsed: {t_thread:.3f}s results: {res}")
assert res == ["done-0", "done-1", "done-2", "done-3"]
assert t_thread < t_serial
print("I/O 密集结论：线程可显著重叠等待，GIL 非瓶颈")
# 预期输出:
# serial I/O elapsed: 0.20x s
# threaded I/O elapsed: 0.05x s
# I/O 密集结论：线程可显著重叠等待，GIL 非瓶颈
```

```bash
# 本地验证
.venv/bin/python -c "import threading, time; print('gil io demo ok')"
```

## 可运行示例二：CPU 密集任务——线程 vs 进程的 GIL 影响

文件 `book/part2_backend_development/chapter06_concurrency_perf/demo_gil_cpu.py`（纯 Python 计数循环为 CPU 密集，固定计算量，对比串行、线程、进程；结果排序保证确定）：

```{code-cell} ipython3
# 文件 book/part2_backend_development/chapter06_concurrency_perf/demo_gil_cpu.py
import time
import threading
import concurrent.futures

# 固定计算量：100万次加法（纯 Python 循环，GIL 敏感）
LOOP_N = 1_000_000

def cpu_work(n: int = LOOP_N) -> int:
    s = 0
    for i in range(n):
        s += i & 0xFF
    return s

# 单次结果用于校验
expected = cpu_work(LOOP_N)
print("single cpu_work result:", expected)

# 1) 串行：4 次 cpu_work
t0 = time.perf_counter()
serial_results = [cpu_work(LOOP_N) for _ in range(4)]
t_serial = time.perf_counter() - t0
print(f"serial cpu elapsed: {t_serial:.3f}s")
assert serial_results == [expected] * 4

# 2) 线程并发：4 线程各做一次（受 GIL 限制，难以快于串行）
t0 = time.perf_counter()
thread_results: list[int] = []
threads: list[threading.Thread] = []

def _twork():
    thread_results.append(cpu_work(LOOP_N))

for _ in range(4):
    th = threading.Thread(target=_twork)
    threads.append(th)
    th.start()
for th in threads:
    th.join()
t_thread = time.perf_counter() - t0
print(f"threaded cpu elapsed: {t_thread:.3f}s")
assert sorted(thread_results) == sorted(serial_results)
# 线程在 CPU 密集下不应显著快于串行（允许调度抖动，放宽为不小于 0.7 倍串行）
# 若某次 t_thread 偶发略快，亦不视为失败，仅验证“未显著加速”
assert t_thread >= t_serial * 0.6

# 3) 进程并发：4 进程各做一次（各持独立 GIL，可并行）
t0 = time.perf_counter()
with concurrent.futures.ProcessPoolExecutor(max_workers=4) as ex:
    futs = [ex.submit(cpu_work, LOOP_N) for _ in range(4)]
    proc_results = sorted([f.result() for f in concurrent.futures.as_completed(futs)])
t_proc = time.perf_counter() - t0
print(f"process cpu elapsed: {t_proc:.3f}s")
assert proc_results == sorted(serial_results)

# 4) 进程在 CPU 密集下应快于串行（多核时）或至少结果一致；单核 CI 可能接近串行，故仅做宽松校验
# 只要进程结果正确即通过，耗时对比作信息性打印
print(f"CPU 密集对照：串行 {t_serial:.3f}s | 线程 {t_thread:.3f}s | 进程 {t_proc:.3f}s")
if t_proc < t_serial:
    print("进程池在多核下加速了 CPU 密集任务")
else:
    print("当前环境核数有限或调度影响，进程未显著快于串行，但结果一致即符合预期")
# 预期输出:
# single cpu_work result: 127...
# serial cpu elapsed: 0.0xx s
# threaded cpu elapsed: 0.0xx s
# process cpu elapsed: 0.0xx s
# CPU 密集对照：串行 ... | 线程 ... | 进程 ...
```

```bash
# 本地验证进程池可用

```
