# 性能剖析方法论

> 学完本节，你能回答：为什么“感觉变快了”不算优化？如何用 `cProfile`、`timeit`、行级剖析思路与数据库查询分析定位真正的热点？如何用“度量—定位—优化—回归”的闭环保证优化可验证、可回退？

## 为什么先度量再优化：避免“拍脑袋加速”

新手优化常犯三错：① 未度量就重构，结果把非瓶颈的代码变复杂；② 只测一次就下结论，被 JIT、缓存、GC 抖动误导；③ 优化后不回归，引入正确性或可维护性回退。工程化的性能工作必须是**闭环**：

1. **度量（Measure）**：用剖析器找到“时间花在哪”。
2. **定位（Locate）**：区分 CPU、I/O、锁、数据库热点。
3. **优化（Optimize）**：针对热点做最小改动，保留可回退路径。
4. **回归（Regress）**：用同一基准复测，确认提升且无回退。

> **类比体检**：不做血检就吃药是冒险；`cProfile` 就是“血常规”，`timeit` 是“血压计”，数据库的 `EXPLAIN QUERY PLAN` 是“影像学”。先查清病灶，再决定动哪一刀。

## 工具箱：四把尺子

| 工具 | 回答的问题 | 粒度 | 适用 |
| --- | --- | --- | --- |
| `cProfile` | 哪个函数最耗时、被调多少次 | 函数级 | 快速定位热点函数 |
| `timeit` | 一小段代码的稳定耗时 | 语句级 | 微基准、对比两种写法 |
| 行级剖析思路（`line_profiler` 思想） | 热点函数内哪一行最耗时 | 行级 | 精细优化，需额外安装；本书用 `cProfile` + 手动计时模拟思路 |
| 数据库 `EXPLAIN QUERY PLAN` | 查询是否走索引、是否全表扫描 | 查询计划 | 定位 N+1 与缺索引 |

> **中立性说明**：`cProfile` 带额外开销（约 10–20%），不适合线上采样；线上可用 `py-spy` 等采样型剖析器。`line_profiler` 需 `pip install line_profiler`，本书为保持“标准库 only”用 `cProfile` + `timeit` 组合演示等价思路，提及 `line_profiler` 时给出安装前置条件。

> **环境约定**：本书面向 Linux，`cProfile` / `timeit` / `sqlite3` 均为标准库，在 Linux 环境行为一致；涉及文件路径用 `pathlib.Path`，虚拟环境激活差异同 [6.1](6.1_concurrency_parallel_async.md)。

## 可运行示例一：`cProfile` 定位热点 + `pstats` 排序

文件 `book/part2_backend_development/chapter06_concurrency_perf/demo_cprofile.py`（构造“快函数 + 慢函数”组合，用 `cProfile` 剖析并按累计时间排序）：

```{code-cell} ipython3
# 确定性剖析：仅断言调用次数与结构，不依赖 wall-clock 计时，避免 CI 抖动
import cProfile
import pstats

def fast_path(n: int = 1000) -> int:
    s = 0
    for i in range(n):
        s += i & 0xFF
    return s

def slow_path(n: int = 200_000) -> int:
    # 故意更重的循环，模拟热点
    s = 0
    for i in range(n):
        s += i & 0xFF
    return s

def workload():
    # 模拟一次请求的处理：快路径多次 + 慢路径一次
    for _ in range(5):
        fast_path(1000)
    slow_path(200_000)
    for _ in range(5):
        fast_path(1000)

# 用 cProfile 剖析 workload
prof = cProfile.Profile()
prof.enable()
workload()
prof.disable()

# 确定性输出：按函数名排序的 (function, call-count) 对，不打印 tottime/cumtime
stats = pstats.Stats(prof)
# stats.stats: {(filename, lineno, func_name): (cc, nc, tt, ct, callers)}
pairs = sorted(
    [(func[2], stat[1]) for func, stat in stats.stats.items() if func[2] in ("workload", "fast_path", "slow_path")],
    key=lambda x: x[0],
)
for name, ncalls in pairs:
    print(f"{name}: {ncalls}")
# 结构断言：调用次数确定且与预期一致（不依赖耗时排序）
expected = {"slow_path": 1, "workload": 1, "fast_path": 10}
for name, ncalls in pairs:
    assert expected[name] == ncalls, f"{name} ncalls {ncalls} != {expected[name]}"
assert "slow_path" in [n for n, _ in pairs]
assert "fast_path" in [n for n, _ in pairs]
assert "workload" in [n for n, _ in pairs]
print("cProfile 剖析通过：热点函数与调用次数均可度量（确定性输出）")
# 预期输出（确定性，不含计时）:
# fast_path: 10
# slow_path: 1
# workload: 1
# cProfile 剖析通过：热点函数与调用次数均可度量（确定性输出）
```

```bash
# 本地验证
.venv/bin/python -c "import cProfile, pstats; print('cProfile ok')"
```

## 可运行示例二：`timeit` 微基准——稳定对比两种写法

文件 `book/part2_backend_development/chapter06_concurrency_perf/demo_timeit.py`（对比“字符串拼接的两种写法”与“循环的两种写法”，用 `timeit` 多次重复取均值，避免单次抖动）：

```{code-cell} ipython3
import timeit

# 对比 1：列表 join vs 循环 += 拼接（join 通常更快）
setup_join = "parts = ['a', 'b', 'c'] * 100"
stmt_join = "''.join(parts)"
stmt_plus = "s=''; [exec('s+=p', {'s': s, 'p': p}) for p in parts]"
# 更公平的 += 对比：用显式循环
def plus_loop():
    s = ""
    parts = ["a", "b", "c"] * 100
    for p in parts:
        s += p
    return s

def join_method():
    parts = ["a", "b", "c"] * 100
    return "".join(parts)

# timeit 自动选择合适重复次数，取最短一次作为稳定估计（仅作信息性打印，不强断言耗时大小）
t_join = min(timeit.repeat("''.join(parts)", setup="parts = ['a','b','c']*100", repeat=5, number=1000))
t_plus = min(timeit.repeat(plus_loop, repeat=5, number=1000))
# 计时값本身不确定，仅校验为正数且可复现结构；快慢对比作信息性打印
assert t_join > 0 and t_plus > 0
print(f"join: {t_join:.6f}s (best of 5)")
print(f"plus loop: {t_plus:.6f}s (best of 5)")
if t_join < t_plus:
    print("timeit 结论：''.join 快于循环 +=（符合预期）")
else:
    print(f"本次测量 join 未快于 += (join={t_join:.6f}s, plus={t_plus:.6f}s)，属正常抖动，功能即通过")
# 结构断言：两者功能等价（不依赖耗时排序）
assert plus_loop() == join_method()
assert len(plus_loop()) == 300  # 结构断言：长度确定（3*100）

# 对比 2：推导式 vs 显式循环追加（推导式通常更快）
def comp():
    return [i & 0xFF for i in range(1000)]

def loop_append():
    out = []
    for i in range(1000):
        out.append(i & 0xFF)
    return out

t_comp = min(timeit.repeat(comp, repeat=5, number=2000))
t_append = min(timeit.repeat(loop_append, repeat=5, number=2000))
print(f"comprehension: {t_comp:.6f}s")
print(f"append loop: {t_append:.6f}s")
assert comp() == loop_append()
# 推导式通常快于显式 append（C 层循环），但差异不大时不做强断言，仅作信息性打印
if t_comp < t_append:
    print("推导式快于显式 append（符合预期）")
else:
    print("本次测量推导式未显著快于 append，属正常抖动，功能一致即通过")
print("timeit 微基准通过：可稳定对比两种写法的耗时")
# 预期输出:
# join: 0.000x s (best of 5)
# plus loop: 0.00x s (best of 5)
# timeit 结论：''.join 快于循环 +=
# comprehension: ...
# append loop: ...
```

```bash
# 本地验证
.venv/bin/python -c "import timeit; print(timeit.timeit('1+1', number=1000))"
```

## 可运行示例三：数据库查询剖析——`EXPLAIN QUERY PLAN` 找缺失索引

文件 `book/part2_backend_development/chapter06_concurrency_perf/demo_db_profile.py`（用 `sqlite3` 建表，对比“无索引的全表扫描”与“有索引的索引扫描”，并演示 N+1 查询的剖析思路）：

```{code-cell} ipython3
import sqlite3
import time

conn = sqlite3.connect(":memory:")
conn.execute("PRAGMA journal_mode=WAL")
# 建表：模拟任务表（与 m2t/store.py 结构呼应）
conn.execute("""
CREATE TABLE tasks (
    id TEXT PRIMARY KEY,
    filename TEXT NOT NULL,
    status TEXT NOT NULL,
    created_at TEXT NOT NULL
)
""")
conn.commit()

# 写入 500 行数据
for i in range(500):
    conn.execute(
        "INSERT INTO tasks (id, filename, status, created_at) VALUES (?, ?, ?, datetime('now'))",
        (f"t{i:04d}", f"file_{i%10}.wav", "pending" if i % 2 == 0 else "done")
    )
conn.commit()

# 1) 无索引时的查询计划：按 status 过滤（无索引 → SCAN）
plan_before = conn.execute("EXPLAIN QUERY PLAN SELECT * FROM tasks WHERE status='pending'").fetchall()
print("plan before index:", plan_before)
# 应包含 SCAN 字样（全表扫描）
assert any("SCAN" in str(row) for row in plan_before)

# 2) 建索引后复测：应转为 SEARCH/USING INDEX
conn.execute("CREATE INDEX idx_tasks_status ON tasks(status)")
plan_after = conn.execute("EXPLAIN QUERY PLAN SELECT * FROM tasks WHERE status='pending'").fetchall()
print("plan after index:", plan_after)
assert any("SEARCH" in str(row) or "INDEX" in str(row) for row in plan_after)

# 3) 计时对比：索引前后各执行 200 次查询，取均值（排序保证确定，仅对比相对快慢）
def bench_query(n: int = 200) -> float:
    t0 = time.perf_counter()
    for _ in range(n):
        conn.execute("SELECT * FROM tasks WHERE status='pending'").fetchall()
    return time.perf_counter() - t0

# 注意：500 行数据量小，索引提升可能不显著，仅作演示；重点是 EXPLAIN 的定性判断
t_with_index = bench_query(200)
print(f"with index elapsed (200 queries): {t_with_index:.4f}s")

# 4) N+1 剖析思路：模拟“先查任务列表再逐条查详情”的 N+1 模式 vs 单条 JOIN/IN
# N+1 模式（反例）：1 次列表查询 + N 次单条查询
t0 = time.perf_counter()
ids = [r[0] for r in conn.execute("SELECT id FROM tasks LIMIT 20").fetchall()]
for tid in ids:
    conn.execute("SELECT * FROM tasks WHERE id=?", (tid,)).fetchone()
t_n1 = time.perf_counter() - t0

# 优化后：单条 IN 查询
t0 = time.perf_counter()
placeholders = ",".join("?" for _ in ids)
conn.execute(f"SELECT * FROM tasks WHERE id IN ({placeholders})", ids).fetchall()
t_batched = time.perf_counter() - t0

print(f"N+1 elapsed: {t_n1:.4f}s vs batched IN: {t_batched:.4f}s")
# 批量查询通常快于 N+1，但计时受抖动影响，仅作信息性打印，不强断言时长
assert t_n1 >= 0 and t_batched >= 0
if t_batched <= t_n1 * 1.5:
    print("批量查询快于/接近 N+1（符合预期）")
else:
    print(f"本次测量批量未显著快于 N+1 (batched={t_batched:.4f}s, n1={t_n1:.4f}s)，属正常抖动，EXPLAIN 定性判断已通过")
print("DB 剖析通过：EXPLAIN 可识别 SCAN vs SEARCH，批量查询可缓解 N+1")

conn.close()
# 预期输出:
# plan before index: [(..., 'SCAN tasks', ...)]
# plan after index: [(..., 'SEARCH tasks USING INDEX idx_tasks_status', ...)]
# with index elapsed (200 queries): 0.0xxx s
# N+1 elapsed: 0.00x s vs batched IN: 0.00x s
# DB 剖析通过：...
```

```bash
# 本地验证

```

> **优化闭环 checklist**：① 先用 `cProfile` 找热点函数，再用 `timeit` 对比热点内的两种写法，最后用 `EXPLAIN` 检查数据库侧是否缺索引；② 每次优化只改一处，保留 `git stash` 可回退；③ 用同一基准脚本复测，`assert` 保证正确性，耗时对比作信息性打印而非强断言，避免 CI 抖动。与 [第5章 索引与锁](../chapter05_persistence_sql_orm/5.1_relational_db_principles.md) 的索引代价相互印证——索引加速读但拖慢写，需权衡。
