# 异常处理与全局响应

学完本节，你能回答：

- 为什么每个路由各自 `try/except`，最终会让前端无法可靠地处理失败？
- 统一响应信封为什么要同时保留 HTTP 状态码与稳定的 JSON 形状？
- FastAPI 如何把校验错误、业务错误和未知异常收敛到同一对外契约？

> 银行柜台不会因为业务不同就换一套回执格式：取款失败、账户冻结、系统维护虽然原因不同，客户都应该看得出“是否成功、失败原因、下一步怎么办”。如果每个窗口随意写纸条，有的只写“失败”，有的给一串内部编号，有的直接把后台报错甩给客户，柜台人员和客户都会无所适从。API 的错误响应也是一种回执；失败的统一性，和成功的统一性同样重要。

接口数量少时，路由里手写 `return {"detail": ...}` 或 `try/except` 很快。接口、错误来源和调用方一多，格式分叉就不可避免：FastAPI 默认把请求校验错误表示为 `detail` 数组，业务冲突可能返回文本，鉴权失败又可能带专用 Header。前端不得不根据每个端点猜解析方式。

## 每个路由各写一份错误：缺了什么

**1. 调用方没有稳定的失败入口**

同一个前端请求封装必须面对多种形状：

```text
{"detail": "not found"}
{"ok": false, "reason": "duplicate"}
{"code": 422, "errors": [...]}
```

接口越多，分支越多；任何一个新路由忘记遵循约定，错误就会在联调时重新出现。

**2. 错误翻译散落在业务代码中**

若 Service 直接构造 `HTTPException` 或信封 JSON，业务规则就被绑定到 FastAPI；若每个 Controller 都负责包装 `code/data/msg`，同样的转换逻辑又会复制到十几个路由中。

**3. 未知异常容易泄露内部细节**

开发期的异常信息对排错有帮助，生产环境直接返回数据库路径、SQL 或堆栈则会泄露实现细节。没有一个统一兜底出口时，团队很难保证每条异常路径都被安全处理。

这些问题的共同根因是：**错误的来源、HTTP 语义和对外 JSON 表示没有经过统一翻译**。每层都在“自己解释自己”，调用方就只能分别适配。

### 从散落的纸条到标准化回执

统一响应并不是让所有错误都返回 `200`，也不是用一个 `code` 取代 HTTP 状态码。它的目标是：**保留 HTTP 的通用结果语义，同时为前端提供稳定、可预测的响应形状**。

## 为什么需要统一响应

没有统一信封的 API，就像每个窗口用不同格式的回执——有的返回 `{"ok": true}`，有的返回 `{"code": 0}`，有的直接抛 `{"detail": "not found"}`。前端不得不为每个接口写一套错误分支，日志与监控也无法按统一字段聚合。

更隐蔽的是**错误来源的多样性**：Pydantic 校验失败（422）、业务规则冲突（409）、资源不存在（404）、未捕获异常（500）、鉴权失败（401）——若各路由自行 `return`，格式必然漂移。

统一响应的两个目标：

1. **成功信封**：`{"code": 0, "data": {...}, "msg": "ok"}` —— `code` 为业务码（0 表成功），`data` 为载荷，`msg` 为可读信息。HTTP 状态码仍保留（201/200/204），但业务码让前端可做“成功但需提示”的细粒度分支。
2. **失败信封**：`{"code": <业务码>, "data": null, "msg": "<可读信息>"}` —— 无论 404/409/422/500，前端按同一形状解析与提示。

> **选型中立性**：信封形态无绝对标准。有的团队用 `{"success": true, "data": ...}`，有的用 `{"error": {...}}`。本书选用 `code/data/msg` 是因为在 MeetingToText 的前端（Vue 3 + Axios 拦截器）中可一行判分：`if (res.data.code !== 0) showError(res.data.msg)`。关键是**全链路统一**，而非字段名本身。

## 全局异常处理：把“散落的 try”收敛到一处

FastAPI 提供两类全局处理器：

- `@app.exception_handler(StarletteHTTPException)` —— 捕获 FastAPI 主动抛出的 HTTP 错误，也覆盖路由匹配产生的 404 等框架错误，统一包装为信封，并保留原状态码与响应 Header。
- `@app.exception_handler(RequestValidationError)` —— 捕获 Pydantic 校验失败（422），将原本的 `{"detail": [...]}` 结构转为同一信封，避免前端对 422 单独分支。
- `@app.exception_handler(Exception)` —— 兜底未捕获异常，转为 `500 + code=500` 的信封并记录日志，避免堆栈泄露。

> **安全提示**：500 响应的 `msg` 不应泄露堆栈与内部路径，仅返回“内部错误，请稍后重试”并附 `request_id` 供服务端追踪，详见 [第10章 错误边界](../../part4_advanced_engineering/chapter10_robustness_security/index.md)。

三者的协作让路由函数只需**抛语义化异常**，无需关心“如何包装”——契约在边界统一收敛，这与 [第3章的分层思想](../chapter03_backend_essence/3.5_layered_architecture.md) 一致：Service 抛 `ValueError`，Controller 转为 `HTTPException`，全局处理器转为信封。

> **环境约定**：本书面向 Linux，异常处理与响应格式与平台无关；若涉及错误日志的本地落盘，统一用 `pathlib.Path` 处理分隔符差异。

## 可运行示例：统一信封 + 全局异常处理器

示例（演示成功/失败信封与三类异常的统一收敛，`TestClient` 本地验证，无网络）：

```{code-cell} ipython3
import tempfile, pathlib
from typing import Any

from fastapi import FastAPI, HTTPException, Request, status
from fastapi.exceptions import RequestValidationError
from fastapi.responses import JSONResponse
from fastapi.testclient import TestClient
from pydantic import BaseModel, Field
from starlette.exceptions import HTTPException as StarletteHTTPException
from m2t.store import TaskStore

tmpdir = tempfile.TemporaryDirectory()
db_path = pathlib.Path(tmpdir.name) / "envelope.db"
store = TaskStore(db_path)

# --- 信封模型：成功与失败的统一形状 ---
class Envelope(BaseModel):
    code: int = Field(description="业务码，0 为成功，非 0 为失败")
    data: Any | None = Field(default=None, description="载荷，失败时为 null")
    msg: str = Field(description="可读信息")

def ok(data: Any = None, msg: str = "ok") -> dict:
    return Envelope(code=0, data=data, msg=msg).model_dump()

def fail(code: int, msg: str, http_status: int = 200) -> JSONResponse:
    # 教学约定：HTTP 状态码仍区分 200/4xx/5xx，但 Body 的 code 供前端业务分支
    # 部分团队选择“HTTP 始终 200，靠 code 区分”，本书保留 HTTP 语义以便网关与监控可按状态码聚合
    return JSONResponse(status_code=http_status, content=Envelope(code=code, data=None, msg=msg).model_dump())

# --- 契约 ---
class TaskCreateIn(BaseModel):
    task_id: str = Field(min_length=1, max_length=64)
    filename: str = Field(min_length=1)

app = FastAPI(title="Envelope Demo")

# --- 全局异常处理器：三类收敛 ---
@app.exception_handler(StarletteHTTPException)
async def http_exception_handler(request: Request, exc: StarletteHTTPException):
    # 保留原状态码与 Header，Body 统一为信封；避免丢失 WWW-Authenticate 等协议信息
    return JSONResponse(
        status_code=exc.status_code,
        content=Envelope(code=exc.status_code, data=None, msg=str(exc.detail)).model_dump(),
        headers=exc.headers,
    )

@app.exception_handler(RequestValidationError)
async def validation_exception_handler(request: Request, exc: RequestValidationError):
    # Pydantic 校验失败：422 收敛为同一信封，msg 拼接首个错误信息
    first = exc.errors()[0] if exc.errors() else {"msg": "validation error"}
    loc = ".".join(str(x) for x in first.get("loc", []))
    msg = f"validation failed at {loc}: {first.get('msg', '')}"
    return JSONResponse(status_code=422, content=Envelope(code=422, data=None, msg=msg).model_dump())

@app.exception_handler(Exception)
async def unhandled_exception_handler(request: Request, exc: Exception):
    # 兜底：未捕获异常 → 500，不泄露堆栈
    return JSONResponse(status_code=500, content=Envelope(code=500, data=None, msg="internal error, please retry").model_dump())

# --- 路由：只需抛语义化异常，无需手写信封 ---
@app.post("/tasks", status_code=status.HTTP_201_CREATED)
def create_task(payload: TaskCreateIn):
    if store.get(payload.task_id) is not None:
        raise HTTPException(status_code=409, detail=f"task {payload.task_id} already exists")
    store.create(payload.task_id, payload.filename)
    row = store.get(payload.task_id)
    assert row is not None
    return ok(data={"id": row["id"], "filename": row["filename"], "status": row["status"]}, msg="created")

@app.get("/tasks/{task_id}")
def get_task(task_id: str):
    row = store.get(task_id)
    if row is None:
        raise HTTPException(status_code=404, detail="task not found")
    return ok(data={"id": row["id"], "filename": row["filename"], "status": row["status"]})

@app.get("/boom")
def boom():
    # 演示兜底处理器：未捕获异常 → 500 信封
    raise RuntimeError("unexpected boom")

# --- 本地验证：用 TestClient 演示“所有错误同一形状” ---
client = TestClient(app, raise_server_exceptions=False)

# 1) 成功：201 + 信封 code=0
r1 = client.post("/tasks", json={"task_id": "e1", "filename": "meeting.wav"})
print("create e1:", r1.status_code, r1.json())
assert r1.status_code == 201
assert r1.json()["code"] == 0
assert r1.json()["data"]["id"] == "e1"

# 2) 成功查询：200 + 信封
r2 = client.get("/tasks/e1")
print("get e1:", r2.json())
assert r2.json()["code"] == 0
assert r2.json()["data"]["filename"] == "meeting.wav"

# 3) 业务冲突：409 + 同一信封（code=409）
r3 = client.post("/tasks", json={"task_id": "e1", "filename": "dup.wav"})
print("duplicate:", r3.status_code, r3.json())
assert r3.status_code == 409
assert r3.json()["code"] == 409
assert r3.json()["data"] is None

# 4) 资源不存在：404 + 同一信封
r4 = client.get("/tasks/missing_xyz")
print("not found:", r4.status_code, r4.json())
assert r4.status_code == 404
assert r4.json()["code"] == 404

# 5) 校验失败：422 + 同一信封（经 RequestValidationError 处理器收敛）
r5 = client.post("/tasks", json={"task_id": "", "filename": "x.wav"})
print("validation:", r5.status_code, r5.json())
assert r5.status_code == 422
assert r5.json()["code"] == 422
assert "validation failed" in r5.json()["msg"]

# 6) 未捕获异常：500 + 同一信封（经 Exception 兜底）
r6 = client.get("/boom")
print("boom:", r6.status_code, r6.json())
assert r6.status_code == 500
assert r6.json()["code"] == 500
assert r6.json()["data"] is None

# 7) 框架路由错误：未注册路径的 404 也进入同一处理器
r7 = client.get("/missing-route")
print("missing route:", r7.status_code, r7.json())
assert r7.status_code == 404
assert r7.json()["code"] == 404

# 8) 前端视角：所有响应均可按同一分支处理
for r in [r1, r2, r3, r4, r5, r6, r7]:
    body = r.json()
    assert "code" in body and "data" in body and "msg" in body
print("前端可按同一形状处理所有响应：code/data/msg")

tmpdir.cleanup()
print("信封校验通过：成功/校验/业务/兜底均收敛到同一契约")
# 预期输出:
# create e1: 201 {'code': 0, 'data': {'id': 'e1', ...}, 'msg': 'created'}
# get e1: {'code': 0, 'data': {'id': 'e1', ...}, 'msg': 'ok'}
# duplicate: 409 {'code': 409, 'data': None, 'msg': 'task e1 already exists'}
# not found: 404 {'code': 404, ...}
# validation: 422 {'code': 422, ...}
# boom: 500 {'code': 500, ...}
# missing route: 404 {'code': 404, ...}
# 前端可按同一形状处理所有响应：code/data/msg
# 信封校验通过：成功/校验/业务/兜底均收敛到同一契约
```

示例中的三类处理器正好对应三种错误来源：

| 错误来源 | 应由谁表达 | 对外 HTTP 结果 | 全局处理器负责什么 |
|---|---|---|---|
| 请求字段不合法 | Pydantic / FastAPI | `422` | 将校验详情翻译为统一信封 |
| 资源不存在、冲突、无权限 | Controller 抛语义化 HTTP 错误 | `404` / `409` / `401` 等 | 保留状态码并统一 Body |
| 未预期的程序故障 | 任意层可能产生 | `500` | 隐藏内部细节、保留追踪线索并记录日志 |

逐层看责任边界：Service 应该报告“任务已存在”这样的业务事实；Controller 决定它映射成 `409 Conflict`；全局异常处理器决定所有 `409` 的 JSON 都长成同一形状。这样，业务规则不会认识 HTTP，路由不会反复拼信封，前端也不必为每一种失败发明新的解析分支。

统一信封也有边界：下载文件、流式响应、第三方 Webhook 和 `204 No Content` 不一定适合包进 `code/data/msg`。关键不是把每一种响应强行套模板，而是让同一类面向前端的 JSON API 保持一致，并清楚记录例外。

回到银行回执的比喻：状态码像窗口的处理结果标签，`code/data/msg` 则是每张回执固定的栏目。客户既能从标签判断是成功、冲突还是系统故障，也能始终从同一个位置读取可展示的信息。下一节将把这份固定回执和路由模型提升为 OpenAPI 契约，并用测试守住它不会悄悄漂移。

> **与前端协作的衔接**：统一信封让前端的 Axios 拦截器可一行收敛——`if (res.data.code !== 0) throw new ApiError(res.data.msg)`，无需为每个接口写单独的错误分支。这一模式将在 [第8章 状态设计](../../part3_frontend_collaboration/chapter08_vue3_core/index.md) 的 Pinia + 请求封装中复用。
