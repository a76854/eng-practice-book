# HTTP 协议精髓

学完本节，你能回答：

- 为什么 `GET`、`POST`、`PUT` 和 `DELETE` 不能只按“都能传数据”来互换？
- 为什么幂等性会直接影响前端、网关和用户能否安全重试？
- 状态码与 Header 分别如何让调用方知道结果、错误归属和追踪线索？

> 邮寄包裹时，寄件人不会只在箱子上写一句“请处理”。收件地址、寄送方式、是否签收、运单号和易碎标志分别告诉邮局不同的事情：包裹送到哪里、该怎么处理、是否已经完成、出了问题找谁追踪。HTTP 请求也是一张这样的运单。URL 与请求体只是包裹本身；方法、状态码和 Header 才让浏览器、网关、缓存和日志系统知道该如何协作。

把 HTTP 当成“发送 JSON 的管道”时，接口通常仍然能跑：所有操作都 `POST`，成功一律 `200`，失败就把文字塞进 Body。问题会在网络超时、重复点击、网关重试和前后端联调时集中出现——调用方拿到了一段 JSON，却不知道它是否真的成功、能否重发、资源在哪里、该如何定位错误。

## 只让接口“能返回 JSON”：缺了什么

**1. 方法丢失业务意图**

如果创建、查询、更新、删除都使用 `POST /api/action`，基础设施只看见“一个可能改变状态的请求”。缓存不知道哪些请求可复用，重试器也不知道超时后能否安全重发。

```text
POST /api/action {"action": "deleteTask", "id": "t1"}
```

动作被藏进 Body，HTTP 层无法理解它是读取、创建还是删除。

**2. 成功与失败只靠阅读 Body 猜测**

若重复创建仍返回 `200`，只是把 `{"ok": false}` 放在响应里，前端、监控和网关就必须各自解析一遍业务字段，才能知道这其实是冲突而不是成功。

```text
200 {"ok": false, "message": "already exists"}
```

状态码的语义被抹平后，错误统计、告警和客户端分支都会变得脆弱。

**3. 追踪与协商信息无处安放**

请求编号、认证信息、缓存标记和客户端期望的格式都不属于业务 JSON。把它们混进请求体，会污染领域模型；完全不传，又会让跨服务排障像在没有运单号的仓库里找一件包裹。

这些问题的共同根因是：**HTTP 的协议语义没有被当作契约的一部分，而只被当成承载 JSON 的外壳**。

### 从“发一段数据”到“交付一份可理解的请求”

上述问题——动作含义不清、结果无法判断、追踪信息缺失——看似属于路由、错误处理和日志，但解决方案是一致的：**让方法表达意图，让状态码表达结果，让 Header 承载正交元数据**。

下面的示例先用请求结果把这三层语义跑出来。重点不是背表，而是观察重复请求和不同结果时，协议如何替调用方做出明确说明。

```{code-cell} ipython3
import tempfile, pathlib

from fastapi import FastAPI, Header, HTTPException, Response, status
from fastapi.testclient import TestClient
from pydantic import BaseModel, Field
from m2t.store import TaskStore

tmpdir = tempfile.TemporaryDirectory()
db_path = pathlib.Path(tmpdir.name) / "http_semantics.db"
store = TaskStore(db_path)

class TaskCreateIn(BaseModel):
    task_id: str = Field(min_length=1, max_length=64, description="任务 ID")
    filename: str = Field(min_length=1, description="文件名")

class TaskOut(BaseModel):
    id: str
    filename: str
    status: str

app = FastAPI(title="HTTP Semantics Demo")

put_counter = {"count": 0}

@app.get("/tasks/{task_id}", response_model=TaskOut)
def get_task(task_id: str, x_request_id: str | None = Header(default=None)):
    row = store.get(task_id)
    if row is None:
        raise HTTPException(status_code=404, detail="task not found")
    return TaskOut(id=row["id"], filename=row["filename"], status=row["status"])

@app.post("/tasks", response_model=TaskOut, status_code=status.HTTP_201_CREATED)
def create_task(payload: TaskCreateIn, response: Response):
    if store.get(payload.task_id) is not None:
        raise HTTPException(status_code=409, detail=f"task {payload.task_id} already exists")
    store.create(payload.task_id, payload.filename)
    row = store.get(payload.task_id)
    assert row is not None
    response.headers["Location"] = f"/tasks/{payload.task_id}"
    return TaskOut(id=row["id"], filename=row["filename"], status=row["status"])

@app.put("/tasks/{task_id}", response_model=TaskOut)
def put_task(task_id: str, payload: TaskCreateIn):
    put_counter["count"] += 1
    existing = store.get(task_id)
    if existing is None:
        store.create(task_id, payload.filename)
    else:
        store.update(task_id, filename=payload.filename)
    row = store.get(task_id)
    assert row is not None
    return TaskOut(id=row["id"], filename=row["filename"], status=row["status"])

@app.delete("/tasks/{task_id}", status_code=status.HTTP_204_NO_CONTENT)
def delete_task(task_id: str):
    row = store.get(task_id)
    if row is None:
        return Response(status_code=status.HTTP_204_NO_CONTENT)
    store.delete(task_id)
    return Response(status_code=status.HTTP_204_NO_CONTENT)

@app.get("/healthz")
def healthz():
    return {"status": "ok"}

client = TestClient(app)

# 1) POST 创建，观测 201 与 Location
r1 = client.post("/tasks", json={"task_id": "t1", "filename": "meeting.wav"})
print("POST t1:", r1.status_code, r1.headers.get("location"), r1.json())
assert r1.status_code == 201
assert r1.headers["location"] == "/tasks/t1"

# 2) POST 重复，观测 409 而非静默覆盖
r2 = client.post("/tasks", json={"task_id": "t1", "filename": "meeting.wav"})
print("POST duplicate:", r2.status_code, r2.json()["detail"])
assert r2.status_code == 409

# 3) GET 存在 200，不存在 404
r3 = client.get("/tasks/t1")
print("GET t1:", r3.status_code, r3.json())
assert r3.status_code == 200
r4 = client.get("/tasks/missing")
print("GET missing:", r4.status_code)
assert r4.status_code == 404

# 4) PUT 幂等：两次相同内容，结果一致
r5 = client.put("/tasks/t1", json={"task_id": "t1", "filename": "demo2.wav"})
r6 = client.put("/tasks/t1", json={"task_id": "t1", "filename": "demo2.wav"})
print("PUT twice:", r5.json(), r6.json())
assert r5.json()["filename"] == "demo2.wav"
assert r6.json()["filename"] == "demo2.wav"

# 5) DELETE 幂等：本示例约定资源不存在时仍返回 204
r7 = client.delete("/tasks/t1")
r8 = client.delete("/tasks/t1")
print("DELETE twice:", r7.status_code, r8.status_code)
assert r7.status_code == 204
assert r8.status_code == 204

# 6) Header 参与请求，404 仍可观测追踪头
r9 = client.get("/tasks/t2", headers={"X-Request-Id": "req-123"})
print("X-Request-Id sent, status:", r9.status_code)
assert r9.status_code == 404

# 7) 校验失败由框架在边界拦截，返回 422
r10 = client.post("/tasks", json={"task_id": "", "filename": "x.wav"})
print("empty task_id:", r10.status_code)
assert r10.status_code == 422

tmpdir.cleanup()
print("HTTP 语义校验通过：方法/幂等/状态码/Header 各司其职")
# 预期输出:
# POST t1: 201 /tasks/t1 {'id': 't1', ...}
# POST duplicate: 409 task t1 already exists
# GET t1: 200 {'id': 't1', ...}
# GET missing: 404
# PUT twice: {'id': 't1', 'filename': 'demo2.wav', ...} ...
# DELETE twice: 204 204
# X-Request-Id sent, status: 404
# empty task_id: 422
# HTTP 语义校验通过：方法/幂等/状态码/Header 各司其职
```

示例中的结果可以收束为一条判断线：创建得到 `201 + Location`，重复创建得到 `409`，查询不到资源得到 `404`，删除后的重复删除仍为 `204`。这些并不是 FastAPI 的私有习惯，而是 HTTP 给调用方提供的、可被通用工具理解的协作信号。

## 逐层拆解：方法、结果与元数据各说什么

### 方法：先说明你想做什么

| 方法 | 面向资源的含义 | 是否应幂等 | 典型任务接口 |
|---|---|---|---|
| `GET` | 读取资源或集合 | 是 | `GET /tasks/t1` |
| `POST` | 在集合中创建新资源 | 通常否 | `POST /tasks` |
| `PUT` | 以给定表示整体设置资源状态 | 是 | `PUT /tasks/t1` |
| `PATCH` | 局部更新资源 | 方法本身不保证；具体操作可设计为幂等 | `PATCH /tasks/t1` |
| `DELETE` | 删除资源 | 是 | `DELETE /tasks/t1` |

幂等并不要求每一次响应字节或状态码完全相同，而是要求**重复执行同一请求后，服务端的预期效果与执行一次相同**。因此重复 `PUT` 同一份任务数据仍是幂等的；“计数加一”式的 `PATCH` 则不是，因为每次都会改变状态。网络不可靠时，客户端和网关正是据此判断请求是否适合自动重试。

同理，重复删除同一资源时，第二次返回 `204` 还是 `404` 属于接口契约选择，并不改变 `DELETE` 的幂等语义：无论调用一次还是多次，目标资源最终都不存在。本节示例选择两次都返回 `204`，是为了让客户端重试无需再区分“此前已删除”和“本次删除”。

### 状态码：再说明发生了什么

状态码负责把结果分成基础设施也能理解的类别：

- `200 OK`：请求成功并返回内容。
- `201 Created`：创建成功；`Location` 指向新资源地址。
- `204 No Content`：操作成功但无需响应体，例如删除。
- `400 Bad Request`：请求整体不符合协议或无法解析。
- `401 Unauthorized`：未完成认证；`403 Forbidden`：已认证但没有权限。
- `404 Not Found`：目标资源不存在或不对当前调用方可见。
- `409 Conflict`：请求与当前资源状态冲突，例如重复创建。
- `413 Payload Too Large`：上传文件或请求体超过服务允许范围。
- `422 Unprocessable Content`：请求格式可读，但字段值不符合声明的业务输入约束。
- `5xx`：服务端无法完成请求，调用方通常需要记录、退避或提示稍后重试。

这里最容易混淆的是 `400` 与 `422`：`400` 泛指服务端因客户端错误而不能或不愿处理请求；`422` 则强调服务端理解内容类型且内容语法正确，却无法处理其中的指令。FastAPI 默认把请求数据校验失败表示为 `422`，例如 `task_id` 为空或优先级越界。不要把两者简单记成“语法错误”和“业务错误”；具体边界还取决于框架行为与团队契约。

### Header：把不属于业务正文的信息放在信封上

URL 定位资源，Body 描述载荷，Header 则承载跨业务通用的元数据：

- `Content-Type` 表示实际发送的内容类型，`Accept` 表示客户端希望接收的类型。
- `Authorization` 携带认证凭据，不应混入任务创建模型。
- `Cache-Control` 与 `ETag` 让客户端和代理知道响应如何缓存与校验。
- `X-Request-Id` 让前端、网关和多个后端日志能关联到同一次请求。

一个实用约定是：网关若没有收到 `X-Request-Id` 就生成一个；后端在日志和错误响应中保留它。这样用户报告“请求失败”时，服务端不必从海量日志里猜测是哪一次调用。

回到包裹运单的比喻：方法是寄送指令，状态码是处理回执，Header 是运单上的追踪与处理标记。三者都不替业务决定“任务应如何转写”，却让每个参与者准确知道该做什么、发生了什么、出了问题去哪里查。下一节会把这种协议语义进一步提升为资源导向的 RESTful 设计。
