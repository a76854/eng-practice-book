# HTTP 协议精髓

> 学完本节，你能回答：为什么 `GET` 与 `POST` 不能互换？幂等性对重试与网关意味着什么？看到 `200 / 201 / 204 / 400 / 404 / 409 / 422` 时，你能否立刻判断“谁该为这个错误负责”？Header 又如何承载内容协商、缓存与追踪？

## 先动手：让返回码告诉你语义是否对

别先背方法表，先看真实接口的返回。下面的单文件 Demo 用 `TestClient` 在本地跑通 7 次请求，每次的 `status_code` 与 `Location` 就是 HTTP 语义的答案。跑完再命名原理。

```{code-cell} ipython3
import tempfile, pathlib

from fastapi import FastAPI, Header, HTTPException, Response, status
from fastapi.testclient import TestClient
from pydantic import BaseModel, Field
from m2t.store import TaskStore

tmpdir = tempfile.TemporaryDirectory()
db_path = pathlib.Path(tmpdir.name) / "http_semantics.db"
store = TaskStore(db_path)

class TaskCreateIn(BaseModel):
    task_id: str = Field(min_length=1, max_length=64, description="任务 ID")
    filename: str = Field(min_length=1, description="文件名")

class TaskOut(BaseModel):
    id: str
    filename: str
    status: str

app = FastAPI(title="HTTP Semantics Demo")

put_counter = {"count": 0}

@app.get("/tasks/{task_id}", response_model=TaskOut)
def get_task(task_id: str, x_request_id: str | None = Header(default=None)):
    row = store.get(task_id)
    if row is None:
        raise HTTPException(status_code=404, detail="task not found")
    return TaskOut(id=row["id"], filename=row["filename"], status=row["status"])

@app.post("/tasks", response_model=TaskOut, status_code=status.HTTP_201_CREATED)
def create_task(payload: TaskCreateIn, response: Response):
    if store.get(payload.task_id) is not None:
        raise HTTPException(status_code=409, detail=f"task {payload.task_id} already exists")
    store.create(payload.task_id, payload.filename)
    row = store.get(payload.task_id)
    assert row is not None
    response.headers["Location"] = f"/tasks/{payload.task_id}"
    return TaskOut(id=row["id"], filename=row["filename"], status=row["status"])

@app.put("/tasks/{task_id}", response_model=TaskOut)
def put_task(task_id: str, payload: TaskCreateIn):
    put_counter["count"] += 1
    existing = store.get(task_id)
    if existing is None:
        store.create(task_id, payload.filename)
    else:
        store.update(task_id, filename=payload.filename)
    row = store.get(task_id)
    assert row is not None
    return TaskOut(id=row["id"], filename=row["filename"], status=row["status"])

@app.delete("/tasks/{task_id}", status_code=status.HTTP_204_NO_CONTENT)
def delete_task(task_id: str):
    row = store.get(task_id)
    if row is None:
        return Response(status_code=status.HTTP_204_NO_CONTENT)
    store.delete(task_id)
    return Response(status_code=status.HTTP_204_NO_CONTENT)

@app.get("/healthz")
def healthz():
    return {"status": "ok"}

client = TestClient(app)

# 1) POST 创建，观测 201 与 Location
r1 = client.post("/tasks", json={"task_id": "t1", "filename": "meeting.wav"})
print("POST t1:", r1.status_code, r1.headers.get("location"), r1.json())
assert r1.status_code == 201
assert r1.headers["location"] == "/tasks/t1"

# 2) POST 重复，观测 409 而非静默覆盖
r2 = client.post("/tasks", json={"task_id": "t1", "filename": "meeting.wav"})
print("POST duplicate:", r2.status_code, r2.json()["detail"])
assert r2.status_code == 409

# 3) GET 存在 200，不存在 404
r3 = client.get("/tasks/t1")
print("GET t1:", r3.status_code, r3.json())
assert r3.status_code == 200
r4 = client.get("/tasks/missing")
print("GET missing:", r4.status_code)
assert r4.status_code == 404

# 4) PUT 幂等：两次相同内容，结果一致
r5 = client.put("/tasks/t1", json={"task_id": "t1", "filename": "demo2.wav"})
r6 = client.put("/tasks/t1", json={"task_id": "t1", "filename": "demo2.wav"})
print("PUT twice:", r5.json(), r6.json())
assert r5.json()["filename"] == "demo2.wav"
assert r6.json()["filename"] == "demo2.wav"

# 5) DELETE 幂等：两次删除均为 204
r7 = client.delete("/tasks/t1")
r8 = client.delete("/tasks/t1")
print("DELETE twice:", r7.status_code, r8.status_code)
assert r7.status_code == 204
assert r8.status_code == 204

# 6) Header 参与请求，404 仍可观测追踪头
r9 = client.get("/tasks/t2", headers={"X-Request-Id": "req-123"})
print("X-Request-Id sent, status:", r9.status_code)
assert r9.status_code == 404

# 7) 校验失败由框架在边界拦截，返回 422
r10 = client.post("/tasks", json={"task_id": "", "filename": "x.wav"})
print("empty task_id:", r10.status_code)
assert r10.status_code == 422

tmpdir.cleanup()
print("HTTP 语义校验通过：方法/幂等/状态码/Header 各司其职")
# 预期输出:
# POST t1: 201 /tasks/t1 {'id': 't1', ...}
# POST duplicate: 409 task t1 already exists
# GET t1: 200 {'id': 't1', ...}
# GET missing: 404
# PUT twice: {'id': 't1', 'filename': 'demo2.wav', ...} ...
# DELETE twice: 204 204
# X-Request-Id sent, status: 404
# empty task_id: 422
# HTTP 语义校验通过：方法/幂等/状态码/Header 各司其职
```

读输出可直接推导三条规则：创建成功必须给 `201 + Location`，重复创建必须给 `409` 而非覆盖，校验失败由框架直接给 `422`。`404` 与 `204` 的幂等语义也在重复请求中自证。先记住这几行的“体感”，再给它们命名。

## 从观测反推：方法语义与幂等性

刚才的 7 次请求已把方法语义跑出来了：

* `GET` 是只读探查，重复读结果一致，所以可安全重试与缓存
* `POST` 是新建，重复发会产生冲突，这就是 `409` 的来源，非幂等
* `PUT` 是整体替换，重复发同一内容会收敛到同一状态，幂等
* `PATCH` 是否幂等取决于你怎么定义它，若是“设为 completed”则幂等，若是“计数加一”则非幂等
* `DELETE` 也是幂等，资源已不存在再删一次仍是 `204`

网络不可靠，超时后能否重试就看这一点。网关与前端的重试按钮都依赖方法的幂等声明做决策，而不是看方法名本身。

方法与幂等的对应可归纳为一张小表，放在观测之后当作记忆锚点即可：

| 方法 | 是否安全 | 是否幂等 | 典型用途 |
|------|----------|----------|----------|
| GET | 是 | 是 | 查询任务、拉取列表 |
| HEAD | 是 | 是 | 只取 Header 探活 |
| POST | 否 | 否 | 创建任务、触发转写 |
| PUT | 否 | 是 | 全量替换任务元数据 |
| PATCH | 否 | 取决于实现 | 修改任务状态或片段 |
| DELETE | 否 | 是 | 删除任务 |

## 从观测反推：状态码即责任划分

状态码首位即责任归属，同样可从刚才的输出反推：

* `2xx` 成功：`200` 通用成功，`201` 资源已创建且带 `Location`，`204` 成功但无返回体，常用于 `DELETE`
* `3xx` 重定向：`301` 永久跳转，`302` 临时跳转，`304` 配合缓存
* `4xx` 客户端错：`400` 通用坏请求，`401` 未认证，`403` 已认证但无权限，`404` 资源不存在，`409` 资源冲突，`422` 语义不可处理（FastAPI 与 Pydantic 校验失败的首选），`413` 载荷过大，`429` 限流
* `5xx` 服务端错：`500` 未捕获异常，`502` 或 `503` 或 `504` 网关或过载或超时

MeetingToText 的映射就是这一划分的实例：上传格式错误走 `400`，重复任务走 `409`，校验失败走 `422`，文件过大走 `413`，任务不存在走 `404`，鉴权失败走 `401`。调用方据此决定是重试、提示用户，还是报警。

> 选型说明：`400` 与 `422` 的争执由来已久，本书遵循 FastAPI 约定，语法层面无法解析用 `400`，语义校验失败用 `422`，团队统一即可。

## Header：信封上的元数据

URL 与 Body 是信件正文，Header 是信封标记。它承载内容协商（`Content-Type` 与 `Accept`）、缓存（`Cache-Control` 与 `ETag`）、认证与追踪（`Authorization` 与 `X-Request-Id`）、跨域与安全（`CORS` 等）这些正交关注点。

两个常被忽视的实践：

1. 内容协商：用 `Accept: application/json` 明确期望 JSON，而不是靠后缀 `?format=json`
2. 请求追踪：网关或前端注入 `X-Request-Id`，后端原样回传并写入日志，靠它串联跨服务调用链

> 环境约定：本书面向 Linux，Header 键名大小写不敏感但值大小写敏感，`multipart/form-data` 边界由浏览器或客户端自动生成，手写易错，直接用 `UploadFile` 即可。
