# HTTP 与 RESTful

学完本节，你能回答：

- 浏览器打开一个网页时，背后发生了一次怎样的对话，HTTP 在其中扮演什么角色？
- HTTP 的五个方法各用在什么场景，其中哪些能安全重试？
- 常用状态码分别代表谁的责任，调用方如何按状态码分支？
- RESTful 为什么会冒出来，它和 HTTP 是什么关系？

> HTTP 是一封有固定格式的信。寄件人、收件人、物品种类都写在规定的位置。邮局看不懂你的业务内容，却认得信封格式，能据此分拣、追踪、缓存。你按格式写信封，全链路的机器就自动替你干活。

你在浏览器输入一个网址，按下回车，几毫秒后页面出现了。这短短的一瞬里，你的浏览器其实完成了一次对话：它向远方的服务器说了一句话，服务器听完回了一句，页面就是服务器那句话的内容。浏览器和服务器各说什么语言、格式是什么、规矩是什么，这套规矩就是 HTTP。它不是什么高深的新技术，而是互联网从诞生起就一直在用的"对话协议"。我们先讲清楚它在干嘛，再讲怎么把它的格式用对。

## HTTP 在干嘛：浏览器与服务器之间的一套对话

1989 年，Tim Berners-Lee 为了让研究者能方便地互相查阅研究文档，发明了万维网，也顺带发明了它的对话协议 HTTP。当时 HTTP 的职责极其单纯：浏览器说"我要看某一篇文档"，服务器把文档拿给它，或者回一句"没有这篇"。

一次对话由两句话组成：

- **请求**：浏览器发出的那句，说明想做什么、对谁做、附带什么额外信息。
- **响应**：服务器回的那句，说明结果如何、正文是什么。

这个"请求加响应"的结构，是理解 HTTP 的一切的起点。后面要讲的方法、状态码、资源，其实都是往这两句话里填不同内容：方法是请求里那个"想做什么"，状态码是响应里那个"结果如何"，资源是"对谁做"的那个对象。

## 方法：请求里的动词

请求的第一部分是一个动词，告诉服务器想干什么。HTTP 定义了五个常用动词：

| 方法 | 用途 | 是否幂等 | 重试安全性 |
|---|---|---|---|
| GET | 读取资源 | 是 | 可无限重试，可缓存 |
| POST | 新建资源 | 否 | 重试可能产生重复数据 |
| PUT | 整体替换资源 | 是 | 可安全重试 |
| PATCH | 局部修改资源 | 不定 | 取决于你如何定义它 |
| DELETE | 删除资源 | 是 | 可安全重试 |

表里最值得记住的是"幂等"这个词。网络不可靠，请求超时是家常便饭，超时之后能不能直接重发，就看这次操作是否幂等。幂等意味着"做一次和做多次，结果一样"。

想通这一点，很多日常困扰就化解了：为什么刷新按钮可以反复点，因为刷新触发的是 GET；为什么支付按钮要做防重复，因为提交支付是 POST，双击就成了两笔。网关的自动重试、前端的手动重试，都靠方法的幂等声明做决策，而不是靠看方法名猜。

## 状态码：响应里的结论

响应的第一行是一个数字，告诉浏览器"这件事结果如何"。它把"谁该为这个结果负责"写进了响应，让调用方不必猜测，直接按数字分支。

| 状态码 | 含义 | 谁的错 | 调用方通常做什么 |
|---|---|---|---|
| 200 | 成功 | 无 | 正常处理数据 |
| 201 | 已创建 | 无 | 读取 Location 定位新资源 |
| 204 | 无内容，如删除成功 | 无 | 不做处理 |
| 400 | 请求格式错误 | 客户端 | 检查请求 |
| 401 | 未认证 | 客户端 | 重新登录 |
| 403 | 无权限 | 客户端 | 提示无权限 |
| 404 | 资源不存在 | 客户端 | 提示或跳转 |
| 409 | 与当前状态冲突 | 客户端 | 提示冲突或重试 |
| 422 | 校验不通过 | 客户端 | 按错误详情修正输入 |
| 500 | 服务端内部错误 | 服务端 | 稍后重试或报警 |

把握一个分组就够用：4 开头的归客户端，5 开头的归服务端。看到 404，是调用方要的地址不对；看到 500，是服务端出了状况。这个分组让监控、日志、网关限流都能各自施策。

## 资源与 RESTful：回到 HTTP 的设计初衷

方法和状态码都齐了，还剩最后一个问题：动词该对谁做？这就是"资源"的来历，也是 RESTful 要解决的事。

在 Web 服务刚兴起的年代，这个问题没有统一答案。有的团队把动词写进地址：`/getUser`、`/createUser`、`/deleteUser`；有的团队把所有操作都发给一个入口，靠请求体里的一个 action 字段区分。十家公司十种风格，前端每对接一家都要重新摸一遍，网关、缓存这些基础设施也看不懂各自在干嘛。

2000 年，HTTP 规范的主要作者之一 Roy Fielding 在他的博士论文里提出了 REST。他的想法很朴素：HTTP 从诞生起，就是为"对资源做动作"设计的，GET 是取一份文档，POST 是提交一份新文档，地址就是文档的位置。与其各自发明一堆自定义风格，不如把这个天性用对。

所以 RESTful 不是什么新协议，而是回到 HTTP 的设计初衷：地址用名词表示资源，动作交给 HTTP 方法表达。

| 意图 | 把动词塞进 URL 的写法 | 资源加动词的 RESTful 写法 |
|---|---|---|
| 创建任务 | POST /createTask | POST /tasks |
| 查询任务 | POST /getTask?id=1 | GET /tasks/1 |
| 更新任务 | POST /updateTask | PUT /tasks/1 |
| 删除任务 | POST /deleteTask | DELETE /tasks/1 |

两种写法表面都能干活，收益却差很多。前一种把"做什么"藏进了地址或请求体，机器看不懂，重试策略无从制定，前端还得记一套动作名。后一种用统一的资源加方法表达，机器直接读懂：POST 是新建，GET 是读取，PUT 是替换，DELETE 是删除。

一个简单的判断标准是：如果一个接口必须靠名字里的动词才能说清它在干嘛，多半是资源边界没划好。先想清楚"这个系统里有哪些资源"，再套用 HTTP 方法，接口设计自然就顺了。

## 本节小结

- HTTP 是浏览器与服务器之间的一套对话协议，一次对话由请求与响应两句话组成，方法是请求里的动词，状态码是响应里的结论。
- 五个方法各有用途，幂等性决定能否重试，网关与前端的重试逻辑都依赖这一声明。
- 状态码是责任划分，4 开头归客户端，5 开头归服务端，调用方按码分支而非猜测。
- RESTful 不是新协议，而是回到 HTTP"对资源做动作"的设计初衷，用名词表示资源、用方法表达动作，语义才能被机器读懂。

> 把 HTTP 当成信封而不是管道，你就能借到整套基础设施的力。
