# OpenAPI 契约测试

学完本节，你能回答：

- 为什么文档和代码分别维护，几乎一定会在联调时发生漂移？
- FastAPI 如何从路由签名与 Pydantic 模型生成 `openapi.json`、Swagger UI 和机器可读 Schema？
- 契约测试如何在本地提前发现路径、字段和状态码的破坏性变化？

> 建筑施工不能只靠一张装修效果图：效果图好看，却不一定标明承重墙、管线位置和材料规格。真正能让设计、施工与验收协作的是同一份可计算的工程模型——改一根梁，图纸、用料和验收项都要一起变化。接口文档也是如此：若 Markdown、后端模型和前端类型各自维护，它们只是三张可能过期的效果图；OpenAPI 的价值在于让这些参与者围绕同一份结构化模型协作。

前几节已经定义了资源路径、参数位置、状态码和统一响应。它们若只存在于开发者脑中或一份手写文档里，仍然会随代码变化而失效。契约真正可靠的标志不是“写得很详细”，而是它能被代码生成、能被测试读取，并在变化时主动失败。

## 把文档当成事后说明：缺了什么

**1. 同一字段有多份真相**

后端把 `priority` 从可选改为必填，前端仍按旧文档发送两个字段；直到真实请求得到 `422`，双方才知道契约早已不一致。

```text
后端模型已变 + 前端类型未变 + 文档未变 = 联调现场失败
```

**2. 破坏性变化无法被自动发现**

删除一个路径、改一个响应字段、把 `201` 改成 `200`，代码审查时未必有人意识到它影响了外部调用方。若没有契约断言，回归测试可能只覆盖后端内部逻辑，完全看不见 API 边界被破坏。

**3. 调用方只能靠人工阅读接入**

前端若只能阅读页面文档再手写类型和请求函数，每新增一个端点都要重复翻译。人为翻译不仅慢，还会把拼写、默认值和枚举范围再次复制一遍。

这些问题的共同根因是：**文档、实现和测试没有共享同一个机器可读的契约来源**。

### 从“写完代码再写文档”到“模型驱动协作”

解决方案不是要求开发者更勤快地更新文档，而是让路由签名与数据模型成为单一事实源，并让测试直接读取由它生成的 OpenAPI。这样，字段变化既会更新文档，也会改变可被 CI 验证的 Schema。

## 文档即代码，还是代码即文档

传统协作的痛点是**文档与实现双轨漂移**：后端改了字段，前端仍按旧文档联调，直到联调现场才暴露“少了一个必填字段”或“类型从 `int` 变成了 `string`”。根因在于文档是“事后描述”，而非“事前契约”。

OpenAPI 的解决思路是**契约即代码**：路由签名、Pydantic 模型和路由装饰器中的 `responses` 等声明共同构成契约的主要事实源，FastAPI 再据此生成 `openapi.json`（机器可读）与 `/docs`（Swagger UI，人可读）。前端可据此生成类型与客户端，后端则用契约测试核对真实行为——**文档不再只是附属品，而成为可验证的协作边界**。

类比建筑图纸：手绘效果图（Markdown 文档）美观但不保证与施工一致；BIM 模型（OpenAPI）由结构数据直接生成，改一根梁，图纸与算量自动同步，施工方可按模型预制构件。

FastAPI 的生成链路是：`Python 类型标注 + Pydantic Field + 路由声明 → JSON Schema → OpenAPI paths/components → openapi.json → Swagger UI / ReDoc / 代码生成器`。常规接口无需手写整份 OpenAPI YAML；模型和路由声明变化时，生成文档会随之变化。

但“自动生成”不等于“自动完整”：代码中临时抛出的 `409`、统一异常信封或动态响应，如果没有通过 `responses`、响应模型等方式声明，就不会凭空出现在 OpenAPI 中；声明的契约也不自动证明运行时一定遵守它。因此下一步仍要用真实请求做契约测试。

## 三个端点：契约的三种形态

- `GET /openapi.json`：完整的 OpenAPI 文档（JSON），供代码生成器（`openapi-generator` / `orval` / `hey-api`）消费，生成前端类型与请求函数。
- `GET /docs`：Swagger UI，交互式文档与在线试调，适合开发期联调与演示。
- `GET /redoc`：ReDoc 风格文档，阅读体验更佳，适合对外发布。

在默认配置下，`FastAPI(title="MeetingToText", version="0.1.0")` 创建的应用会暴露这三个端点；本节用一个独立的最小应用演示该机制。关键实践是**为每个路由补充 `summary / description / response_model / status_code / responses`**，让生成的文档尽量完整地表达对外契约。

## 契约测试：用 TestClient 守住“契约不漂移”

契约测试的核心断言是：**`openapi.json` 中描述的路径、方法、请求体与响应形状，与 `TestClient` 的真实请求行为一致**。一旦后端新增必填字段、修改类型或删除路径，测试即失败，迫使协作方同步更新。

测试可在本地无网络完成：`TestClient` 直接调用 ASGI 应用，无需启动服务；断言覆盖路径存在性、请求体必填、响应 `required` 字段与状态码语义。

> **环境约定**：本书面向 Linux，OpenAPI 生成与契约测试与平台无关；若涉及 `openapi.json` 的本地落盘，统一用 `pathlib.Path` 处理分隔符差异。

## 可运行示例：读取 openapi.json 校验契约

示例（演示自动生成与契约测试，`TestClient` 本地验证，无网络）：

```{code-cell} ipython3
import tempfile, pathlib

from fastapi import FastAPI, HTTPException, status
from fastapi.testclient import TestClient
from pydantic import BaseModel, Field
from m2t.store import TaskStore

tmpdir = tempfile.TemporaryDirectory()
db_path = pathlib.Path(tmpdir.name) / "openapi.db"
store = TaskStore(db_path)

# --- 契约：Pydantic 模型（即 OpenAPI 的 components.schemas 来源） ---
class TaskCreateIn(BaseModel):
    task_id: str = Field(min_length=1, max_length=64, description="任务 ID")
    filename: str = Field(min_length=1, description="文件名")
    priority: int = Field(default=0, ge=0, le=10, description="优先级 0–10")

class TaskOut(BaseModel):
    id: str = Field(description="任务 ID")
    filename: str = Field(description="文件名")
    status: str = Field(description="任务状态")
    priority: int = Field(default=0, description="优先级")

app = FastAPI(
    title="MeetingToText Contract Demo",
    version="0.1.0",
    description="演示 OpenAPI 自动生成与契约测试（MeetingToText 的极简切片）",
)

@app.post(
    "/tasks",
    response_model=TaskOut,
    status_code=status.HTTP_201_CREATED,
    summary="创建任务",
    responses={409: {"description": "任务已存在"}},
    tags=["tasks"],
)
def create_task(payload: TaskCreateIn):
    """创建任务：契约由 TaskCreateIn 与 TaskOut 自动生成到 openapi.json。"""
    if store.get(payload.task_id) is not None:
        raise HTTPException(status_code=409, detail="already exists")
    store.create(payload.task_id, payload.filename)
    row = store.get(payload.task_id)
    assert row is not None
    return TaskOut(id=row["id"], filename=row["filename"], status=row["status"], priority=payload.priority)

@app.get("/tasks/{task_id}", response_model=TaskOut, summary="查询任务", tags=["tasks"])
def get_task(task_id: str):
    row = store.get(task_id)
    if row is None:
        raise HTTPException(status_code=404, detail="not found")
    return TaskOut(id=row["id"], filename=row["filename"], status=row["status"])

@app.get("/healthz", summary="健康检查", tags=["ops"])
def healthz():
    return {"status": "ok"}

# --- 本地验证：用 TestClient 读取并校验 openapi.json（无网络） ---
client = TestClient(app)

# 1) 拉取 openapi.json（FastAPI 自动生成，无需手写）
openapi = client.get("/openapi.json").json()
print("openapi version:", openapi["openapi"])
print("title:", openapi["info"]["title"], "version:", openapi["info"]["version"])
assert openapi["openapi"].startswith("3.")
assert openapi["info"]["title"] == "MeetingToText Contract Demo"
assert "/tasks" in openapi["paths"]
assert "/tasks/{task_id}" in openapi["paths"]
assert "/healthz" in openapi["paths"]

# 2) 校验路径与方法：POST /tasks 存在于契约中
post_tasks = openapi["paths"]["/tasks"]["post"]
print("POST /tasks summary:", post_tasks["summary"])
assert post_tasks["summary"] == "创建任务"
assert "201" in {str(k) for k in post_tasks["responses"].keys()}
assert "409" in {str(k) for k in post_tasks["responses"].keys()}

# 3) 校验请求体：TaskCreateIn 的字段被生成到 components.schemas
schemas = openapi["components"]["schemas"]
assert "TaskCreateIn" in schemas
create_schema = schemas["TaskCreateIn"]
print("TaskCreateIn required:", create_schema.get("required"))
assert "task_id" in create_schema["required"]
assert "filename" in create_schema["required"]

# 4) 校验响应：TaskOut 的字段被生成
assert "TaskOut" in schemas
out_schema = schemas["TaskOut"]
print("TaskOut properties:", sorted(out_schema["properties"].keys()))
assert "id" in out_schema["properties"]
assert "status" in out_schema["properties"]

# 5) 契约与行为一致：真实请求符合契约描述
r1 = client.post("/tasks", json={"task_id": "c1", "filename": "meeting.wav", "priority": 3})
print("POST /tasks real:", r1.status_code, r1.json())
assert r1.status_code == 201

# 6) 契约守卫：空 task_id 被校验拦截（422），与 openapi.json 的 minLength 约束一致
r2 = client.post("/tasks", json={"task_id": "", "filename": "x.wav"})
print("empty task_id:", r2.status_code)
assert r2.status_code == 422

# 7) 契约守卫：重复创建得到 409，且该分支已经由 responses 写入契约
r3 = client.post("/tasks", json={"task_id": "c1", "filename": "dup.wav"})
print("duplicate:", r3.status_code)
assert r3.status_code == 409

# 8) Swagger UI 可达（仅校验可访问性，不解析 HTML）
r_docs = client.get("/docs")
print("GET /docs:", r_docs.status_code, "content-type:", r_docs.headers.get("content-type", "")[:30])
assert r_docs.status_code == 200

# 9) 演示“契约漂移”的检测思路：若后端新增必填字段而前端未同步，契约测试会以 422 失败
# （此处仅演示断言形态，实际漂移由 CI 中的契约测试捕获）
print("契约测试通过：已声明的 OpenAPI 契约与本例真实行为一致")

tmpdir.cleanup()
# 预期输出:
# openapi version: 3.1.0
# title: MeetingToText Contract Demo version: 0.1.0
# POST /tasks summary: 创建任务
# TaskCreateIn required: ['task_id', 'filename']
# TaskOut properties: ['filename', 'id', 'priority', 'status']
# POST /tasks real: 201 {'id': 'c1', ...}
# empty task_id: 422
# duplicate: 409
# GET /docs: 200 text/html ...
# 契约测试通过：已声明的 OpenAPI 契约与本例真实行为一致
```

示例中的测试不是在检查“Swagger 页面能否打开”这么简单，而是在验证四种对调用方可见的承诺：

| 契约层面 | 从哪里生成 | 测试断言什么 | 变化时谁需要关注 |
|---|---|---|---|
| 路径与方法 | 路由装饰器 | `/tasks` 是否仍有 `POST` | 前端路由、网关、客户端 |
| 请求字段与约束 | `TaskCreateIn` | 必填字段、长度与类型是否仍存在 | 表单、请求函数、类型生成 |
| 响应结构与状态码 | `response_model` 与路由声明 | `201`、`TaskOut` 是否仍符合约定 | 前端状态管理、监控、集成方 |
| 真实行为 | `TestClient` 请求 | 合法请求成功、非法请求得到预期错误 | 后端实现与回归测试 |

逐层看生成链路：Python 类型和 `Field` 先形成 JSON Schema；路由把它们放进 OpenAPI 的 `paths` 与 `components.schemas`；`/openapi.json` 供代码生成器读取；`/docs` 与 `/redoc` 再把同一份结构呈现给人。任何一层都不是另一份手工副本，因此模型变化会沿链路自然传播。

契约测试也有边界。它能及时发现“路径不见了、字段变了、响应状态码变了”，却不能证明所有业务规则都正确；性能、鉴权策略和跨服务兼容性还需要对应的集成测试与端到端测试。它守住的是接口边界，而不是替代整个测试体系。

回到建筑模型的比喻：OpenAPI 是项目共享的结构模型，Swagger UI 是给人看的视图，前端客户端生成是根据模型预制构件，契约测试则是验收时核对施工结果没有偏离模型。模型一旦改变，所有协作者都应该尽早看到变化，而不是等到房子交付时才发现门的位置不对。
