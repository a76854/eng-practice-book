# 统一响应与契约

学完本节，你能回答：

- 为什么项目一大，错误格式就各写各的，前端对接会崩溃？
- 统一信封长什么样，全局异常处理器如何把不同来源的错误收敛到同一形状？
- 文档和代码为什么总是脱节，OpenAPI 如何让代码成为契约的唯一来源？

> 格式统一，就像所有窗口都用同一种回执单。无论办成没办成，回执上的栏位都一样，你只需按同一种方式读它，而不是每个窗口一套读法。

上一节我们把路由写好了，成功路径很顺：创建返回 201，查询返回数据。但一个系统不会只走成功路径，它每天都要面对各种失败：传错了参数、查了不存在的资源、撞上了冲突、代码抛了异常。这些失败怎么告诉前端，是一个容易被忽略、一旦忽略就出大麻烦的环节。这一节讲两件事：把失败和成功收敛成同一个形状，再让这个形状成为前后端不会漂移的契约。

## 为什么需要统一响应：一个关于"接口多了"的故事

想象一个小项目慢慢长大。一开始只有三五个接口，返回格式随意一点没人计较。后来接口长到几十个上百个，问题就浮上来了：有的接口成功返回 data 字段，有的返回 result；有的出错返回 detail，有的返回 error，还有一个返回 message。

前端同学负责对接这些接口，写着写着就崩溃了：每个接口都要单独判断"成功长什么样、失败长什么样"，一百个接口就是一百套分支。更麻烦的是日志和监控，因为字段不统一，想按字段统计错误都无从下手。

问题的根源不在前端，而在于后端一开始就没有约定好"成功和失败分别长什么样"。事后去改一百个接口，代价高得吓人，所以这事得在一开始就定。

## 统一信封：把成功和失败都装进一个形状

解决的办法是约定一个统一信封，成功和失败都套上它：

| 字段 | 含义 | 成功时 | 失败时 |
|---|---|---|---|
| code | 业务码，0 表示成功 | 0 | 非 0，通常取状态码 |
| data | 业务数据 | 具体载荷 | null |
| msg | 可读信息 | ok | 可读的错误原因 |

信封的字段名没有绝对标准，有的团队用 success、有的用 error，关键是全链路统一。统一之后，前端就能一行收敛判断：code 不为零就走错误分支。HTTP 状态码仍保留，供网关与监控聚合，信封里的 code 供前端做细粒度分支，两者各司其职。

但信封不能靠每个路由自觉遵守，得靠全局异常处理器兜底。错误来源天生多样，FastAPI 提供三类全局处理器，把它们收敛到同一个信封：

| 异常处理器 | 捕获谁 | 收敛成什么 |
|---|---|---|
| HTTPException | 业务抛出的 404、409、401 等 | 保留状态码，Body 转为信封 |
| RequestValidationError | Pydantic 校验失败的 422 | 把 detail 数组转为信封的 msg |
| Exception | 未捕获的异常 | 500 信封，不泄露堆栈 |

三者的协作让路由只管抛语义化异常，包装的活交给全局一层。这也和上一章的分层思想一脉相承：Service 抛业务错误，Controller 转为 HTTP 异常，全局处理器转为统一信封。

## 为什么需要 OpenAPI：一个关于"文档脱节"的故事

格式统一之后，下一个麻烦是文档。传统开发里，后端写完接口，手写一份文档交给前端。但文档是"事后描述"，后端改了字段，可能忘了更新文档，或者更新了前端没看到。

于是联调现场经常上演这样的对话：前端说"你这个接口的 user_id 字段怎么没了"，后端说"我上周改成必填了，文档里写了"。前端翻出一份三个月前的文档，字段早就对不上。

文档和代码脱节，是因为它们有两个来源：代码是一个来源，手写文档是另一个来源。两个来源各自演进，漂移是必然的，只是时间早晚。

## OpenAPI：让代码成为契约的唯一来源

OpenAPI 的思路是砍掉一个来源，让代码自己生成文档。FastAPI 从类型标注与 Pydantic 模型自动生成机器可读的 openapi.json，以及人可读的交互式文档。改动模型即改动契约，文档自动跟随，漂移的根就断了。

FastAPI 默认暴露三个端点，分别服务不同的消费方：

| 端点 | 形态 | 消费方 |
|---|---|---|
| /openapi.json | 机器可读的 JSON | 前端代码生成器、契约测试 |
| /docs | Swagger UI，可交互试调 | 开发期联调与演示 |
| /redoc | ReDoc 风格，阅读友好 | 对外发布的文档 |

契约测试的思路很朴素：断言 openapi.json 里描述的路径、方法与响应形状，和真实请求行为一致。一旦后端新增必填字段、改了类型或删了路径，测试立刻失败，迫使前后端同步。文档从此不再是被遗忘的附属品，而是一条可以验证的协作边界。

## 本节小结

- 项目一大，错误格式就会各写各的，统一信封在一开始约定好成功与失败的形状，避免前端写一百套分支。
- 全局异常处理器把 HTTP 异常、校验失败与未捕获异常统一包装，路由只管抛异常。
- 文档与代码脱节的根源是两个来源各自演进，OpenAPI 让代码成为契约的唯一来源，文档自动跟随。
- 契约测试断言文档与行为一致，让前后端对齐从口头约定变成可验证的事实。

> 让错误收敛到一种形状，让文档长在代码上，协作才能不被细节拖垮。
