# RESTful 成熟度模型

学完本节，你能回答：

- 为什么把所有操作都塞进 `POST /api/action` 会让接口越来越难理解和演进？
- Richardson 成熟度模型的四个层级分别增加了什么能力，又带来什么成本？
- 为什么本课程多数 API 选择 Level 2，而不把 Hypermedia 当作必须完成的目标？

> 图书馆若只有一个服务台，读者每次都要说“帮我借这本书”“帮我还这本书”“帮我查这本书”，服务台再靠口头动作决定去哪个书架、改哪条记录。书不多时没有问题；书一多，读者、管理员和自助机都要背同一套暗号。资源导向的设计像给每本书一个可查的编号、给书架一个稳定分类，再用“查询、借阅、归还”这些统一规则操作它。RESTful 不在于 URL 漂不漂亮，而在于接口是否让人和工具都看得出正在操作什么。

HTTP 已经提供了方法、状态码和 Header 这套通用语言；资源导向的 HTTP API 会进一步把业务对象组织成资源，并让 URL、方法和结果语义相互配合。完整 REST 还包含无状态、可缓存、统一接口和超媒体等约束，因此不能只凭“路径用了名词、方法用了 GET/POST”就断言一个系统已经满足 REST。这里讨论的是降低协作认知成本的设计方式，不是一条“所有接口必须长成同一个样子”的教条。

## 所有动作挤在一个入口：缺了什么

初学者常从 RPC 风格开始：只暴露一个入口，用请求体里的 `action` 决定做什么。

```json
POST /api
{"action": "createTask", "task_id": "t1", "filename": "meeting.wav"}
```

这种方式实现直接，但动作不断增加后，协议语义会被藏进越来越大的分发函数。

**1. URL 看不出正在操作什么资源**

`/api` 对网关、日志和新同学几乎没有信息量。要知道请求是创建任务、导出文本还是取消转写，必须解析 Body。

```text
POST /api  ← 所有业务看起来完全一样
```

路径无法作为文档、监控维度或权限规则的稳定锚点。

**2. HTTP 方法和状态码无法发挥作用**

所有请求都是 `POST` 时，读取操作也失去缓存机会，重试器不知道哪些调用可安全重发；如果所有结果都 `200`，冲突与创建成功又只能靠业务字段区分。

```text
200 {"ok": true}   和   200 {"ok": false}
```

调用方不得不重复实现本应由协议提供的判断逻辑。

**3. 动作分发会膨胀成第二套路由系统**

随着 `createTask`、`getTask`、`deleteTask`、`exportTask` 增加，一个路由内部逐渐出现长串 `if/elif`。每个分支又要各自校验参数、处理错误和维护文档。

这些问题的根因是：**接口没有把“资源是什么”和“对资源做什么”分别表达**。动作被塞进载荷，HTTP 只能充当隧道，无法参与理解和治理。

### 从口头暗号到可寻址资源

上述问题——路径失去含义、协议语义失效、分发逻辑膨胀——看似发生在 URL、状态码和代码结构中，但解决方案是一致的：**先识别资源，再用 HTTP 方法表达对资源的操作**。

## 成熟度模型：逐步把语义还给协议

Richardson 成熟度模型不是 REST 的官方合规标准，也不是给 API 打分的排行榜，而是一种帮助团队理解 HTTP API 演进路径的思考模型。Martin Fowler 对该模型的介绍也特别指出：它适合用来学习和讨论，但不能把某一层级直接当成“符合 REST”的认证。

| 层级 | 核心做法 | 得到什么 | 主要代价 |
|---|---|---|---|
| Level 0 | 单一端点，Body 中携带动作 | 实现最快 | HTTP 语义几乎全部丢失 |
| Level 1 | 为业务对象划分资源 URI | 资源边界更清晰 | 仍可能只使用 `POST` |
| Level 2 | 资源 URI + HTTP 方法 + 状态码 | 缓存、重试、网关和文档可理解接口 | 需要设计一致的资源模型 |
| Level 3 | 在响应中提供可执行链接（Hypermedia） | 客户端可按服务端状态发现下一步 | 响应和客户端复杂度显著上升 |

按 Richardson 模型观察，本课程的任务接口主要采用 **Level 2**：`POST /tasks` 创建任务，`GET /tasks/{task_id}` 查询任务，`DELETE /tasks/{task_id}` 删除任务。这已经能让前端、TestClient、网关和 OpenAPI 在不读业务暗号的前提下理解大部分语义；更准确地说，它是资源导向的 HTTP API，而不是仅凭 Level 2 就宣称实现了完整 REST。

Level 3 的 Hypermedia 并非“更高级所以必须用”。若 API 面向大量未知第三方客户端、工作流会随状态变化，链接可以提高自发现能力；对课程项目和内部前后端协作而言，OpenAPI 加稳定资源路径通常是成本更低的选择。

## 对照式实现：同一业务的 Level 0 与 Level 2

下面用同一个“创建、查询、删除任务”场景对照两种水位。重点观察：谁需要阅读 Body 才能理解动作，谁可以直接利用方法、路径、状态码和 `Location`。

文件 `examples/rest_maturity_demo.py`：

```{code-cell} ipython3
import pathlib
import tempfile

from fastapi import FastAPI, HTTPException, Response, status
from fastapi.testclient import TestClient
from pydantic import BaseModel, Field

from m2t.store import TaskStore

tmpdir = tempfile.TemporaryDirectory()
store = TaskStore(pathlib.Path(tmpdir.name) / "maturity.db")

class TaskCreateIn(BaseModel):
    task_id: str = Field(min_length=1)
    filename: str = Field(min_length=1)

# Level 0：单一入口，动作与参数都藏在 Body
class RpcIn(BaseModel):
    action: str
    task_id: str | None = None
    filename: str | None = None

app_l0 = FastAPI(title="Level 0 RPC")

@app_l0.post("/api")
def rpc_dispatch(payload: RpcIn):
    if payload.action == "createTask":
        if not payload.task_id or not payload.filename:
            raise HTTPException(status_code=400, detail="missing fields")
        if store.get(payload.task_id) is not None:
            raise HTTPException(status_code=409, detail="already exists")
        store.create(payload.task_id, payload.filename)
        return {"ok": True, "id": payload.task_id}
    if payload.action == "getTask":
        row = store.get(payload.task_id or "")
        if row is None:
            raise HTTPException(status_code=404, detail="not found")
        return {"ok": True, "task": row}
    raise HTTPException(status_code=400, detail="unknown action")

# Level 2：资源路径、方法与状态码共同表达语义
class TaskOut(BaseModel):
    id: str
    filename: str
    status: str

app_l2 = FastAPI(title="Level 2 Resource API")

@app_l2.post("/tasks", response_model=TaskOut, status_code=status.HTTP_201_CREATED)
def create_task(payload: TaskCreateIn, response: Response):
    if store.get(payload.task_id) is not None:
        raise HTTPException(status_code=409, detail="already exists")
    store.create(payload.task_id, payload.filename)
    row = store.get(payload.task_id)
    assert row is not None
    response.headers["Location"] = f"/tasks/{payload.task_id}"
    return TaskOut(id=row["id"], filename=row["filename"], status=row["status"])

@app_l2.get("/tasks/{task_id}", response_model=TaskOut)
def get_task(task_id: str):
    row = store.get(task_id)
    if row is None:
        raise HTTPException(status_code=404, detail="not found")
    return TaskOut(id=row["id"], filename=row["filename"], status=row["status"])

@app_l2.delete("/tasks/{task_id}", status_code=status.HTTP_204_NO_CONTENT)
def delete_task(task_id: str):
    if store.get(task_id) is not None:
        store.delete(task_id)
    return Response(status_code=status.HTTP_204_NO_CONTENT)

c0 = TestClient(app_l0)
c2 = TestClient(app_l2)

l0_created = c0.post(
    "/api",
    json={"action": "createTask", "task_id": "m0", "filename": "a.wav"},
)
print("L0 create:", l0_created.status_code, l0_created.json())
assert l0_created.status_code == 200

l2_created = c2.post("/tasks", json={"task_id": "m2", "filename": "b.wav"})
print("L2 create:", l2_created.status_code, l2_created.headers["location"])
assert l2_created.status_code == 201
assert l2_created.headers["location"] == "/tasks/m2"

l2_read = c2.get("/tasks/m2")
print("L2 get:", l2_read.status_code, l2_read.json())
assert l2_read.json()["id"] == "m2"

l2_duplicate = c2.post("/tasks", json={"task_id": "m2", "filename": "b.wav"})
print("L2 duplicate:", l2_duplicate.status_code)
assert l2_duplicate.status_code == 409

l2_deleted = c2.delete("/tasks/m2")
print("L2 delete:", l2_deleted.status_code)
assert l2_deleted.status_code == 204

tmpdir.cleanup()

# 预期输出：
# L0 create: 200 {'ok': True, 'id': 'm0'}
# L2 create: 201 /tasks/m2
# L2 get: 200 {'id': 'm2', 'filename': 'b.wav', 'status': 'pending'}
# L2 duplicate: 409
# L2 delete: 204
```

逐项看差别：

- Level 0 的调用方必须知道 `action` 字符串和每种动作需要哪些字段。
- Level 2 的 `POST /tasks` 已经说明“在任务集合中创建资源”；`GET /tasks/m2` 直接说明“读取 m2”。
- `201`、`Location`、`409` 与 `204` 让创建、定位、冲突和删除结果在协议层可见。
- 两者都能完成业务，但 Level 2 更容易被前端、日志、权限规则、OpenAPI 和通用 HTTP 工具共同理解。

回到图书馆：Level 0 像所有请求都去同一个服务台说暗号；Level 2 则让书架、图书编号和借还规则变成所有人共用的导航系统。资源导向 HTTP API 的价值不在于让路径看起来“标准”，而在于减少每个新调用方必须重新学习的隐性规则。
