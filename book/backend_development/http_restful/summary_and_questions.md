## 本章小结

- **HTTP 是一套用法而非管道**：方法承载操作的语义，幂等性决定能否重试；状态码划分责任，4 开头归客户端、5 开头归服务端；资源用名词表达，动作交给方法。三条准则用对，网关、缓存与重试就能自动配合。
- **FastAPI 把语义落到代码**：方法对应装饰器，状态码对应 status_code，资源对应路径结构；路径参数定位资源、查询参数修饰集合、请求体承载载荷；类型标注与 Field 约束在边界自动校验，以 422 暴露。
- **统一响应与契约让协作收敛**：信封把成功与失败收敛成固定形状，全局异常处理器把 HTTP 异常、校验失败与未捕获异常统一包装；OpenAPI 让代码成为契约来源，契约测试断言文档与行为一致，前后端对齐不再靠口头约定。

## 思考题

1. **幂等性的两种选择**：POST 重复创建返回 409，若改为"重复时直接返回已有资源的 200"是否也算幂等？两种设计对前端重试与去重的语义有何不同？在什么场景下你会选后者？

2. **状态码的取舍**：400 与 422 都可表示客户端错误，团队若统一只用 400 会失去什么信息？网关按状态码做限流与监控时，422 相比 400 能带来哪些可观测性收益？

3. **参数的分工**：查询批量资源时，GET 加逗号分隔的查询参数与 POST 一个批量请求体，在缓存、URL 长度与幂等性上有何 trade-off？你会如何选择？

4. **校验的边界**：Field 的 ge/le/pattern 能拦截形状错误，但"任务标题不能重复"这类规则是否应放在 Pydantic 层？结合分层思想，讨论形状校验与业务规则校验的分工与测试策略。

5. **信封与状态码**：若改为 HTTP 始终 200、靠 Body 里的 code 区分成败，会对网关重试、CDN 缓存与错误监控带来哪些影响？两种方案各自的适用场景是什么？

6. **契约的演进**：后端为响应模型新增一个必填字段而前端尚未更新，契约测试会在哪一环失败？应如何用"新增字段设默认值加版本协商"降低协作成本？
