## 本章小结

- **建模是想清楚数据的关系**：数据活在内存里会消失，文件扛不住查询、并发与约束，于是需要数据库；用实体、属性、关系三要素把一张大表拆成多张窄表加关系表，范式化给拆表一个递进的标尺，本质是让每一份事实只存一处。
- **建库是把模型落成表**：DDL 里主键、外键、非空与 CHECK 都是可执行的约束，表结构之后会演进，用迁移管版本。
- **SQL 是访问数据库的语言**：连接与游标是入口，增删改查四句 SQL 撑起读写，参数化与事务守住注入与一致性两条底线；查询从单表筛选、聚合统计到 JOIN 与子查询层层递进；索引以读加速换写成本，执行计划能验证它建没建对。
- **访问方式要成套看**：直接方式（sqlite3 手写 SQL）透明零依赖，适合教学；生产还要连接池复用连接、ORM 省重复劳动、迁移脚本管表结构演进，SQLAlchemy 分 Core 与 ORM 两层，选型看场景，前提都是先懂 SQL。

## 思考题

1. **范式化的度**：若一张订单表既存商品名又存商品价格，而价格又依赖商品编号，这违反了第几范式？拆出商品表分别会缓解什么、引入什么？在什么情况下你宁愿保留这份冗余？

2. **索引的取舍**：为一张每小时写入数千条、查询以按状态过滤为主的表，是否应为状态列建索引？建与不建分别影响什么？如何用 `EXPLAIN QUERY PLAN` 验证判断，而不是凭感觉？

3. **事务的边界**：若"创建订单后立即扣减库存"需保证原子性，两步包在一个事务里与分两次提交，在并发与失败回滚上有何差异？什么信号提示你一组操作必须放进同一个事务？

4. **JOIN 与子查询**：找出"至少选过一门课的学生"，用 EXISTS 子查询与 INNER JOIN 都能实现，两者的执行计划与结果去重上有何差异？当关联表有重复记录时，JOIN 是否会导致结果行膨胀？

5. **ORM 的边界**：团队查询以复杂聚合为主，ORM 生成的 SQL 常不符合预期，此时坚持 ORM 会付出什么代价？为什么说先学 SQL 再学 ORM 比反过来更稳？在什么信号出现时你会退回原生 SQL？

6. **防注入的本质**：参数化查询为什么能从根上防注入，而"对输入做转义再拼接"仍然不可靠？占位符风格因驱动而异，这种差异背后共同的机制是什么？

7. **连接池与迁移的边界**：教学用 SQLite 直连没有问题，生产环境为什么必须上连接池与迁移脚本？如果一个小工具也硬上这套装备，会付出什么代价？判断"该不该上"的标准是什么？
