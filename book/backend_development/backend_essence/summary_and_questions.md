## 本章小结

- **后端的定位是一段演进**：从服务端模板直出的一体到返回 JSON 的分离，前端、后端、存储三层各司其职，后端守 API 设计、业务逻辑、数据流转与安全防护四条边界，可收束为面向前端提供可编程数据接口、面向存储维护一致性与安全的服务层。
- **语言选型无银弹，只有约束求解**：Java 适合强规范与长期维护，C# 适合平台与工具链统一，Go 适合高并发网关与二进制交付，PHP 适合存量与快速上线，Python 适合数据与算法闭环及教学，结论需附带场景、团队与运维等约束。
- **框架谱系是约束的映射**：Django 以全栈约定见长，适合规范强与后台重的项目，Flask 以微核扩展见长，适合原型与小工具，FastAPI 以现代类型与异步原生见长，适合 I/O 密集与需自动文档的服务，三者无替代关系。
- **先定语言，再定框架**：AI 时代的智能与数据层由 Python 主导，靠生态绑定、快速验证、胶水能力与可读性站住脚跟。在此之上，FastAPI 的异步原生让 I/O 等待可让出，自动文档让契约即代码，类型安全让非法输入在边界即被拦截，三者在特定约束下共同成立。
- **分层让每一层可独立演进**：Controller 薄而专注 HTTP 翻译，Service 厚而承载业务与事务，Repository 封装存储细节，依赖方向为 Controller 向 Service 向 Repository，替换存储或编排业务时只需沿边界操作，结合内存 Repository 与 TestClient 即可在本地完成可回归的验证。
- **贯穿启示**：本章的职责、选型、框架、分层四步为后续章节提供锚点，第 4 章的 HTTP 与 RESTful 细化契约，第 5 章的持久化深化 Repository，第 6 章的并发展开异步，第 10 章的安全回到纵深防护。

## 思考题

1. **职责切分**：在任务从创建到查询的链路中，若把去重放在前端而非后端 Service，会对一致性与可观测性带来哪些影响？职责边界应如何重新划分？
2. **选型再辨**：假设团队以 Java 为主但需集成 Python 的数据处理能力，你会选择 Java 网关加 Python 微服务还是全量切换技术栈？请列出约束清单并说明判断依据。
3. **框架取舍**：一个以管理后台为主、定制少、交付期紧的项目，你会选 Django 还是 FastAPI？若后期需暴露大量 OpenAPI 给外部团队，结论会如何变化？
4. **异步的边界**：FastAPI 的异步能提升 I/O 密集场景的吞吐，但在 CPU 密集处理中为何未必有效？结合第 6 章的 GIL 与异步讨论何时该用异步、何时该用进程或外部服务。
5. **分层的度**：三层架构在小项目中是否过度设计？请讨论何时合并 Service 与 Repository、何时拆分的判断信号，以及合并后对测试与替换的影响。
6. **契约的演进**：当前后端通过 Pydantic 自动生成 OpenAPI，若前端已据此生成代码，后端新增一个必填字段会如何影响协作？应如何通过版本、默认值与兼容性设计降低契约漂移的成本？
7. **存储替换**：若将内存 Repository 替换为基于 SQLAlchemy 的持久化实现，哪些层需要改动、哪些层可保持不变？Repository 接口应如何设计以承载事务与分页等新需求？
