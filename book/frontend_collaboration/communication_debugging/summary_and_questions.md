## 本章小结

- **通信是一条六站的链**：发请求、收请求、办业务、取数据、回响应、画页面，前端管"发"与"画"，后端管"收"与"办"，交接点是请求与响应的约定（见 [前后端是怎么连上的](communication_overview.md)）。
- **发请求看规模选工具**：`fetch` 轻而裸（判状态、转 JSON、三步手写），`axios` 包了工程常用件（自动 JSON、抛错、超时、拦截器），带登录态的应用用 `axios` 更省事（见 [发出请求：fetch 与 axios](fetch_axios.md)）。
- **异步有四态**：没搜、正在搜、搜到了、搜失败了，一个不能少；`loading` / `error` / `data` 三元组同生共灭；竞态用序号牌或取消旧请求，输入框自动搜索必配防抖或序号牌（见 [等一个结果：异步状态](async_state.md)）。
- **契约五样要机器可验证**：方法、路径、参数、状态码、形状；类型一对一、命名只用一种、演进只加不删，前端取认得的字段（见 [对得上：契约落地](contract_alignment.md)）。
- **CORS 拦的是浏览器不是后端**：协议域名端口差一样就算跨域；后端用响应头放行、开发期可用 Vite 代理兜底，生产收紧域名（见 [跨过去：CORS 与开发代理](cors_proxy.md)）。
- **错误分类处理、定位从近到远**：401 跳登录、4xx 就地提示、5xx 给重试；请求发出去了吗、状态码对吗、形状对吗、渲染对吗，一站一站排除，Network 面板加 curl 取证（见 [出了错：错误处理与联调定位](error_debugging.md)）。
- **总体启示**：联调不是"前后端坐一起调通就行"，而是把链路、契约、状态、跨域、错误五件事织成可复用的协作闭环；链路清、契约硬，联调翻车就从玄学变成按图索骥。

## 思考题

1. **请分析**：`fetch` 默认 4xx/5xx 不抛错、`axios` 默认抛错，这两种设计分别把"判断请求成没成"的责任放在了谁身上？结合"统一错误提示"的需求，讨论在哪一层收敛错误处理最合适，并说明拦截器相对每个调用处手写 try/catch 的收益与代价。
2. **请判断**：搜索框每敲一个字母就发一次请求，不加防抖也不加序号牌。从"竞态请求覆盖"的角度分析：用户快速输入 "pydantic" 时，界面最终显示的可能是哪个关键词的结果？给出至少两种规避方案，并比较它们的实现成本与体验差异。
3. **请分析**：后端给搜索结果新增一个 `score` 字段，前端没做任何改动。从"向后兼容"的三条纪律出发，判断这次变更是否安全，并说明"加字段安全、删字段危险、改含义最危险"背后的原因。如果后端把 `score` 从 0-1 改成 0-100，前端应该怎么做？
4. **请判断**：开发期前端用 Vite 代理绕过 CORS，上线后切成"前端与后端同域 + 后端配 CORS"。讨论这种"开发一套、生产一套"的做法会带来哪些"在我机器上是好的"的风险，并说明如何通过"开发代理配置与生产 CORS 配置同源"来降低这类风险。
5. **请分析**：前端收到 401 跳登录、收到 5xx 提示重试、收到 422 提示字段错。结合"状态码即动作"的原则，讨论：什么情况下前端应该"静默重试"而不是提示用户？重试几次、间隔多久是合理的？无限重试会带来什么问题？
6. **请设计**：为文档搜索设计一套联调定位检查表，覆盖"请求、状态码、形状、渲染"四个环节。每个环节列出要看什么、用什么工具看、看到什么算正常、看到什么算异常，并说明当"curl 通而浏览器不通"时应该优先查哪一环。
