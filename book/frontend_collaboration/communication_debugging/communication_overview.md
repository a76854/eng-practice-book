# 前后端是怎么连上的

学完本节，你能回答：

- 一次"搜 pydantic"从点下搜索按钮到看到结果，中间经历了哪几站？
- 前端和后端在这条链路上各自负责什么？交接点在哪？
- 为什么前后端约定用 JSON 通信，而不是 HTML 或其他格式？
- 没有契约时，前后端并行开发会卡在哪？

第 4 章讲后端怎么开接口，第 9 章讲前端怎么画页面，但两者之间那道网还没人缝过。这一节先不写代码，把"连上"这件事的全貌摆出来，后面几节再逐段深入。

> 点外卖下单后，订单先到平台、再到商家后厨、做好了交骑手、最后送到你手上。任何一站卡住，你都知道该找谁。前后端通信也是一条链：请求从浏览器出发，经过网络、网关、后端服务（可能再调外部搜索），响应原路返回渲染成页面。链路画清楚，联调出问题才知道该查哪一站。

一次文档搜索的完整链路长这样：

```{mermaid}
flowchart LR
    A["搜索框输入 pydantic<br/>点搜索"] --> B["fetch 发<br/>GET /api/search?q=pydantic"]
    B --> C["FastAPI 路由<br/>解析 q 与分页"]
    C --> D["Service 校验<br/>去重"]
    D --> E["Repository 调 WebSearch<br/>拿搜索结果"]
    E --> F["200 + JSON<br/>回前端"]
    F --> G["Vue 渲染<br/>结果列表"]
```

请求过去、响应回来，中间每一站都有名有姓。链路定下来，分工自然就清楚了：

| 站点 | 归谁 | 做什么 | 例子 |
| --- | --- | --- | --- |
| 发请求 | 前端 | 按契约组装方法、路径、参数 | `GET /api/search?q=pydantic` |
| 收请求 | 后端路由 | 解析 URL、分发到对应处理函数 | FastAPI 路由 |
| 办业务 | 后端 Service | 校验、编排、组装结果 | 去重、分页 |
| 取数据 | 后端依赖 | 调外部搜索或查库 | Tavily / SQLite |
| 回响应 | 后端 | 按约定状态码与形状返回 | 200 + JSON 列表 |
| 画页面 | 前端 | 把 JSON 变成看得见的界面 | 结果列表 |

前后端唯一的交接点，就是中间那个"请求与响应"的约定。前端不关心后端是调 Tavily 还是查库，后端不关心前端是 Vue 还是 React，双方只认那份约定。这份约定就是契约：方法、路径、参数、状态码、响应形状，一共五样。

为什么用 JSON 而不是 HTML 做交接？因为 JSON 只传数据不掺表现，同一份结果能被 Web、App、小程序各自渲染；它是纯文本、可压缩、可缓存、可被网关与监控直接读懂。HTML 掺了排版，只能给浏览器看。做"数据交接"选 JSON，做"页面直出"才选 HTML，第 8 章讲渲染选型时已经分过一次。

没有契约会怎样？前端不知道 `q` 是必填还是可选、空结果是 `[]` 还是 `null`、失败回 4xx 还是 200 包错误码；后端不知道前端要不要分页、字段名是驼峰还是下划线。两边只能串行等对方，联调现场变成猜谜。本章后面会给出解法，但先把这条链和这份约定的位置记住：链路是骨架，契约是关节。

## 本节小结

- 一次搜索从"输入关键词"出发，经过发请求、路由、业务、取数、回响应、渲染六站回到页面。
- 前端负责"发"与"画"，后端负责"收"与"办"，两端唯一的交接点是"请求与响应的约定"。
- JSON 是数据交接的共同语言，HTML 是页面直出的产物，两者选型看场景。
- 契约锁定方法、路径、参数、状态码、形状五样，是前后端能并行开发的前提。

金句：链路画清楚再看联调，出的每一个错都有名有姓，都有该去的那一站。
