# 契约落地

学完本节，你能回答：

- 前后端"对得上"具体指哪几样东西对得上？
- OpenAPI 的类型定义，怎么从后端落到前端的类型里？
- 后端把字段从下划线改成驼峰，前端要改多少处？有没有一劳永逸的办法？
- 后端给搜索结果多加一个字段，前端没更新会不会炸？向后兼容怎么做？

> 两家公司签合同，一个写"下周三交货"，一个理解成"下下周三"，到日子就扯皮。前后端契约也一样：路径、形状、状态码，五样里任何一样含糊，联调时都会变成现场扯皮。契约落地，就是把这五样从"口头约定"变成"机器可验证"的东西。

请求能发出去、界面四态也画全，联调现场最常见的翻车还在后面：前后端各写各的，联调时才发现对不上。本节在整章的位置是"对"：把两端唯一的交接点落字为据，让前后端按同一份约定各自开发、各自验证。目的是回答联调现场最贵的那两个问题：以谁为准，变了怎么办。

## 响应形状

第 4 章讲过，后端用 Pydantic 模型 + FastAPI 自动生成 OpenAPI，代码即契约。前进到前端侧，这份契约要落成 TypeScript 类型，否则前端取字段全靠记忆，改一个字段名就得到处翻：

```typescript
// src/types/search.ts —— 对照后端 DocOut 模型手写，字段名一对一
interface SearchResult {
  id: string        // 后端 DocOut.id
  title: string     // 后端 DocOut.title
  source: string    // 后端 DocOut.source
  url: string       // 后端 DocOut.url
  content: string   // 后端 DocOut.content
}
```

手写类型是起点，规模上去之后用 OpenAPI 生成器（openapi-typescript 等）从 `openapi.json` 直接生成，模型一改、类型跟着变，漂移在构建时就被拦住。小项目手写即可，但"类型与后端模型一对一"这条纪律，从第一天就要立。

## 字段命名

Python 后端习惯下划线（`doc_title`），JavaScript 前端习惯驼峰（`docTitle`）。两边各守各的命名，交界处就得有人让一步。常见做法有两种：

| 做法 | 谁让步 | 代价 |
| --- | --- | --- |
| 后端出驼峰 | 后端用 alias 把字段转成驼峰 | 后端模型多一层 alias，Python 侧读着别扭 |
| 前端做转换 | 前端收到后统一把下划线转驼峰 | 前端多一层转换逻辑 |

没有银弹，关键是全项目只用一种，写进契约。文档搜索的 `Document` 字段本就不多，本书统一用后端直出的形状（`title`、`source`、`url`、`content` 全是单个词，无下划线争议），把命名之争消灭在萌芽里。

## 向后兼容

契约一定会变。后端给搜索结果多加一个 `score` 字段，前端没更新，会不会炸？答案是不会——前端取自己认得的字段，多出来的直接忽略。**加字段是安全的，删字段和改字段含义是危险的。**

向后兼容的三条纪律：

1. **只加不删**：新字段直接加，旧字段保留；非要删，先标记废弃、给前端留迁移期。
2. **新字段给默认值**：前端老版本取不到新字段时，后端保证它有合理的默认值，而不是 `null` 炸模板。
3. **改含义等于换接口**：`score` 从"0-1 相关度"改成"0-100"，必须走新版本或新字段，不能悄悄改。

第 4 章的统一信封（`code` / `data` / `msg`）在这里也派上用场：前端先判 `code` 再读 `data`，后端加字段只动 `data` 内部，错误分支的形状永远稳定。

## 统一信封长什么样

统一信封落到联调现场，就是成功与失败各一个固定样子。成功：

```json
{"code": 0, "msg": "ok", "data": [{"id": "doc-001", "title": "Pydantic 简介"}]}
```

失败：

```json
{"code": 40401, "msg": "收藏不存在", "data": null}
```

前端先判 `code` 再读 `data`：Pydantic 校验失败的 422 和业务 404 在前端走同一套三态，不用为每种错误各写一套分支。信封是契约里最便宜的一层稳定，后端加字段只动 `data` 内部，`code` 与 `msg` 的位置雷打不动。

## 本节小结

- "对得上"指五样：方法、路径、参数、状态码、响应形状，全部要机器可验证，不能靠口头。
- OpenAPI 类型落到前端（手写或生成），字段一对一，模型一改类型跟着变。
- 命名只用一种（下划线或驼峰），写进契约；本项目的字段避开下划线，从源头消灭争议。
- 演进只加不删、新字段给默认值、改含义等于换接口，前端取认得的字段、多余的忽略。
- 统一信封让成功与失败走同一套形状：前端先判 `code` 再读 `data`，后端演进只动 `data` 内部。

金句：契约是前后端唯一的共同上级——对不齐不要先吵架，先看契约，再看是谁没按契约办。
