# 错误处理与联调定位

学完本节，你能回答：

- 后端回 4xx 和 5xx 时，前端分别该给用户看什么、做什么动作？
- 前端说"数据没回来"、后端说"日志里 200 了"，这笔糊涂账从哪查起？
- 浏览器 Network 面板里，哪几个字段是联调取证的关键？
- "刷新后状态丢了""切页面要重新登录"这类怪相，分别归哪一站管？

契约对齐了、跨域也过了，联调现场还是会有错。错本身不可怕，可怕的是两边各说各话、定位靠猜。这一节给两样东西：前端按状态码分类处理错误的章法，以及联调出问题时的"四步定位法"。

> 停电了先别怪物业：先看是自家跳闸、单元停电，还是整片区都没电。定位顺序是从离自己近的一端向远端查。联调定位也一样：先看请求发出去了吗，再看状态码对吗，再看响应形状对吗，最后看渲染对吗。从近到远，一站一站排除，不要跳步。

## 前端按状态码分类处理

后端的状态码不是摆设，每一类都对应前端的一种动作：

| 状态码 | 含义 | 前端动作 |
| --- | --- | --- |
| 200 | 成功 | 渲染数据 |
| 400 / 422 | 客户端传错了 | 就地提示错在哪（关键词为空、分页越界） |
| 401 | 没登录 | 跳登录页 |
| 403 | 没权限 | 提示"无权访问"，不重试 |
| 404 | 资源不存在 | 提示"没找到"，收藏页的过期收藏可顺手清理 |
| 429 | 被限流 | 提示"稍后再试"，按 `Retry-After` 等待 |
| 5xx | 服务端错了 | 提示"服务开小差了"，给重试按钮，不要自动无限重试 |

再配上第 4 章的统一信封：先判 `code`，成功才读 `data`，失败走 `msg` 提示。错误分支的形状永远稳定，Pydantic 校验失败的 422 和业务 404 在前端走同一套三态。

```javascript
// 搜索失败的分类：网络错、4xx、5xx 各归各的提示
try {
  const { data } = await api.get('/search', { params: { q: keyword } })
  results.value = data
} catch (err) {
  if (!err.response) error.value = '网络不通，检查后端是否启动'
  else if (err.response.status === 401) router.push('/login')
  else if (err.response.status >= 500) error.value = '服务开小差了，稍后重试'
  else error.value = err.response.data?.msg ?? '请求失败'
}
```

## 四步定位法

联调现场的糊涂账，九成是"跳步猜"猜出来的。按这个顺序走，每一步都有明确的是非：

1. **请求发出去了吗**：打开 Network 面板，有没有这条请求？没有——前端代码根本没发（事件没绑、条件没进、baseURL 拼错）。有——看下一步。
2. **状态码对吗**：200 还是 4xx/5xx？4xx 看请求（参数、路径、token）；5xx 看后端日志。是 CORS 红字——回上一节配跨域。
3. **响应形状对吗**：点开 Response 页签，字段名、类型、空值表示，和契约（OpenAPI/类型定义）对得上吗？对不上——后端改了字段或前端类型过期。
4. **渲染对吗**：数据是对的但页面没显示——前端模板/响应式/路由的问题，按第 9 章的"数据、派生、副作用"三步查。

```bash
# 和浏览器对照的另一只眼：curl 直调后端，排除前端干扰
curl -s "http://localhost:8000/api/search?q=pydantic" | head -c 300
```

curl 通而浏览器不通——八成是 CORS 或前端拼错了 URL；curl 也不通——后端服务或路由本身有问题。两只眼一起看，责任立刻分清。

## 几类怪相归哪管

联调现场几类高频怪相，直接对号入座：

- **"刷新后收藏没了"**：前端 Pinia 是内存缓存，刷新即失——正常；要持久得到后端账户或 localStorage 兜底。
- **"切到收藏页要重新登录"**：token 没带上或过期了——查请求头 `Authorization` 在不在，401 就跳登录。
- **"搜 pydantic 显示的是上次的结果"**：竞态——回"异步状态"一节看序号牌。
- **"本地好好的，一部署就 404"**：前端路由用了 history 模式，刷新时服务器不认这个路径——要配 fallback 到 `index.html`，或切 hash 模式。

## 本节小结

- 状态码即动作：401 跳登录、4xx 就地提示、5xx 给重试，不要所有错误一个弹框。
- 定位从近到远：请求发出了吗 → 状态码对吗 → 响应形状对吗 → 渲染对吗，一站一站排除。
- Network 面板看请求、状态码、响应体三样；curl 是排除前端干扰的另一只眼。
- 刷新丢状态、重复登录、结果串了、部署 404，四个怪相各有归属，不要一锅烩。

金句：联调不靠吼，靠取证——Network 面板和 curl 就是你的两只眼，先看到底是哪一站没办好，再说话。
