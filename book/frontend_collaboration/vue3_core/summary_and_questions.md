## 本章小结

- **Vue 3 是本章的框架载体**：单文件组件聚拢模板、逻辑与样式，组合式 API 按关注点组织代码，Proxy 把响应式补得更圆，Vite 拆分开开发期按需与生产期打包（见 [Vue 3 与 Vite](why_vue3_vite.md)）。
- **模板把数据写进页面**：`{{ }}` 插值放进文字，`v-bind`（简写 `:`）绑进属性，`v-on`（简写 `@`）挂上事件；`v-if` 管条件渲染、`v-for` 管列表（`:key` 区分每项身份），`v-model` 是"传值 + 监听输入"的语法糖（见 [把数据写进页面](template_directives.md)）。
- **响应式让"改数据"与"改视图"焊在一起**：`ref` 装单值、`reactive` 装对象，都是可观测容器；`computed` 管派生值（带缓存），`watch` 管副作用（源变即执行）。本质是"记录依赖 + 变化通知"，你只改数据，视图照着数据的形状自己变（见 [数据如何驱动视图](reactivity_principles.md)）。
- **组件是带契约的部件**：Props 向下只读传数据、Emits 向上发事件通知、插槽留内容位，一套单向数据流覆盖父子通信；`onMounted` 是前端向后端拉数据的标准时机，`onBeforeUnmount` 用来清理（见 [把界面拆成组件](component_design.md)）。
- **路由是"URL 到组件"的映射加一道门**：路由表把页面挂到路径上，`:date` 是动态参数；全局守卫 `beforeEach` 做鉴权、`beforeEnter` 做参数校验；懒加载用动态 `import()` 按路由拆包，首屏只加载当前页（见 [多页面与登录守卫](routing_management.md)）。
- **Pinia 用三层管跨组件状态**：State 存原始状态、Getter 存派生只读、Action 是唯一写入口，单例让任何组件看到同一份；前端状态是缓存、后端是真相，刷新即以 `loadWeather()` 重拉为准（见 [跨组件共享的状态](cross_component_state_pinia.md)）。
- **组件测试守住前端改动**：手动点页面慢且不完整，Vitest 的 `describe`/`it`/`expect` 与 pytest 是一套心智，`@vue/test-utils` 的 `mount` 测渲染（`wrapper.text()`）与交互（`emitted()`），和接口测试的"断言行为 + 替换依赖"同构（见 [组件测试](component_testing.md)）。
- **总体启示**：站在后端视角，Vue 3 的五块恰好都能翻译成熟悉的东西，模板是"数据到界面的取值规则"，响应式是前端的"发布订阅"，组件是"带契约的函数"，路由是"路径到处理器的映射"，Pinia 是"单例服务"。读懂这层对应，联调时"为何视图不动""状态归谁管""刷新后为何丢失"这些提问就有处可查。

## 思考题

1. **请分析**：响应式"改数据就改视图"很省心，但它是隐式的。对比命令式"手动改 DOM"，讨论隐式响应式在排查"界面为什么没更新"时的利弊，并提出一个能从"状态对不对、派生对不对、副作用对不对"三步定位的顺序。
2. **请分析**：模板里写 `{{ weather.city }}`，和写 `document.getElementById('city').textContent = weather.city`，一个是声明式、一个是命令式。结合天气页"加载中/出错/有结果"三种状态的切换，讨论声明式模板省掉了哪些手工活，又带来了哪些排查上的代价。
3. **请判断**：一个页面同时有"天气卡片"和"单位切换"两个区域，都要用到温度单位和天气数据。你何时用 Props 往下传、何时提升到 Pinia？给出判断标准，并说明"提得太早"和"提得太晚"各会付出什么代价。
4. **请分析**：`ref` 和 `reactive` 都能做响应式，但不少团队倾向"简单值用 ref、对象用 reactive"。如果团队想彻底统一只用一个，你会选哪个？为什么？
5. **请判断**：前端路由守卫做了登录拦截，后端接口也有鉴权。这两道门分别防的是什么？如果只留前端拦截、去掉后端鉴权，会发生什么？
6. **请分析**：`onMounted` 里拉数据是惯例，但有些页面在路由切到它之前就该提前请求。结合"进页面才拉"与"提前拉"两种做法，讨论它们的体验差异与各自的适用场景。
7. **请判断**：懒加载按路由拆包让首屏变快，但页面之间切换会多出请求。什么规模的应用值得做懒加载？一个只有两三个页面的小工具是否也需要？
8. **请设计**：前端状态是缓存、后端是真相。为"收藏城市"设计一套"前端先展示、后台再确认"的交互，并说明网络失败时前端该如何退回、如何提示，才能既响应快又不误导用户。

9. **请判断**：组件测试在隔离环境里 mount，不碰真实浏览器和网络，跑得快但覆盖不到真实渲染。结合"组件测试 + 端到端测试"的分工，讨论什么场景下组件测试的断言就够了，什么场景必须补充真实浏览器的端到端验证，并说明各自在流水线里该跑多频繁。
